## 1. 목표와 경계

사용자가 “평소 여유 있는 핏을 좋아하지만 오늘 발표에는 슬림하게”라고 하면 두 정보를 분리한다. 오늘의 슬림 핏은 이번 요청에서만 기본 핏을 대신한다. 새 요청에서는 여유 있는 핏이 다시 기본으로 조회된다. “앞으로도 슬림 핏으로 추천해 주세요”라고 내용과 범위를 명시하면 장기 변경을 별도로 확정한다.

내용이 맞다는 **확인**, 이후 추천에도 쓰겠다는 **동의**, 지금 요청에서의 **적용**, 기록의 **보관**을 각각 다룬다. 기본 취향으로 저장하지 않음, 추천 활용 철회, 실제 삭제는 서로 다른 조작이다. 추정이나 반복만으로 장기화하지 않는다.

이번에는 계약·가상 사례·검증기와 승인 후 구현 계획을 준비한다. 제품 앱·인증·DB·실제 모델·전체 UI·배포·실제 연구 데이터 수집은 구현하지 않는다. 연구 질문을 바꾸지 않는다.

## 4. 기억 단위와 저장 객체 — D01·D05·D09

하나의 기억은 독립적으로 확인·수정·활용 철회할 수 있는 하나의 주장이다. “여유 있는 핏, 고객 미팅이 잦음”은 두 항목이다. “고객 미팅 때 정장 느낌을 피함”은 조건을 포함한 한 항목이다. 부정·강도·예외를 요약에서 지우지 않는다.

| 객체 | 책임과 필수 정보 | 생성 권한 |
|---|---|---|
| Request | 사용자·ID·kind(onboarding/styling)·상태·revision·생성/최근활동 시각·timezone·retention_until | 시스템. 새 요청 원자적으로 생성 |
| MemoryItem | 스키마 버전, ID/소유자/객체 version, content/tags/claim, 범위, 적용 조건·기간, 확인, 근거, lifecycle, lineage | 시스템. 모델은 내용 후보만 제안 |
| UserEvidence | 인증된 현재 입력 참조, 항목별 content/claim/조건/기간/범위 snapshot, 선택 이미지 요소·실제 조작 역할·제시된 철회/삭제 대상 집합 | 시스템이 기록·검증. 모델의 주장만으로 생성 불가 |
| IntentDecision | 입력·문맥 참조, 제안/보류/변경 없음, 근거 대응·확인 질문 | 모델/규칙 adapter. 권한 없는 제안 |

| ContextResult / 추천 기록 | 실제 used/excluded/overridden/truncated/unresolved, 이유, 요청/profile revision, 항목별 version | 조회·결합 계층. 모델 설명과 대조 |

`schema_version`은 형식 버전이고 `version`은 동일 항목 변경 횟수다. 새 항목 version=1, 같은 ID의 확인·근거 추가·철회는 +1이다. 내용·조건·기간·범위의 의미를 바꾸면 새 ID를 만들며 기존 동의는 복사하지 않는다. `profile_revision`은 사용자의 장기 항목 집합이 바뀔 때 증가한다.

동일 input_ref의 여러 항목은 서로 다른 snapshot_id를 쓴다. input_ref는 공통 사용자 이벤트 메타데이터만 식별하고, 각 proposal/action의 snapshot_ref가 대상 내용·claim·권한을 정확히 지정한다. 첫 snapshot의 내용을 다른 항목에 적용하지 않는다. 구조화 claim도 snapshot과 대조해 내용 확인을 다른 속성·방향으로 확대하지 않는다. cause_input_ref는 시스템이 가진 현재 입력과 일치해야 하며 과거 승인 이벤트를 새 입력으로 선언할 수 없다.

`claim`은 최소 `key`, `value`, `polarity(prefer/avoid/require)`, `strength(soft/hard)`다. key는 `fit`, `color`, `material`, `mood`, `formality`, `item.<이름>`, `activity`, `occasion` 같은 작은 명시 사전에서 시작한다. `free_text`는 표시·질문용이며 자동 병합·확정 검색에 쓰지 않는다. 사전은 상품 분류 체계나 고정 스타일 정체성을 강제하지 않는다.

조건은 자연어 표시와 구조화 field/value AND predicates를 함께 둔다. 미매핑 조건은 **unknown**으로 보류하고 확인한다. 조건이 없으면 관련성 검사를 생략하는 것은 아니다. 같은 의미 판정은 key/value/polarity/strength/전체 조건/기간이 일치할 때만 가능하다. 띄어쓰기·태그 유사성만으로 동일성을 주장하지 않는다.

`scope`는 `short_term(request_id)` 또는 `long_term(approval)` 두 가지다. 장기 후보라는 세 번째 활용 범위는 만들지 않는다. 후보는 단기이고 내용 확인 뒤 활성화된다. 장기 직접 create는 대상 내용·기간·조건과 이후 활용을 현재 이벤트에서 모두 확인할 수 있을 때 허용한다. 초기 설정 후보는 kind=onboarding인 Request ID로 묶으며 일반 styling 요청의 단기로 자동 이월하지 않는다.

상태는 `candidate`, `active`, `superseded`, `withdrawn`이다. 만료는 조회 시 기간으로 계산한다. 삭제는 항목 제거이며 상태값을 추가하지 않는다. lineage는 `create`, `promote`, `replace`; promote는 동일 의미의 사본 관계, replace는 의미가 달라진 관계다. 철회가 replace를 무조건 넘어 새 의미까지 중단시키지 않는다.

원본 항목이 삭제돼도 독립 동의가 있는 새 의미의 기억을 함께 삭제하지는 않는다. 이때 시스템은 source_memory_id를 지우고 source_redacted와 source_redaction_id로 관계 소거를 표시한다. 삭제 과정이 생성한 증명은 남아 있는 항목 ID·사용자·관계 연산·변경 version·시각만 담고 지운 부모 ID/내용을 보관하지 않는다. 증명은 그 독립 항목과 같은 보관 시한을 쓰고 해당 항목 삭제 시 함께 지운다. 내용 변경이 아닌 삭제 메타데이터 변경으로 version을 올리며 영향받는 항목 CAS도 검사한다. 신규 모델 제안이 이 표시나 임의의 증명 ID로 원본 검증을 우회할 수는 없다.

## 5. 요청 수명과 날짜 — D02

| 행동 | ID·상태·조건 |
|---|---|
| 새 요청 | 비어 있지 않은 사용자 전송을 시스템이 수락할 때 새 ID·revision=1·open. 이전 단기 없음. 전송 재시도는 동일 ID 반환. |
| 종료 | 사용자 종료 확정으로 closed. 대화창 닫기·추천 표시만으로 자동 종료하지 않음. 단기 추천 적용 중단, 보관은 계속. |
| 취소 | 사용자 취소로 cancelled. 보관·실제 삭제 안내는 별도. 이미 확정한 장기 저장은 취소만으로 되돌리지 않음. |
| 재개 | 같은 소유자의 보관 중 요청에 resume 확정 → 같은 ID·open·revision 증가. 날짜 지난 항목은 제외하고 새 내용 확인. |
| 복제 | 새 ID. 가져올 내용을 먼저 표시하고 사용자가 선택·확인한 내용만 새 입력 근거로 생성. 원본 동의·임시 조건 자동 복사 없음. |
| 보관 만료 뒤 재개 | 요청 내용은 삭제되어 복원 불가 표시. 새 요청·장기 기본 취향에서 시작. |

상대 날짜는 **현재 발화의 발생 시각+사용자 timezone**으로 해석한다. “오늘”은 그 지역 00:00부터 다음 날 00:00까지 `[from, until)`다. 서버 날짜나 접속 지역 추정으로 사용자 timezone을 덮어쓰지 않는다. timezone 미제공 시 확인하며, 기본값으로 UTC를 silently 적용하지 않는다. “다음 금요일” 등 해석이 여러 개인 날짜는 절대 날짜를 보여주고 확인한다. 사용자가 timezone을 바꿔도 이미 확인한 절대 시각은 자동 재작성하지 않는다.

같은 요청을 재개할 때 기간·상황이 여전히 맞는 항목만 복원한다. 기간이 없는 취향은 유지 가능하지만 목적·일정이 달라진 요청이면 영향받는 상황 조건을 재확인한다. 원문 없이 지난 조건을 새 날짜로 재활성화하지 않는다.

## 6. 해석·확인·저장 화면 — D03·D04·D08

| 입력/조작 | 판단·변경 | 화면 결과 |
|---|---|---|
| “오늘은 슬림하게” | 확인된 단기 create. 장기 변화 없음 | 이번 요청에 표시 |
| “평소 좋아해요”, 반복 선택 | 명시 내용 확인 가능, 장기 동의 아님. 같은 활성 의미면 근거 추가 | 기본 저장 후보를 제안할 수 있으나 미체크 |
| 내용 질문에 “맞아요” | 정확히 제시한 항목 version·조건·기간에 연결한 confirm만 | 활성 단기, 장기 동의 없음 |
| 저장 질문에 “맞아요” | 제시된 내용과 이후 활용 범위가 유일하면 그 항목만 저장 | 실제 저장 결과 표시 |
| “기억해 줘”, “앞으로는” 대상 불명 | needs_clarification; 변경 없음 | 어떤 내용을 언제까지/어디에 쓸지 묶어 질문 |
| “앞으로도 이 핏으로 추천해 줘” | 정확한 확인·동의면 long create 또는 기존 short promote | 저장된 문장·조건·기간 표시 |
| 인용·과거 대화·모델 제안 | 현재 사용자의 채택 없으면 확인·동의 아님 | 설명 또는 확인 중, 저장 없음 |
| 이미지에서 핏만 선택 | 명시 선택·설명의 핏만 확인. 색·소재는 확정 안 함 | 핏 조건, 다른 요소는 미확인 |
| 이미지 선택 이유 불명 | 단기 추정 후보 또는 질문. 확정 추천 조건에서 제외 | “어떤 요소가 마음에 드나요?” |

초기 직접 입력은 내용을 항목으로 나눠 보여준다. 이미지 경로는 선택 이미지 ID와 요소/이유를 확인한다. 둘 다 “다음 요청에도 참고할 요소 선택”에서 **기본 체크 해제**, 편집 후 확인·저장을 수행한다. 빈 프로필의 사용하면서 알아가기 경로는 현재 요청으로 바로 간다. 기존 프로필이 있어도 사용자 선택 없이 초기 설정을 재실행하거나 프로필을 덮어쓰지 않는다.

추천 후 저장 후보는 확인된 현재 정보 중 아직 저장되지 않은 항목이다. 요청 전용 일정·날씨는 기본 저장 후보에 섞지 않는다. 반복 상황은 별도 범위 안내 후 저장할 수 있다. 대화 중 명시 저장도 동일한 항목별 확인·동의 계약을 사용한다. 두 경로가 중복 저장하면 같은 구조 일치 항목은 “이미 저장됨”으로 처리한다.

이미지를 바꿔도 이미 확인한 요소는 원래 근거 이미지와 연결해 유지하고 새 이미지 속성으로 자동 변경하지 않는다. 이전 화면으로 돌아가도 확정 조건은 유지한다.

모달의 선택·편집은 확정 전 지역 상태다. 전부 해제하면 저장 버튼 비활성, 이번에만 적용하기·닫기·취소는 장기 쓰기 없음과 현재 요청 유지, 대화 화면 복귀다. 복수 선택 허용. 충돌 수정은 전후·조건·기간을 보여준다. 저장 실패는 전체 실패로 표시하고 선택을 유지한다. 사용자가 별도 일부 선택으로 다시 확정하기 전에는 일부만 저장하지 않는다.

조건 패널은 기본 스타일, 이번 요청, 확인 중을 구분한다. 기본 항목에는 `이번 요청에서 제외`, `기본 취향 수정`, `활용 철회`, `기록 삭제`를 각각 제공한다. 이번 요청 제외는 request-local exclusion이며 장기 상태를 바꾸지 않는다. 오래된 저장 화면은 현재 항목 버전과 다르면 저장 대신 변경 내용을 다시 보여준다. UI 세부 디자인·Figma 변경은 후속 구현 범위다.

## 7. 쓰기 전이·중복·실패 — D05·D09

| 연산 | 사전 조건 | 결과 |
|---|---|---|
| create | 근거가 같은 사용자 현재 입력. 추정은 미확인 단기만; 장기는 내용+활용 동의 | 새 ID. 단기는 candidate 또는 active, 장기는 active |
| confirm | 현재 단기 candidate와 제시 내용·버전이 일치하는 내용 확인 | 같은 ID active, version 증가 |
| promote | 활성·확인 단기, 동일 의미·조건·기간의 이후 활용 동의 | 새 장기 ID, short 유지, 동일 가족 표시 |
| replace | 수정할 대상·새 의미 확인; 장기는 새 동의. 활성→미확인 교체 금지 | 새 ID+기존 superseded를 함께 확정 |
| withdraw | 대표 항목과 동일 promote 가족·영향 범위를 표시한 현재 사용자 확인 | 가족 전체 withdrawn, 즉시 추천·질문 근거에서 제외 |
| add_evidence | 활성·확인 항목과 구조 동일. 새 사용자 근거 | 같은 ID/version+1, 내용·범위·동의 기간 유지 |
| delete | 삭제 범위/파생 영향 제시 후 현재 사용자 확정 | 해당 데이터 접근 차단·삭제 작업. 아래 D10 계약 |

같은 내용의 재저장은 신규 장기 ID를 만들지 않는다. 확인된 구조가 같은 장기 항목이 있으면 기존 결과를 보여주며 현재 근거만 필요 시 추가한다. 조건·기간·부정·강도가 다르면 별도 정보 또는 명시 replace이고 자동 병합하지 않는다. 철회 정보의 재저장은 경계 이후 새 확인·새 장기 동의로 새 ID를 만든다.

시스템 실행 순서는 현재 사용자 입력 기록 → 소유권·요청/프로필 snapshot 조회 → 의도 제안 → 구조/참조/내용·동의/전이 검증 → 최신 CAS 재검사 → 배치 전체 확정 → 새 조건·추천 갱신 필요 표시다. LLM은 IDs/소유자/확정 상태/동의/감사 이벤트를 확정할 수 없다. schema에 맞는 동의 문자열도 실제 사용자 이벤트와 대응하지 않으면 거부한다.

한 UI 확정은 하나의 `batch_id`다. 내부 actions는 선행 결과를 참조할 수 있지만 commit 전 staged 상태에서 모두 검증한다. 검증·버전·저장·이벤트 실패 중 하나라도 있으면 전체 rollback이다. 선택적 저장은 사용자가 선택한 일부를 한 번에 성공시키는 뜻이며, 시스템이 임의로 일부 성공시키는 뜻이 아니다.

최소안의 실제 삭제는 전용 관리 배치다. 저장/교체와 삭제를 한 배치에 섞는 입력은 보류하고 각각의 영향 범위를 확정한다. 삭제 완료 영수증은 항목 내용/ID를 포함하지 않는 opaque token·fingerprint·완료 시각·24시간 시한이며 일반 저장 result와 분리한다.

| 오류 | 쓰기 결과·복구·UI |
|---|---|
| invalid_schema / invalid_reference / unauthorized | 변경 없음. 외부에 다른 사용자 객체 존재를 드러내지 않음. 입력 수정 또는 다시 조회 |
| needs_clarification / consent_required / conflicting_intents | 변경 없음. 대상·내용·범위 질문 후 새로운 현재 이벤트로 재판단 |
| version_conflict / stale_context | 전체 변경 없음. 최신 상태를 표시하고 새 동의가 필요하면 재확인 |
| request_closed / request_expired | 단기 쓰기 없음. 재개 확정 또는 새 요청 안내 |
| idempotency_conflict | 동일 ID의 다른 본문 거부. 새 의도는 새 batch ID |
| storage_failure | 전체 rollback·선택 유지. 같은 ID/본문 재시도 |
| deletion_pending / deletion_failed | 이미 활용 차단됨. 완료로 표시하지 않고 삭제 상태·재시도 표시 |

성공한 동일 `user_id+batch_id`와 동일 본문 재시도는 최초 result 반환, 이벤트 중복 없음. payload digest는 삭제 시 제거한다. 다른 본문이면 충돌이다. 실패한 배치는 성공 영수증을 만들지 않으며 저장 장애 재시도는 같은 ID를 쓴다. 버전 충돌 후 재검토로 본문이 달라지면 새 ID를 쓴다.

모델 응답·추천은 request revision, profile_revision, context_snapshot_id와 연결한다. 어느 하나라도 달라지거나 요청이 닫혔으면 늦은 응답을 현재 패널에 적용하지 않는다. 장기 변경은 같은 사용자의 열린 요청들에서 기존 추천을 갱신 필요로 표시한다. 쓰기 전 재검사와 화면 전 재검사를 모두 수행한다. 실제 DB 원자성·동시성은 후속 통합 테스트 대상이다.

## 8. 조회·결합·모델 문맥 — D06·D07·D08

추천 조회는 다음 순서다. 이후 단계의 높은 관련성 점수로 앞 단계의 제외를 우회할 수 없다.

1. 인증 사용자와 소유권 일치, 요청 open·보관 중인지 확인한다. 다른 요청의 단기·온보딩 후보는 제외한다.
2. active·confirmed만 추천 대상으로 둔다. 후보는 별도 확인 질문 목록, withdrawn/superseded는 개인화 질문에도 쓰지 않는다.
3. 기간 `[from, until)`과 retention을 적용한다. 구조화 조건을 현재 요청 facts와 비교한다. 불일치는 제외, unknown은 질문 대상으로 분리한다.
4. 장기 관련성은 요청 `target_keys`와 claim.key 일치=3, tags 교집합=2, 사전에 등록된 일반 스타일 key=1, 그 외=0. 최고 한 점수를 사용한다. `free_text`/미매핑 조건은 보류한다. 단기는 현재 요청에 확인된 조건이므로 관련성 절삭을 하지 않는다.
5. request-local exclusions 반영 → 동일 promote 가족 대표 선택 → 충돌 판정. 가족 대표는 현재 단기 우선, 없으면 최신 활성 장기. ID 목록을 연결해 한 번만 반영한다.
6. 초기 단일값 슬롯은 fit/formality/occasion이다. 같은 key의 다른 value가 겹치는 적용 조건에서 상충하면 명시된 현재 단기가 장기를 일시 대체한다. color/material/mood/activity/item.*의 다른 positive value는 공존 가능하다. 같은 value의 prefer/require와 avoid는 상충이다. 같은 범위의 상충은 둘 다 unresolved로 빼고 질문한다. `hard`와 `soft`는 제약 강도이며 동의·범위 우선순위를 역전시키지 않는다.
7. 점수 내림차순 → created_at 내림차순 → ID 오름차순으로 장기를 최대 12개, 단기를 최대 20개 담는다. 단기를 먼저 예산에 담고 장기를 담는다. content+조건 표시의 Unicode 문자 총 6,000, 항목을 중간 절단하지 않는다. 초과는 truncated와 이유로 남긴다. 필수 단기/hard 조건을 예산 때문에 뺄 경우 추천을 보류하고 조건 축약·확인을 요청한다.
8. used/excluded/overridden/truncated/unresolved와 사유·버전 묶음을 context에 기록한다. 결과 없음은 빈 프로필 가능으로 처리하고 현재 요청 정보만 사용한다. 낮은 관련성을 개인화 근거로 끼워 넣지 않는다.

임의 점수는 의미 정확도 확률이 아니며 재현 가능한 최소 랭킹 파라미터다. 12/20/6,000은 승인된 프로토타입 초기값이다. 누락·질문 부담·예산 초과를 후속 파일럿에서 기록하고 변경할 때 문서·fixture도 맞춘다. 벡터 검색 도입은 필요가 확인된 별도 설계 변경이다.

장기 12개는 기본 스타일의 작은 활성 집합을 먼저 검토하려는 상한, 단기 20개는 요청별 상황·취향 항목을 명시적으로 점검할 상한이다. 6,000자는 모델 토큰 한도를 확정하는 수치가 아니라 content·조건의 크기를 제한하는 초기 운영값이다. 이를 넘으면 중요한 조건을 조용히 잃지 않고 사용자에게 알려 조정한다.

LLM 추천 입력은 `base_preferences`, `request_constraints`, `unresolved_questions`, `used_refs`를 분리한다. 미확인 후보는 추천 조건 배열에 넣지 않는다. 최근 대화는 질문 대상 연결에만 최소한 제공하며 구조화 기억으로 확인되지 않은 과거 문장을 선호로 재추출하지 않는다. 요약은 사용 가능 항목 ID/version으로 재생성하고 부정·조건·기간을 보존한다. 원문을 압축한 자유문 요약을 별도 개인화 정본으로 저장하지 않는다.

모델 설명의 “기본 취향”과 “이번 예외”는 실제 used/overridden에 대조한다. 예: “이번 발표에는 슬림 핏을 적용했습니다. 기본 여유 핏은 다음 요청에도 유지됩니다.” 무관한 기억이나 제외된 기억을 추천 이유로 주장하면 결과를 다시 생성하거나 설명을 교정한다.

## 9. 보관·철회·실제 삭제 — D10

아래 기간은 **사용자가 승인한 초기 메모리 설계 정책**이다. 법적 의무·문헌 결과·현재 서버 정책이 아니다. 의미의 유효 기간과 데이터 보관 시한 중 이른 시점부터 추천 활용이 제한된다. 데이터 종류별 삭제 작업의 성공은 별도 확인한다.

| 데이터 | 최소 내용·보관 종료 | 활용/삭제 효과 |
|---|---|---|
| 요청·원문·선택 이미지 참조·단기/후보 | `min(last_activity+30일, created_at+90일)` | 종료/취소면 단기 적용 중단. 보관 만료면 물리 삭제·재개 불가. 조회만으로 활동 시각 연장 금지 |
| 사용자 업로드 이미지 원본·음성 | 최소안은 수집/영속 저장하지 않음 | 가상/참조 이미지 ID만 사용. 실제 업로드 도입 전 별도 정책·권한 필요 |

| 변경 이벤트 | IDs/버전/상태/역할/시각, content 전체 snapshot 없음. 참조 데이터와 함께 또는 최대 90일 | 삭제 대상의 근거·연결은 삭제/비식별화. 감사 이유로 원문 보존하지 않음 |
| 독립 기억의 원본 관계 소거 증명 | 남아 있는 항목 ID·사용자·관계 연산·version·시각·opaque 증명 ID만, 그 항목과 같은 시한 | 삭제된 부모 ID/내용 없음. 임의의 source_redacted 표시를 증명과 대조. 해당 독립 항목 삭제 시 함께 소거 |
| 추천·적용/제외 로그 | 요청 보관 기간. 원문/기억 content 중복 저장 없이 IDs·이유·버전 | 연결 항목 삭제 시 참조·설명 파생 내용도 소거/재생성 |
| 요약·검색 인덱스·문맥 캐시 | canonical 활성 ID/version 기반의 재생성 자료. 캐시는 메모리 내 한 처리 수명 | 철회/교체/삭제/버전 변경 즉시 무효화. 디스크 캐시·벡터 인덱스 없음 |

30일 비활동 시한은 가까운 요청을 다시 열 수 있게 하면서 원문을 무기한 남기지 않으려는 제안이고, 생성 후 90일 상한은 재개가 반복돼도 원문 보관이 계속 연장되지 않게 한다. 365일 장기 시한은 계절이 한 번 바뀐 뒤에도 쓰는 취향을 연 단위로 다시 선택하게 하려는 제안이다. 비활성 내용 30일은 최근 수정·철회 내용을 확인할 이력 창이다. 연구로 최적 기간이 입증된 것은 아니므로 사용자는 이 목적과 부담을 포함한 권고안 전체를 승인했다.

장기 기억의 독립 동의 snapshot은 내용·조건·범위·기간·사용자 확정 역할의 최소 표시값이다. 원요청 전체를 계속 보관하기 위한 수단이 아니다. 원요청 만료 뒤에도 승인된 장기 정보와 snapshot은 장기 보관 시한까지 유지된다. 원래 input ref가 삭제됐으면 redacted 참조임을 명시하고 존재하지 않는 원문이 있다고 표시하지 않는다.

**활용 철회**는 현재 대표와 동일 promote 가족을 보여주고 즉시 추천·확인 질문·요약에서 뺀다. 내용 보관은 제한된 이력 기간 동안 계속하며 UI에 “추천에는 쓰지 않으며, 기록 삭제는 별도”라고 표시한다. `이번 요청에서 제외`는 현재 요청에만 적용되는 제외다.

**기록 삭제**는 먼저 접근·활용을 차단하고 canonical+동일 사본+근거 snapshot+원문 해당 부분+요약/인덱스/캐시+추천 설명/참조+개인 참조 영수증을 삭제한다. 다른 항목이 같은 원문에 의존하면 해당 부분을 안전하게 지우고 독립 확인 snapshot만 남긴다. 부분 삭제를 보장할 수 없으면 전체 원문을 지우고 영향받는 항목을 표시한다. 삭제 범위 밖 독립 장기 snapshot의 유지 여부도 UI에 제시한다.

요청 삭제는 그 요청의 원문·단기·추천·파생자료를 지우며, 독립 승인된 장기까지 지울지는 영향 범위 화면에서 선택·확정한다. 기억 항목 삭제는 해당 의미 가족의 저장된 내용과 그 내용의 파생 근거까지 지운다. 계정 전체 삭제는 사용자 namespace 전체다. 모든 경로는 같은 삭제 closure 계산을 쓴다.

오래된 입력·응답·요약에서 삭제/철회 정보를 자동 재생성하지 않는다. 명시 삭제 후 payload가 사라져 내용 비교 tombstone을 보관할 필요가 없다. 개인 내용·ID가 없는 프로필 변경 버전과 삭제 시점 경계로 과거 입력·저장 화면의 재사용을 막는다. 이 경계는 남은 과거 원문을 처리할 수 있는 기간에 한정해 최대 90일이며 계정 삭제 시 함께 소거한다. 삭제 이후 사용자의 **새 입력**이 같은 내용을 말하면 새 내용 확인이 가능하고, 장기는 새 동의가 필요하다. 삭제 재시도는 항목 정보 없는 완료 토큰으로 응답하고 같은 ID의 다른 본문은 거부한다. 삭제 작업 실패는 차단 상태를 유지하고 `삭제 처리 중/실패`를 표시한다. canonical transaction과 파일 제거·캐시 무효화까지 확인한 뒤 완료로 바꾼다. SQL DELETE만으로 끝내지 않으며 secure_delete·DB 정리·journal 확인을 후속 저장소 검증에 포함한다. 완료 범위는 시스템이 관리하는 데이터이며 OS/저장매체나 사용자가 만든 외부 사본의 복구 불가를 약속하지 않는다. 이번 fixture 통과는 실제 디스크·백업 삭제를 검증한 것이 아니다.

## 10. RQ1 비교와 RQ2 책임 경계 — D12

2026-10-04의 RQ1은 비분리 방식과 분리·확인·수정 제공 방식의 결합 효과를 비교한다. 기능별 단독 효과로 확대하지 않는다. 실사용 기본 취향을 자동 오염시키는 구현을 대조 조건으로 배포하지 않는다.

| 요소 | 비분리 비교 adapter | 분리·확인·수정 adapter | 공통 통제 |
|---|---|---|---|
| 기억 입력 | 가상 trial의 확인된 기본·임시 정보를 하나의 논리 pool에서 이어 사용 | 장기와 현재 요청의 단기만 사용 | 동일 초기 문장·부정/조건·후보 품질·사용자 namespace |
| 이어지는 요청 | 앞 과제의 임시 정보가 pool에 남는 기대 사례 | 이전 단기는 자동 이월 안 됨 | 두 과제의 동일 입력·순서; 조건별 namespace 완전 분리 |
| UI·수정 | 범위 구분 없이 조건 목록·대화 수정 | 기본/이번/확인 중, 범위 선택·항목별 수정 | 같은 추천 후보·설명량·응답 지연을 맞추는 계획 |
| 권한·보관 | 실사용 저장소 자동 변경 없음 | 사용자 확정에 따른 변경 | 소유권·삭제·수집 동의·기간을 실험 요인으로 바꾸지 않음 |

이 비교 adapter는 우선 **가상 fixture 전용**이다. 비분리 pool은 별도 study/trial namespace이며 실제 장기 저장 정책을 우회하지 않는다. 실제 참여자 연구로 확장하려면 과제 내 입력 재사용 설명·동의·로그 보관과 조건 순서/배정 등을 별도 프로토콜에서 승인해야 한다. 이번 설계가 참여자 수집이나 전체 프로토콜을 확정하지 않는다.

이어지는 과제는 “기본 여유 핏 → 오늘 발표에만 슬림 → 다음 일상 요청”이다. 실제 사용한 IDs/범위, 임시 이월, 사용자의 수정·저장 선택과 설명을 기록한다. 평가지표는 추천 방향을 제어한다고 느끼는 정도와 그 근거 행동이며, 추천 정확도·질문 수는 대체 지표가 아니다.

메모리 계층은 **무엇이 미확인/충돌/동의 부족인지** 제공한다. RQ2 대화 정책은 그 사실에 따라 **텍스트·이미지 형식과 다음 질문 순서**를 선택한다. 저장 동의가 부족하다는 이유로 특정 형식이나 고정 질문 수를 강제하지 않는다. 내용·범위 확인은 연구 조건에 맞춰 제공하되 저장·권한 검증은 형식과 무관하게 동일하다. RQ2 전체 정책·이미지 공급 품질은 이번 범위 밖이다.

## 12. 승인 및 한계

**2026-10-13 사용자 최종 승인 완료:** D01–D12, 두 ADR, 보관 기간·검색 상한·Python+SQLite 최소안과 후속 구현 계획을 승인 회신에 따라 확정했다. Issue #1의 설계·계획 범위와 AC별 근거는 [구현 계획 6–7절](memory-implementation-plan.md#6-ac별-완료-근거)에 정리했다. 원격 Issue 종료·체크박스 갱신은 수행하지 않았다. 중요한 결정 변경은 새로운 승인·ADR로 기록하고 계약·사례·현재 동작 문서를 함께 조정한다.

구조 검사·가상 정책 검증은 동의 진위, 모델의 한국어/이미지 이해, 실제 SQLite 원자성, 파일/백업 삭제, 사용자 제어감 개선을 보장하지 않는다. 실제 제품의 인증·수집·외부 모델·연구 프로토콜은 이번 승인 범위와 별도다.
