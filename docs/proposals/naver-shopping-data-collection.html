A

무엇을 먼저 확정할까

항목 추천하는 1차 범위 이유
상품 범위 네이버 쇼핑에 입점한 스마트스토어·브랜드스토어의 여성 바지 현재 고정 사전의 값 있는 실행 매핑은 Pants만 지원한다. 연구 전체의 과제나 RQ를 바꾸는 결정은 아니다.
실제 수집원 사용 권한을 확보한 판매자 상품자료·이미지와 허용된 상세페이지 검색목록만으로 소재·옵션별 이미지·디테일 근거를 확보하기 어렵다.
데이터 단위 판매처의 상품 ID × 색상 옵션 1개 블랙 사진에 베이지 라벨이 붙는 오류를 막고, 선택 이미지와 상품 Map을 대응시킨다.
종류 구성 Jeans·Leggings·Slacks·Overalls·Cargo pants·Chinos·Jogger의 7종을 포괄 Slacks·Jeans 중심으로 시작하고 나머지 종류도 확보한다. 희귀 종류의 동일 수량을 강제하지 않는다.
초기 수량 파일럿 60개 → 화면 검증용 최대 80개 → 수집·라벨 자산 1,000개 모두 상품×색상 기준이다. 대규모 자산과 현재 실행용 카탈로그의 크기를 구분한다.
공급 다양성 확보 가능한 8~12개 판매처를 목표 특정 판매처의 사진·문구에만 맞는 추출 규칙을 피한다. 판매처 수보다 사용 권한과 자료 품질을 우선한다.
첫 수집에서 뺄 자료 구매자 리뷰·리뷰 사진·닉네임, 주문·개인 정보 PI 중심의 첫 구현에 필요하지 않다. 리뷰 기반 FEA는 추후 필요성과 수집 가능성을 검토한다.

수집 경로의 전제가 바뀌었다. 네이버 쇼핑 검색 API는 2026-07-31 종료됐고 NAVER API HUB에도 대체 API가 없다. 예전 쇼핑 검색 API의 상품 ID·최저가 응답을 전제로 크롤러를 설계하면 안 된다. 네이버 종료 공지, 이관·대체 API 안내.

권장 순서는 판매자 제공 파일·이미지 → 권한이 있는 스토어의 커머스API → 수집이 허용된 공개 상세페이지다. 커머스API는 권한이 있는 스토어 자산에 접근하는 수단이며 다른 스토어 전체를 조회하는 공개 검색 API가 아니다. 판매자 파일도 필요한 컬럼·이미지를 실제로 제공받을 수 있는지 확인해야 한다. 커머스API센터의 접근 범위.

페이지 수집은 대상의 약관·robots 정책과 이용 범위를 확인한 경로에 한정한다. robots 허용만으로 이미지 재사용 허락까지 확보한 것으로 보지 않는다. 접근 차단이 발생하면 해당 작업을 중단하고 판매자 자료 제공 경로를 사용한다. 네이버 수집 정책, 콘텐츠 이용 관련 약관.

이번에 확정할 수 있는 것은 데이터 사양이다. 실제 판매처·제공 권한·상세페이지 접근성은 아직 확인하지 않았으므로, 자동 수집 경로와 확보량은 파일럿에서 확정한다.

상품마다 무엇을 가져올까

묶음 수집할 원자료 사용처
식별·출처 판매처 ID, 상품 ID, 원문 URL, 수집 시각, 판매자 모델 코드가 있으면 해당 코드 중복 제거와 원자료 추적. 네이버 가격비교 카탈로그 ID와 판매자 상품 ID를 분리한다.
이름·분류 상품명 원문, 카테고리 경로, 브랜드·제조사 원문, 상세 설명 Type 후보와 근거. 판매처 이름을 브랜드로 대체하지 않는다.
옵션·거래 정보 색상/사이즈 옵션 ID·이름, 옵션별 판매 가능 상태, 기본 판매가·옵션 추가금·통화·배송비 상품×색상 분리, 정확한 가격 보존. 회원/쿠폰 조건부 가격과 일반 판매가를 구분한다.
기술 정보 제품 소재·부위별 혼용률, 핏 설명, 디테일, 실측표·세탁/관리 정보 Fabric·Fit·Detail과 기능 해석의 근거. 미기재·상품상세 참조를 실제 값으로 채우지 않는다.
이미지 색상이 식별되는 상품/착용 사진, 앞·뒤·디테일, 필요한 상세정보 이미지 추천 카드, 부분 선택, OCR·시각 라벨 후보. 모든 이미지를 한 장으로 합치지 않는다.
증거·재현 정보 원문 필드/구절, HTML 또는 제공 파일의 해시, 이미지 바이트 해시, 파서·정규화 규칙 버전 라벨의 원자료·처리 규칙·재검토 이력을 연결한다.

네이버의 공식 원상품 구조체에는 의류의 소재·색상·치수·취급 주의사항과 옵션 조합 필드가 있다. 스키마에 필드가 있다는 사실은 모든 공개 페이지에서 값이 충실하게 제공된다는 뜻이 아니다. 제공 파일/API/페이지마다 실제 확보 여부를 측정한다. 원상품 정보 구조체.

하나의 상품이 3색·4사이즈라면 기본적으로 색상별 Map 3개를 만든다. 사이즈 12개는 원자료 옵션으로 보존한다. 사이즈에 따라 소재·기장·형태가 달라지면 추가로 나누고, 색상별 이미지 대응이 불명확한 옵션은 화면용 목록에서 제외한다. 동일 디자인의 다른 색상은 별도 선택 후보이지만 독립 디자인 수로 세지 않는다.

사이즈·기장·혼용률·판매상태는 수집 가치가 있어도 고정 PI/FEA의 새 feature로 추가하지 않는다. 원자료에 보존하고 사전에 있는 값만 상품 Map으로 보낸다.

PI 7개 항목은 어디까지 채울 수 있을까

다음의 높음·중간 평가는 상세정보를 확보했을 때의 설계상 판단이다. 실측 완성률이나 모델 정확도는 아니다.

PI 확보 가능성·주요 근거 정규화와 현재 실행 경계
Type 높음. 카테고리·명시 상품 분류·상품명 허용된 바지 종류 7개로 매핑한다. 단순히 팬츠라고만 쓰였으면 세부 종류는 미확인이다. 상품명에서 추출한 후보를 자동 확정하지 않는다.
Brand 원문 확보 가능. 브랜드 필드·제조사 정보 원문과 공급자 ID를 보존한다. 419개 전체 사전이 미공개여서 현재 Brand 실행 매핑은 미지원이다. 판매자명이나 모델 추측으로 채우지 않는다.
Price 수치 확보 가능. 일반 판매가·옵션 추가금 수치·통화·조건·시각을 원자료에 보존한다. 현재 코드는 숫자 가격→고정 5구간을 계산하지 않는다. 경계·통화·가격 기준 결정이 먼저다.
Color 높음. 선택 옵션·색상 고시·색상별 사진 15개 허용값을 쓴다. 검정→Black처럼 의미가 명확한 규칙부터 검토한다. 아이보리·오트밀·먹색처럼 경계가 모호하면 원문을 남기고 미확인/검토로 둔다.
Fit 중간~높음. 명시 핏 설명, 보조 이미지 Baggy·Bootcut·Skinny·Straight·Slim·Wide의 6값이다. 와이드→Wide는 검토 가능한 규칙이다. 세미와이드·여유핏은 일괄 치환하지 않는다.
Fabric 중간~높음. 부위별 소재 고시·혼용률 Nylon·Rayon·Linen·Cotton·Wool·Polyurethane·Polyester. 혼방은 복수 값으로 남긴다. 데님/니트는 섬유 원료가 아니므로 Cotton/Wool로 추측하지 않는다.
Detail 중간. 명시 설명·디테일 사진 Roll-up·Banding·Washing·Pleats·Distressed. 설명이 없으면 사진에서 후보를 제안할 수 있지만 검토 전 확정하지 않는다. 세탁 방법을 Washing으로 읽지 않는다.

1차 검색에 연결할 핵심은 Type·Color·Fit·Fabric·Detail의 5개 축이다. 상품마다 5개가 모두 확인된다는 뜻은 아니다. Brand와 Price는 수집을 진행하되, 현재 실행의 공백을 원자료 확보와 혼동하지 않는다.

가격의 후속 실행 규칙으로는 KRW 일반 판매가+옵션 추가금, 배송비·조건부 쿠폰 제외, 구간은 하한 포함·상한 제외를 추천한다. 예컨대 43,900원은 두 번째 구간이다. 이는 아직 승인되지 않은 제안이며, 기존 구간 문자열이나 실행 코드를 이번에 바꾸지는 않는다. “5만 원 이하” 같은 수치 예산은 구간만으로 정확히 처리할 수 없으므로 별도 수치 필터도 필요하다.

Fabric은 겉감·안감·주머니감을 구분해 보존한다. 혼용률 일부가 없거나 사전 밖 섬유가 포함되면 부분 목록으로 “울 없음” 같은 부재를 확정하지 않는다. 현재 검색은 확인된 값의 포함 여부로 회피 조건을 판정하므로, 완전한 조성을 확인하지 못한 자료를 완전한 Fabric 라벨처럼 공급하지 않는 검증이 필요하다.

D

FEA 30태그는 어디까지 채울 수 있을까

FEA는 소비자 요구와 상품 근거를 연결하는 의미 분류다. PI와 합쳐 37개의 동등한 물리 속성으로 취급하지 않는다. 30개 모두의 빈 칸을 채우는 작업을 목표로 삼지 않는다.

Aesthetic · Trends 수집 시점의 외부 유행 근거·명시 설명 신상·인기순·검색 순위만으로 유행 반영을 확정하지 않는다. 첫 데이터에서 필수 완성 항목으로 삼지 않는다.

초기에는 TPO·신발 매칭·실루엣 관련 태그의 해석 후보를 확보하기 쉽고, 기능성·가성비·유행·타인의 반응은 검증 부담이 크다고 본다. 이는 가능성에 대한 판단이며 실제 채움 비율은 파일럿에서 태그별로 측정한다.

판매자 설명은 “판매자가 이렇게 주장했다”는 근거다. 사람이 그 문장을 읽었다고 성능을 측정한 것이 되지는 않는다. 맥락 적합성 라벨을 사람이 검토할 때도 그 검토 범위를 기록한다.

E

크롤링부터 전처리까지 어떻게 진행할까

  1. 수집 목록을 고정한다. 먼저 소수 판매처의 제공 자료 또는 허용된 URL을 확보한다. 허용된 목록 탐색에 한해 종류·핏·가격대를 나눠 표본을 구성한다. 검색어·시각·순위·광고 여부가 확인되면 수집 이력에 남기되, 이를 상품 feature의 근거로 쓰지 않는다.
  2. 원본과 파싱 결과를 분리한다. 제공 JSON/CSV·허용된 HTML·이미지와 해시를 저장한다. 일반 HTTP로 구조 정보를 확보하고, 허용된 동적 페이지에 필요한 경우 브라우저의 정상 렌더링 결과를 파싱한다. 403·429·차단 화면·빈 결과를 구분해 실패를 기록한다.
  3. 색상·사이즈·이미지를 연결한다. 옵션의 순서나 대표 사진만으로 색상을 단정하지 않는다. 각 사진의 색상·뷰·대상 바지를 검토하고, 코디의 상의·신발을 바지 feature로 읽지 않게 한다. 부분 선택용 바지 영역은 원본 이미지 좌표로 연결한다.
  4. 텍스트와 이미지를 정리한다. 표시 태그·공백·문자 인코딩을 정리하면서 원문을 보존한다. 상세정보 이미지의 OCR은 원본 이미지 ID·영역·인식 문장을 연결한다. 부정어·조건·단위·혼용률을 보존하고 무조건 스톱워드를 삭제하지 않는다.
  5. 중복을 묶는다. 동일 판매처 상품 ID·옵션 ID로 정확 중복을 처리한다. 모델 코드·브랜드·사진 해시로 판매처 간 동일 디자인 후보를 묶고 사람이 확인한다. 이미지 유사도만으로 다른 상품을 삭제하지 않는다. 모델 평가용 데이터는 색상·사이즈·재판매가 같은 분할에 들어가게 한다.
  6. 실행용 자료를 내보낸다. 검토한 원자료·라벨을 현재 CatalogRecord JSONL로 변환한다. 원본 HTML 전체를 4,000자 description에 밀어 넣지 않고, 필요한 발췌와 외부 원본 참조를 유지한다. 이미지 바이트는 별도 준비하며 개발·실험 데이터와 실행 DB는 저장소 밖에 둔다.

원자료는 수집 재시도 없이 다시 파싱할 수 있어야 한다. 원문 변경·규칙 변경·라벨 변경을 별도 버전으로 관리하고, 실험에 쓰는 카탈로그는 실행 중 고정한다. 판매 상태·가격은 특정 수집 시점의 정보로 표시한다.

F

라벨을 어떻게 만들고 검토할까

구조 필드 → 검토된 정규화 규칙 → OCR/텍스트·이미지 해석 → 사람 검토 순서를 추천한다. 새로운 모델 학습부터 시작할 필요는 없다. 자동 라벨과 사람 검토 결과를 구분해 축적한 뒤, 반복되는 오류가 확인되면 학습 필요성을 판단한다.

상태 부여할 조건 검색에 연결하는 방식
confirmed 정확한 canonical PI 메타데이터 또는 해당 판단을 뒷받침하는 검증 라벨 현재 코드의 필수 조건·선호 점수 계산에 사용된다. 공급자가 무엇을 확인했는지 별도 기준이 필요하다.
inferred 모델/OCR 해석·모호한 별칭·미검토 후보 후보·검토 대상으로 보존한다. 현재 코드는 상품의 inferred 값을 필수 조건이나 선호 점수에 사용하지 않는다.
unknown 자료 없음·판단 근거 부족 값은 null이다. 언급이 없다는 이유로 FEA false를 채우지 않는다.
conflict 제목·옵션·상세·이미지 등에서 상충 원문을 보존하고 검토한다. 모델 자신감으로 덮어쓰지 않는다.

규칙의 첫 대상은 명시적인 일대일 표현이다. 검정→Black, 면→Cotton, 와이드→Wide도 적용할 필드와 예외를 먼저 검토한다. raw_metadata.supplier_fit="Wide"를 넣으면 현재 매퍼는 직접 확인값으로 받아들일 수 있으므로, 미검토 모델 출력을 이 필드에 넣어 확정값처럼 만드는 전처리를 금지해야 한다. 원문과 규칙·검토 이력은 유지한다.

모델을 사용한다면 고정 사전의 경로·값만 출력하게 하고, 원문 구절이나 실제로 본 이미지·영역을 근거로 요구한다. 모르면 null, 후보는 inferred다. 이미지 추론은 실제 이미지 바이트를 입력한 별도 과정이어야 한다. 현 catalog_mapping.py는 이미지 바이트를 읽거나 모델에 전달하지 않는다.

가상 예시: 상품 고시가 “네이비 / 와이드 / 겉감 면 97%, 폴리우레탄 3%”이고 “출근룩으로 추천”이라는 문구가 있다고 하자. 고시와 옵션을 검토해 Color=Navy, Fit=Wide, Fabric=[Cotton, Polyurethane]를 부여할 수 있다. 혼용률과 부위는 원자료에 남긴다. Business wear는 용도 해석 후보, Elasticity는 함량만으로 미확인이다. 매칭 신발 사진이 없으면 Sneakers는 null이다.

각 판단에는 최소한 상품/색상 ID, feature 경로, 값, 상태, 원문 필드·구절 또는 이미지 영역, 처리 규칙·사전 버전, 검토자·시각·검토 근거를 연결한다. 현재 labels[].provenance에는 source_field, quote, evidence_ref, verifier, verified_at을 대응시키고, 추가 작업 이력은 별도 감사 자료로 보존한다. 기존 CatalogRecord의 최상위 필드를 임의 확장하지 않는다.

G

얼마나 모으고 무엇으로 통과를 판단할까

단계 제안 규모 이 단계에서 내릴 판단
파일럿 상품×색상 60개, 종류·판매처·핏·가격 다양성 확보 접근/제공 가능성, 필드 누락, 옵션-사진 대응, PI별 자동화 가능성, FEA 근거 유무를 확인한다.
규칙 개발과 검증 처음 20개로 규칙 조정, 나머지 40개로 고정 규칙 평가 같은 디자인의 다른 색상·재판매 상품이 두 묶음에 걸치지 않게 한다. 60개는 작은 점검 표본이며 일반화 성능을 입증하지 않는다.
화면용 카탈로그 최대 80개, 상품당 최대 3장, 합계 최대 240개 이미지 참조 핵심 PI와 색상-사진 대응을 전수 검토한다. 실제 조건 조합을 가진 후보를 확보한다.
수집·라벨 자산 확장 누적 1,000개를 잠정 목표 파일럿의 품질·검토 비용을 보고 증감한다. 현재 검색기에 전량 바로 연결하는 목표는 아니다.

파일럿은 두 검토자가 독립적으로 라벨링하고 불일치를 조정하는 방식을 추천한다. 검증용 40개는 자동 결과를 보기 전에 정답을 작성한다. 희귀 태그의 표본이 없으면 해당 태그의 정확도를 보고하지 않는다.

제안 통과 기준: 핵심 PI는 항목별로 자동 부여한 값의 precision 95% 이상을 목표로 하고, 미확인을 포함한 coverage를 따로 보고한다. 표본 수·오류 수를 함께 제시한다. 이는 실측 성능이나 신뢰구간의 보장이 아니다. 화면용 상품은 색상-사진 오대응과 출처 없는 확정값이 검토에서 0건이어야 한다.

보고할 수치는 접근 성공/시도, 원문 확보/대상, confirmed·inferred·unknown·conflict/항목, 자동 부여 정답/자동 부여, 상품당 검토 시간이다. FEA는 태그별 근거 유형·검토 일치도·지원 표본 수를 먼저 보고한다. 빈 칸을 많이 채웠다는 이유만으로 품질이 높다고 판단하지 않는다.

수집량의 완료 조건은 단순 총수가 아니다. 예를 들어 Slacks의 Navy/Black × Wide/Slim 같은 실제 조합이 있어야 이미지 비교를 구성할 수 있다. 특정 축을 비교할 때 다른 속성 차이도 기록한다. 같은 디자인의 색상 차이는 비교 자원이 될 수 있지만 독립 디자인 수를 늘린 것으로 세지 않는다.

H

현재 코드에 무엇을 연결하고 무엇을 추가해야 할까

구분 현재 근거와 다음 작업
그대로 사용할 경로 CatalogRecord JSONL → catalog-import → catalog-map → ProductMap → 검색. 사용자 메모리 DB와 상품 카탈로그 DB는 분리돼 있다.
새로 필요한 전처리 판매자 자료/허용 페이지 adapter, 옵션·이미지 연결, OCR, 검토된 별칭 규칙, 중복 묶음, 라벨 검토·증거 기록, 로컬 이미지 준비. 현재 구현 완료로 보지 않는다.
Brand·Price 원문은 지금부터 수집한다. Brand 값 검증과 가격의 통화·경계·필터 기준은 별도 결정과 구현이 필요하다.
FEA 해석의 활용 현재 상품 inferred 값은 soft 점수에도 반영되지 않는다. 해석값을 순위에 쓰려면 확정값과 구별한 별도 점수·설명·검증 설계가 필요하다.
이미지 실행 현재 소비자 화면에는 로컬 이미지가 필요하다. 원격 URL을 저장하는 것만으로 다운로드·표시·이미지 추론이 끝나지 않는다. 실제 바이트·해시·영역을 준비한다.
데이터 규모 현재 current_versions()는 상품 ID·이미지 ID 각각 256개 제한이다. 검색은 스캔한 상품과 이미지 의존성을 모으므로 카드 몇 개만 보여줘도 대량 입력 문제가 남는다. 큰 카탈로그 연결 전 의존성 검증·조회 범위를 개선해야 한다.
갱신과 품절 import는 추가/갱신이며 파일에서 빠진 상품을 삭제하지 않는다. 현재 화면용 자료는 검토된 판매 가능 snapshot으로 만들고 실행 중 고정한다. 재고·가격 실시간 연동은 후속이다.

따라서 **지금 확정할 추천 범위는 “네이버 입점 여성 바지, 상품×색상 단위, 상세정보+실제 이미지, 검증된 PI 5축 우선, FEA는 근거 있는 일부만”**이다. 첫 파일럿 60개에서 확보량과 라벨 비용을 확인한 뒤 1,000개 수집 목표를 조정한다. 구매자 리뷰와 FEA 전수 확정은 첫 수집의 완료 조건으로 두지 않는다.

이번 제안은 중간보고서 3.4~3.7, 현 docs/master.md의 확정 사전/실행 계약, contracts.py, catalog_mapping.py, catalog_validation.py, product_search.py, catalog.py를 직접 확인한 결과에 근거한다. 공식 네이버 공지·커머스 문서·정책은 2026-10-30에 확인했다. 실제 상품 페이지 표본, 크롤링 성공률, 필드 완성률, 라벨 의미 품질, 모델/API 실행은 확인하지 않았다.
