# 문서 안내

세 저장소의 공통 문서 구조는 같은 경로와 역할을 사용한다. 먼저 필요한 문서 한 곳을 찾고, 관련 부분만 읽는다.

## 고정 구조

| 알고 싶은 것 | 위치 | 기록할 내용 |
|---|---|---|
| 무슨 프로젝트이고 어떻게 시작하나? | [README.md](../README.md) | 소개·실행·검증 진입점 |
| 작업할 때 무엇을 지키나? | [AGENTS.md](../AGENTS.md) | 작업 규칙·프로젝트별 제약 |
| 현재 무엇을 만들고 어디까지 됐나? | [project.md](project.md) | 목표·범위·현재 동작·남은 일 |
| 왜 이 방향을 선택했나? | [adr/](adr/README.md) | 중요한 결정의 이유·대안·영향 |
| 이번에 무엇을 해야 하나? | GitHub Issue 또는 현재 요청 | 문제·목표·완료 조건·제외 범위 |
| 이번에 무엇을 바꾸고 확인했나? | GitHub PR 또는 현재 대화의 결과 | 변경·실제 검증·남은 점 |

## 문서 작성 규칙

1. 파일명과 경로를 먼저 고른다. 같은 역할의 `master.md`, `prd.md`, `INDEX.md`, 루트 계획·요약 MD를 새로 만들지 않는다. 루트의 안내 파일은 대소문자까지 `README.md`, `AGENTS.md`로 고정한다.
2. 현재 설명은 기존 정본을 직접 고친다. Issue의 완료 조건, PR의 검증 결과, ADR의 결정 이유를 서로 복제하지 않고 링크한다. 현재 요청만으로 작업할 수 있으며 Issue·PR 게시를 선행 조건으로 만들지 않는다.
3. `project.md`는 현재 상태를 설명한다. 완료된 작업 일지·과거 계획을 누적하지 않는다. 구체적인 할 일과 진행 상황은 Issue, 변경 결과는 PR, 이전 파일 내용은 Git 이력에서 찾는다.
4. 상세 설명이 실제로 필요할 때만 아래 고정 이름을 사용한다. 빈 파일·폴더는 미리 만들지 않는다. 새 문서에는 한 가지 역할만 주고 이 안내에서 연결한다.
5. 상세 문서가 생기면 해당 내용은 그곳으로 옮기고 `project.md`에는 요약과 링크를 남긴다. 여러 문서를 같은 내용의 정본으로 선언하지 않는다.
6. 새 문서 종류·폴더·명명 규칙은 사용자의 구조 변경 요청과 ADR 없이 늘리지 않는다. 공통 구조 변경은 세 레포의 규칙·검사도 함께 맞춘다.
7. 대체된 문서·중복 사본은 참조와 현재 내용의 Git 복구 가능성을 확인한 뒤 삭제한다. 미커밋·미추적·유일 원본과 연구·재현·라이선스 근거는 임의로 삭제하지 않는다. `archive/`, `backup/`, 날짜별 사본을 새 보관처로 늘리지 않는다.

## 필요할 때만 쓰는 이름

| 경로 | 역할 |
|---|---|
| `docs/architecture.md` | 구현 구조·API·저장 계약 |
| `docs/evaluation.md` | 연구 평가의 설계·수행·판정 기준 |
| `docs/workflow.md` | Issue→PR 절차·자동화·인계 계약이 길어질 때의 상세 안내 |
| `docs/specs/<short-name>.md` | 독립적으로 참조할 상세 계약. 소문자 영문·숫자·하이픈 파일명 |
| `docs/sources/` | 실제로 참조하는 원문·출처·라이선스 자료. 원본 파일명 유지 |

코드, 논문, 실험 결과와 원자료는 각 프로젝트의 기존 폴더를 따른다. 모듈별 사용·재현 안내는 해당 폴더의 `README.md`에 둘 수 있다. 생성 보고서·고정 프로토콜·출처 원문을 공통 문서 이름에 맞추려고 재작성하지 않는다.

## 구조 확인

`python3 scripts/check_context.py`는 고정 파일·허용 경로·ADR 번호와 파일명·템플릿 존재를 검사한다. 기존 공통 검사와 CI에서도 실행한다. 링크·내용 정확성·실제 연구 결과는 각 레포의 별도 검증 범위다.
