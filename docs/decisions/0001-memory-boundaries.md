# 0001 · 요청 범위·사용자 동의와 삭제 경계

- Status: Accepted
- Date: 2026-10-13
- Related Issue: [#1](https://github.com/jongrionro-debug/HCI_HANDSOME/issues/1)
- Approval: 2026-10-13 · 현재 채팅의 승인 질문(D01–D12·ADR 0001/0002·보관 기간·Python+SQLite 최소안)에 사용자가 **“권고안 전체 승인”**으로 응답했다.

## Context

[연구 기준](../master.md)의 RQ1은 기본·일시 선호의 분리와 사용자 확인·수정을 다룬다. 기존 [제품 흐름](../workflow.md)과 보관 초안은 자동 장기 덮어쓰기를 막지만 요청 종료·재개, 동의 대상, 실제 삭제·파생 데이터와 보관 기간은 정하지 않았다. 이번 요청에만 쓰는 정보와 오래 보관되는 정보를 같은 의미로 취급하면 다음 요청 오염과 UI의 잘못된 보관 약속이 생긴다.

## Decision

승인된 결정은 [메모리 설계](../memory-design.md)의 D01–D05·D10이다.

- 독립적으로 수정 가능한 문장과 최소 claim/조건/기간을 저장한다. 취향과 반복 상황은 항목별 명시 동의가 있으면 장기가 될 수 있다.
- 현재 요청 단기와 이후 활용 장기, 내용 확인과 활용 동의를 분리한다. 명시된 현재 발화는 확인 근거가 될 수 있으나 반복·“평소”·인용은 동의가 아니다.
- 신규 요청은 새 ID. 같은 요청 재개는 사용자 확정과 날짜/조건 재확인, 복제는 선택된 내용을 새 입력으로 확인한다.
- 장기 선택은 기본 미체크. 직접 장기 생성과 단기 승격 모두 허용하며 같은 확인·동의 검증을 적용한다.
- 의미 수정은 새 ID와 새 확인·동의. 같은 promote 가족은 추천에서 한 번만 사용하고 철회·삭제 때 함께 처리한다.
- 기본 저장 안 함, 이번 요청 제외, 활용 철회, 기록 삭제를 서로 다른 조작으로 제공한다. 과거 원문·요약을 통해 철회/삭제한 정보를 자동 재생성하지 않는다.
- 보관 제안: 요청은 마지막 사용자 활동+30일과 생성+90일 중 이른 시한, 활성 장기는 명시 동의+365일, 교체/철회 내용은 최대 30일. 원문 없는 경계 메타데이터는 최대 90일, 내용 없는 삭제 완료 영수증은 24시간이다.
- 원문 전체를 장기 감사 근거로 복제하지 않는다. 독립된 항목별 확인/동의 snapshot을 최소 보관한다. 삭제 closure는 기억·사본·원문 해당 부분·snapshot·추천 참조·요약·캐시까지 포함한다.

이 문서의 정책·기간은 위 사용자 회신으로 승인됐다. 구현 여부와 사용자 연구 효과를 주장하지 않는다.

## Alternatives

| 대안 | 검토 결과 |
|---|---|
| 반복·최근성으로 자동 장기화 | 사용자가 이번 요청만의 요구를 평소 선호로 남기지 않으려는 기준과 충돌한다. |
| 모든 정보를 추가 클릭으로 확인 | 명시된 직접 발화까지 되묻는 부담이 크다. 내용은 발화로 확인 가능하게 하고 이후 활용 선택은 별도로 검증한다. |
| 취향만 장기화, 상황은 전부 일회성 | 고객 미팅 등 사용자가 다시 활용하길 원하는 반복 상황을 표현하지 못한다. 반복 상황도 명시 조건과 동의로 허용한다. |
| 같은 ID를 수정하고 기존 동의를 재사용 | 의미·조건·기간 변경이 과거 동의를 벗어날 수 있고 전후 설명을 잃는다. |
| 전체 원문·이벤트를 무기한 보존 | 삭제·최소 보관 요구와 충돌한다. 독립 snapshot과 내용 없는 이벤트를 선택한다. |
| 요청 접속 종료 즉시 삭제 | 같은 요청 재개 사례를 지원하지 못한다. 적용 종료와 제한된 보관 기간을 분리한다. |

## Trade-offs

미체크 선택·모호한 범위 확인·만료 시 재동의는 상호작용 비용이다. 대신 사용자가 내용과 이후 활용 범위를 직접 조절할 수 있다. 장기 상황 조건과 최소 snapshot은 취향만 저장하는 구조보다 복잡하다. 삭제가 원문과 여러 항목에 걸칠 수 있으므로 영향 범위를 먼저 보여줘야 한다.

30/90/365일은 제한된 로컬 프로토타입의 승인된 초기값이며 법적 요구·연구로 입증된 최적값·운영 완료로 다루지 않는다. 이후 운영 범위를 바꾸면 승인된 ADR 본문을 고치는 대신 새 결정과 마이그레이션을 남긴다. 이번 Issue에서 실제 연구 수집·외부 서비스·OS 백업의 보관을 승인하지 않는다.

## Consequences

Request·MemoryItem·UserEvidence·삭제 closure가 필요하다. 원문 삭제 이후의 redacted 참조와 독립 장기 snapshot을 분리한다. 신규·재개·복제·선택 저장·수정·철회·삭제 및 과거 재유입을 가상 사례로 검증하고, 후속 구현에서는 실제 저장소·파일 삭제와 UI 결과를 통합 검증한다. 구현 순서는 [계획](../memory-implementation-plan.md)을 따른다.

Issue #1의 설계 범위는 승인 완료다. 실제 제품 구현·원격 Issue 종료·병합은 별도 작업이다.
