# LUMI 설계와 구현 상태

기준: **2026-10-14 사용자 지정 [LUMI 시스템 설계 보고서](../LUMI_system_design.html)**. 보고서가 시스템 설계 정본이며 이 문서는 현재 구현과의 대응을 관리한다. 과거 Figma 화면·흐름 등 LUMI 이전 자료는 [archive](../archive/README.md)에 보관한다.

## 1. 설계의 핵심 경계

보고서는 **현재 요청 + Memory Layer → LLM 선호 해석 → User Preference Map → Candidate Look 설계 → 실제 상품 기반 추천 → 이미지 선택·피드백 → 세션 재추천**을 정의한다. 사용자가 확정·중단하고, 장기 저장은 이후의 별도 선택이다.

| 표현 | 담는 내용 | 현재 구현과의 관계 |
|---|---|---|
| User Preference Map | 사용자 선호의 확정·추론·Unknown 상태 | 현재 17개 아이템 목표 속성과 context가 일부 기반을 제공. 전체 세션/Outfit 선호 상태는 미구현 |
| Candidate Look | 선호·명시 제약을 반영한 후보 코디 방향 | 미구현. 후보 설계값은 사용자의 확정 선호가 아님 |
| Product Feature Map | VLM/메타데이터로 얻는 실제 상품 속성 | 미구현. 현재 목표값·registry의 허용값은 실제 상품 관측값이 아님 |

모든 속성을 사용자 취향으로 채우지 않는다. Unknown을 허용하고 후보에 필요한 값은 코디 설계와 상품 검색에서 구체화한다. **룩 선택은 긍정적 근거이며 특정 속성 선호의 확정이 아니다. 미선택은 싫어함으로 기록하지 않는다.** 전체 룩은 Outfit-level, 부분 선택은 Item-level 근거로 분리한다.

## 2. 보고서 단계별 구현 대응

아래 ‘현재’는 코드에 존재하는 범위다. 보고서의 설계 채택과 코드 구현 여부를 구분한다.

| 보고서 절 | 설계 동작 | 현재 | 남은 범위 |
|---|---|---|---|
| 1 · 전체 Architecture | 입력·기억·선호·후보·실제 상품을 분리 | 메모리 저장, 대상별 context, 아이템 목표 추론·검증 | 세 상태의 통합 계약, 상품 데이터·후보 연결 |
| 2 · 초기 선호/후보 | 명시 조건·장기기억·맥락 추론·가설, 초기 LOOK 5개와 2:1:2 기본 전략 | 직접 조건 보존, 현재 단기 예외·장기 기본 결합, inferred/Unknown 출력 | 5개 코디 방향 생성·다양성·명시 제약에 따른 구성 조정 |
| 3 · Image-first | 0~5개 복수 선택, 상의·하의 등 부분 선택 | 미구현 | 이미지 제시·선택 이벤트·Item/Outfit 근거 |
| 4 · Adaptive Feedback | 가설 분석, 질문 생략·원탭 확인, 조건부 이미지 비교 | 개발자 도구의 텍스트 후보 추출·수동 확인 | 선택 이유 분석·다음 행동 결정·질문/비교 정책 |
| 5 · Update/종료 | Confirmed/Hypothesis 세션 갱신, 사용자 종료·Agent 종료 제안, 별도 장기 동의 | 확인·동의·요청 종료의 저장 기반 | 이미지 피드백 갱신·재추천·사용자 종료 UI·종료 제안 |
| 6 · Agent 역할 | Interpreter·Decision·Policy·Recommendation·Memory의 논리적 책임 | 텍스트 해석 adapter, 값/근거 검증, Memory Layer 일부 | Decision Agent·Recommendation Engine과 통합 루프 |
| 7 · 최종 파이프라인 | Minimal 기본을 보존하며 이번 Street 방향 탐색 | 단기 예외 이후 새 요청에서 장기 기본 복원하는 CLI/테스트 | 실제 LOOK·상품으로 이어지는 시나리오 |

[실행 계약](shopping-memory-prototype.md)과 [개발자 관찰 도구](developer-memory-inspector.md)가 현재 동작의 근거다. 관찰 도구의 세 패널은 개발용이며 소비자 추천 화면이 아니다. 기존 `stylemate_memory` 패키지·CLI·스키마 식별자는 유지한다.

## 3. 후속 구현에서 지킬 정책

1. 우선순위는 **현재 요청의 명시적 제약 > 이번 세션의 확인된 선호 > 관련 장기기억 > LLM 가설**이다. 2:1:2는 초기 기본 전략이며 현재 요청과 충돌하면 조정한다.
2. 이유 분석이 충분하면 질문 없이 Hypothesis로 재추천할 수 있다. 모델 가설을 확정된 사용자 취향으로 올리지 않는다.
3. 확인이 유용할 때만 구체적인 이유를 원탭으로 제안한다. ‘잘 모르겠어요’·‘그냥 느낌이 좋아요’에는 이유 질문을 멈추고 선택 LOOK의 긍정 근거를 유지한다.
4. 이미지 비교는 말로 설명하기 어렵고, 해당 속성 구분이 추천에 중요하며, 비교 가능한 후보가 있을 때만 2~3개로 제공한다.
5. 장기기억과 다른 선택은 이번 세션 적용을 확인하고 장기기억을 보존한다. 반복 선택·세션 종료만으로 장기를 바꾸지 않는다.
6. 사용자는 언제든 코디 확정·종료를 선택한다. Agent는 긍정 반응·필수 제약 충족·개선 여지 감소에 따라 종료를 제안하고, 반복 불만족·피로에는 방향 전환·조건 수정·종료를 제공한다.
7. 종료 뒤 장기 저장은 선택이다. 저장할 구체적 선호를 보여주고 향후 활용 동의를 별도로 확인한다.

이 목록은 보고서의 설계 정책이며 전체가 현재 코드로 구현된 것은 아니다. 특히 현재 저장소의 **미확인 메모리 후보는 유효 목표 context에서 제외**된다. 목표 추론의 `inferred` 출력과 보고서의 세션 Hypothesis를 활용한 재추천을 같은 기능으로 취급하지 않는다. 세션기억은 현재 요청의 `short_term` 범위에 대응하며 새 저장 scope를 추가하지 않았다. 후속 구현에서는 가설을 탐색 신호로 쓰는 표현·경계를 구체화하고, 확정 조건·장기기억과 구분해야 한다.

기존 초기 소비자 UI 방향은 질문·이미지 선택·추천·수정에 집중하고 전체 Feature Map·메모리 상태를 기본 노출하지 않는 것이다. 내부 근거·범위 검증은 유지한다. 실제 화면은 미구현이다.

## 4. 아직 정하지 않은 구현 세부사항

보고서의 ‘팀 내 합의·검증 포인트’와 마지막 페이지는 5개/2:1:2, 가설 확인·Fallback, Hybrid 종료를 **제안·실험 필요**로 표시한다. 정본 지정은 검증 결과나 세부 실행 계약의 완성을 뜻하지 않는다.

- 장기기억이 비어 있을 때의 초기 후보 구성과 다양성 기준.
- User Preference Map·Candidate Look·Product Feature Map의 필드/버전/근거 연결, Item/Outfit 상태 및 세션 가설 표현.
- 질문 예산의 구체 값, 확인·이미지 비교의 선택 기준, 개선 여지·피로·종료 제안의 판정 기준.
- 상품 데이터·VLM·검색 방식, 전체 제품 UI·인증·서비스 스택, 실패/재시도 동작.

각 컴포넌트는 논리적 역할이다. 별도 LLM이나 서버로 나누는 결정은 하지 않았다. 제품 스택·저장 정책·공개 API 계약을 바꾸는 작업은 [개발 절차](engineering-workflow.md)에 따라 제안·승인한다. 연구 RQ·비교 조건·평가 지표는 [연구 기준](master.md)에서 별도로 정한다.

## 5. 검증의 구분

현재 오프라인 테스트는 SQLite·확인/동의·대상/조건별 context·목표값/근거·가상 adapter 연결을 검사한다. LOOK 선택·상품 속성·코디 품질·적응형 질문/종료·사용자 만족 효과는 검증하지 않는다. 문서 링크 검사와 HTML 원문 일치는 이 동작을 대신 검증하지 않는다.

```sh
python3 scripts/check_repository.py
git diff --check
PYTHONPATH=src python3 -m unittest discover -s tests -q
PYTHONPATH=src python3 -m stylemate_memory.cli demo --synthetic
```
