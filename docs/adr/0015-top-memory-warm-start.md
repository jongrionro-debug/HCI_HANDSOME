# 0015 · 상의 첫 빌드: 동의한 기억으로 시작하고 종료 요약에서 다시 동의받는다

- Status: Proposed
- Date: 2026-11-20
- Related Work: 현재 대화의 LUMI 상의 첫 빌드 요청, 설계 화이트보드("LUMI 상의 에이전트"), [ADR 0013](0013-langgraph-intent-loop.md), [ADR 0014](0014-crawled-catalog-pi-v2.md)
- Approval: 2026-11-20 사용자 결정
  - 목표: 쓸수록 메모리가 쌓여 같은 상황이든 다른 상황이든 더 적은 수고로 맞는 상의를 받고(RQ1), 이미지 인터랙션으로 원하는 아이템을 찾는다(RQ2)
  - 흐름은 코드 규칙(LangGraph), LLM은 해석과 설명 한 줄만 맡는다. 장기 기억은 종료 시 항목별 동의를 유지한다
  - 첫 빌드 범위 6가지(이 문서 결정 1~6), 뺀 것(하의·이미지 온보딩·평가 도구)
  - 기록 방식: 0013 보완 대신 새 ADR 0015
  - 이 ADR의 Accepted 승인은 미승인
- Supersedes: [ADR 0013](0013-langgraph-intent-loop.md) 결정 8의 "점수는 이번 요청에만 쓴다"(부분: 수렴한 값을 종료 요약의 동의 후보로 올린다), 결정 11의 "`기타`는 매칭에 쓰지 않는다"(부분: 사용자가 직접 적은 "나의 상황"은 원문으로 저장하고 LLM이 비슷한 과거 상황에 연결한다). 다른 결정은 유지

## 맥락

graph 엔진은 요청마다 빈 의도 상태로 시작하고 동의한 장기 기억을 읽지 않는다. Beta 점수는 요청 안에서만 쓰여 종료 요약의 동의 후보가 되지 않는다. 상황은 닫힌 사전이고 사전 밖 값은 매칭되지 않는다. 그래서 같은 사용자가 요청을 반복해도 첫 그리드가 나아지지 않아 RQ1(반복 사용 효과)을 볼 수 없다. 검증은 한 세션 안에서 상황을 바꿔 가며 요청 3~4회로 한다. 진행 방식은 먼저 만들고, 직접 써 보고, 고치는 것이다.

## 결정

1. 범위: 상의(`Top`)만 다룬다. 요청 시작 때 성별(남성·여성·전체)을 고르고 카탈로그 원본의 `gender`로 걸러 낸다(Shopify 남성복, 29CM 남녀 혼재). 성별 값이 없는 상품은 "전체"에서만 보인다. 하의·이미지 온보딩·평가 도구는 이번 범위에서 뺀다.
2. 상황 칩: 시작 화면에 [출근·데이트·주말·나의 상황]을 둔다. 앞의 셋은 사전 값(출근·데이트·주말 외출)으로 바로 넣는다. "나의 상황"은 자유 텍스트이며 원문을 그대로 상황으로 둔다(값 `기타`, 원문 보존). 다음 요청에서 자유 상황이 들어오면, 과거에 동의해 저장한 자유 상황 원문 목록을 LLM에 주고 비슷한 것을 고르게 한다(없으면 없음). 코드는 목록 안의 원문만 받는다. 연결은 화면에 "비슷한 상황: ○○"로 보이고 x로 끌 수 있다. 연결된 과거 상황의 상황별 기억만 이번 요청에 쓴다.
3. 그리드: [ADR 0013](0013-langgraph-intent-loop.md) 결정 8의 8장 그리드(수렴·탐색·대조)를 유지하고 결정 5의 새로움 칸을 더한다.
4. warm start: 요청 시작 시 동의한 장기 기억(평소 취향 + 품목·상황이 맞는 상황별 선호)의 PI 연결값을 Beta 사전값(soft, hard 아님)으로 넣는다. 사전값은 학습 점수와 따로 두어 끄거나 약하게 할 수 있다. 같은 축에 상황별 기억이 있으면 상황이 우선하고, 평소 취향은 상황과 부딪치지 않는 축(예: 색·톤)에만 적용한다. 이번 요청에서 직접 말한 축에도 평소 취향을 적용하지 않는다. 적용한 기억은 "이렇게 시작할게요" 아래 짧은 한국어 문장 칩 최대 3개(상황별 먼저)로 보이고, x로 끄면 그 기억의 사전값을 이번 요청에서 뺀다. 사전값은 이해 칩을 만들지 않는다(칩은 이번 요청의 반응으로만 생긴다).
5. 새로움 칸: 기억을 적용한 그리드에서 1~2장은 기억 사전값 없이 고르고, 기억이 선호하는 값이 없는 상품을 우선한다. 새로움 칸을 두 턴 이상 고르거나 "평소랑 다르게" 같은 글이 있으면 "이번엔 새로운 스타일로 볼까요?"를 한 번만 묻는다. 예라고 하면 기억 칩을 흐리게 하고 사전값 세기를 줄인다. 기억 칩 영역의 "이번엔 다르게" 버튼은 묻지 않고 같은 일을 한다. 기억의 선호값이 대조 노출에서 두 턴 이상 반대로 갱신되면 "취향이 바뀌었나요?"를 한 번 묻고, 예면 그 기억을 이번 요청에서 끈다. 기억 자체는 바꾸지 않는다.
6. 종료 요약과 동의: 사용자가 "마치기"를 누르면 요청을 닫기 전에 제안 문장 최대 3개를 코드가 만든다. 재료는 말한 선호(직접 말한 PI), 이유 있는 거절(직접 말한 비선호), 이미지로 수렴한 값(이해 칩 기준), 최종 상품이다. 각 문장은 [평소에도][이 상황만][저장 안 함]이고 기본은 선택 안 함이다. 저장할 때 고른 문장만 기존 저장 계약으로 넘긴다: 보여 준 문장 그대로의 내용 확인(`confirm_content`)으로 단기 기억을 만들고, 요청을 닫은 뒤 같은 문장의 이후 활용 동의(`future_reuse`)로 장기 기억에 올린다. 한 번의 버튼 선택이 그 문장의 확인과 동의를 함께 뜻하며, 화면은 이를 "다음 요청에도 이 문장을 씁니다"로 보인다. 근거는 이번 요청의 원문·이미지 선택 근거를 그대로 연결한다. 저장 후 LLM이 동의한 장기 기억 전체를 짧은 취향 프로필(평소 3줄 + 상황별 1~2줄)로 다시 쓴다. 문장이 바뀐 것만 [바꾸기][그대로]로 다시 동의받고, 바꾸면 기존 `replace`로 새 장기 기억을 만들고 원래 기억은 `superseded`로 근거와 함께 보존한다.
7. 저장 계약(`store_v1.apply_batch`, 확인·동의 분리, 확인·동의 표시 이벤트)은 바꾸지 않는다. 요약 제안·프로필 초안은 graph 체크포인트 DB의 요청별 행에 두고 요청 삭제 때 함께 지운다.
8. 수치(사전값 세기 2.0, 흐림 배수 0.3, 새로움 칸 2장→흐림 때 1장, 반대 갱신 2턴, 새로움 선택 2턴)는 써 보고 정할 초기 가정이다.

## 대안

- 0013 본문 보완: 이미 승인된 결정 8·11의 문구를 고쳐야 한다. 사용자가 새 ADR을 골랐다.
- 기억을 hard 조건으로 시작: 같은 상황이라도 이번 요청의 반응이 기억을 뒤집을 수 없다.
- 기억을 그리드 순위 가산점(soft 조건)으로만 반영: 이번 요청의 선택과 같은 척도로 섞이지 않아 반대 선택이 쌓여도 영향이 줄지 않는다. Beta 사전값은 관측이 쌓이면 자연히 약해진다.
- 자유 상황을 코드 문자열 일치로 연결: 같은 뜻의 다른 표현이 매칭되지 않는다. 사전 확장만으로는 사용자 고유 상황을 담지 못한다.
- 종료 요약 없이 수렴 값을 자동 저장: [ADR 0007](0007-joint-feedback-and-end-consent.md)의 종료 후 항목별 동의와 충돌한다.
- 확인과 동의를 따로 두 번 묻기: 저장 계약은 두 이벤트를 요구하지만, 시스템이 만든 한 문장에 두 번 답하게 하면 종료 부담이 커진다. 같은 문장·같은 버튼에서 두 이벤트를 기록한다.

## 영향

- 이점: 두 번째 요청부터 첫 그리드에 동의한 취향이 반영된다. 상황이 달라도 평소 취향(색·톤 등)은 이어진다. 기억 적용이 문장 칩·새로움 칸·"이번엔 다르게"로 보이고 통제된다.
- 비용·위험: 기억 사전값이 탐색을 좁혀 새 취향을 늦게 발견할 수 있다(새로움 칸·흐림으로 완화). 자유 상황 연결은 LLM 판단이라 틀릴 수 있다(화면에 보이고 끌 수 있음). 확인과 동의를 한 버튼에서 받는 것은 [ADR 0007](0007-joint-feedback-and-end-consent.md)의 "확인·동의 구분"을 화면에서 한 단계로 줄인다. 영어 값 라벨이 문장에 그대로 나온다(미정).
- 후속 작업: 직접 써 본 뒤 결정 8의 수치, 새로움 칸 비율, 프로필 말투, 값 라벨의 한국어 표시를 정한다. 프로필 재작성의 병합(여러 기억 → 한 문장)은 이번 범위에서 1:1 재작성으로 제한한다.
- 검증: graph 순수 로직 테스트와 각본 모델 통합 테스트(warm start, 새로움 칸, 종료 동의, 자유 상황 연결). 실제 DeepSeek 품질은 사용자가 직접 실행해 확인한다.
