# 0006 · FEA→PI 가설을 이미지 비교로 구체화

- 후속 결정: [ADR 0010](0010-derive-pi-values-from-collected-products.md)이 PI value의 확정 근거를 수집 데이터로 변경한다. 이 ADR의 직접 PI·FEA→PI 가설·상품 비교 역할과 확인 경계는 유지한다.
- Status: Accepted
- Date: 2026-11-01
- Related Work: 현재 대화의 사용자 목표 Feature Map·상품 Map 역할과 이미지 비교 흐름 재정의
- Approval: 2026-11-01 (Asia/Seoul), 사용자가 직접 표현한 PI는 반영하고 FEA→PI 연결을 가설로 두어 해당 PI 값의 포함/비포함 이미지로 확인하는 설명에 “그게 맞아. 이제 그런 방향으로 반영해줘.”라고 승인함. 범위 질문에는 “실행 코드·UI까지 함께 변경”으로 답함
- Applies to: 사용자 목표 Map의 PI·FEA 역할, 상품 Map의 PI 비교 범위, 가설 생성·이미지 비교·피드백의 로컬 실행 구현. 기존 데이터·범용 v1 호출은 호환 경로로 보존하며 실제 모델·상품·사용자 효과와 구분

## Context

변경 전 구현은 사용자 목표와 상품 관찰 양쪽에 PI·FEA를 표현하고, 미정 속성의 차이를 비교 후보로 제시했다. 사용자는 상품 Map에는 PI를 두고, 사용자 목표 Map에는 원하는 상품의 PI와 그 이유·맥락을 나타내는 FEA를 함께 두는 방향을 제안했다. 이후 대화의 중심은 첫 입력과 관련 장단기 기억에서 만든 FEA→PI 해석을 이미지로 확인하는 과정이다.

보고서 3.4–3.6의 직접 조건 우선, 추론 구분, 선택 이유 확인과 장기 활용 동의는 유지한다. 상품 PI 중심 비교와 FEA→PI 가설 연결은 이번 후속 승인으로 구체화한 선택이며, 원문 보고서나 Park et al.의 실험 결과로 소급하지 않는다.

## Decision

1. **두 입력 경로:** 현재 입력과 유효한 장단기 기억에서 직접 표현된 PI는 원래 근거·대상·조건·강도와 함께 목표 PI에 반영한다. 추상적 요구는 FEA로 정리한다. 직접 PI를 FEA로 압축했다가 다시 복원하지 않는다. 직접 요구도 기존 확인 경계를 유지한다.
2. **연결 자체를 가설로 관리:** LLM은 FEA 요구를 구현할 수 있는 PI 값과 대안을 제안한다. 예를 들어 “편하게 입고 싶다”에서 `Fit=Wide`를 제안할 수 있지만, 편안함과 와이드핏의 연결은 해당 사용자·요청·상황에 대한 미확인 가설이다. 사전 밖 값이나 근거 없는 확정 PI를 만들지 않으며 직접 PI를 덮어쓰거나 가설을 hard 조건으로 승격하지 않는다.
3. **Map 역할 분리:** 사용자 목표 Map에는 직접/확인 PI, FEA 요구, FEA→PI 가설을 연결한다. 상품 Map의 비교 대상은 출처·확인 상태가 있는 PI다. 상품별 FEA 30태그를 채우는 것은 이 후속 설계의 전제가 아니다. 검색은 사용자 목표 PI와 상품 PI를 비교한다.
4. **가설 중심 비교:** 초기 채팅 이후에는 중요한 미확인 FEA→PI 연결을 우선 확인한다. 해당 PI 값이 있는 실제 상품과 그 값이 없는 것으로 확인된 대안 상품을 비교하며, 다른 직접 조건을 유지하고 배경·다른 속성의 차이를 가능한 한 줄인다. 미확인 PI를 비포함 사례로 쓰지 않는다. 후보 수나 모든 가설의 확인을 고정 절차로 강제하지 않는다.
5. **응답과 가설의 연결:** 비교 목적·대상·차이가 명확한 응답은 그 가설을 확인하거나 수정·기각하는 근거가 될 수 있다. 같은 응답의 의미가 분명하면 별도의 동일 질문을 반복할 필요가 없다. 여러 차이가 섞였거나 이유가 불명확하면 지지 신호와 확정을 구분하고 필요한 경우에만 질문한다. 반대 후보 선택은 모든 속성 비선호가 아니며, 없음·모르겠음·건너뛰기는 가설 확인이 아니다.
6. **수정·재탐색·종료:** 반응에 따라 목표 PI와 연결 가설을 갱신하고 다음 비교 또는 추천으로 진행한다. 추론에서 시작한 연결은 확인돼도 출처를 보존한다. 새 발화로 직접 PI를 수정할 수 있고, 모든 값을 채우기 전에 종료할 수 있다. 이번 확인은 장기 활용 동의와 별개다.
7. **성능 판단 경계:** 이미지 응답은 원하는 PI 해석을 확인하는 근거다. `Fit=Wide`를 골랐다고 실제 착용 편안함을 검증한 것은 아니다. 현재 PI 7항목으로 확인할 수 없는 필수 기능 요구는 원문·FEA와 함께 미해결로 남기고, 추가 상품 근거 확인이나 사용자 조정 없이 충족 처리하지 않는다.

## Alternatives

| 대안 | 판단 |
|---|---|
| 모든 입력·기억을 FEA로 만든 뒤 PI 생성 | 직접 색·핏·가격 등의 구체 조건을 잃을 수 있어 채택하지 않음 |
| 사용자·상품 양쪽에 FEA를 라벨링해 직접 비교 | 기존 실행 계약으로 보존. 이번 후속 설계는 상품 PI 비교와 사용자의 해석 확인을 중심으로 변경 |
| LLM이 FEA에서 PI를 확정한 뒤 검색 | 여러 PI 조합이 같은 요구를 구현할 수 있어 사용자 비교 없이 확정하지 않음 |
| 직접 PI 반영 + FEA→PI 가설 + 이미지 비교 | 사용자 승인 방향으로 채택 |

## Trade-offs

상품 PI를 중심으로 자료를 준비하고, 사용자가 추상적인 요구를 이미지로 구체화할 수 있다. 대신 FEA→PI가 일대일 변환은 아니므로 연결과 대안·사용자 반응을 추적해야 한다. 실제 상품에서는 비교 축 외의 차이를 완전히 통제하기 어렵고, 이미지로 성능을 검증할 수 없다. 추천 품질·표현 부담·턴 수의 개선은 아직 검증하지 않았다.

## Consequences

현재 설계는 [master의 가설 흐름](../project.md#직접-pi와-feapi-가설)과 [이미지·텍스트 인터랙션](../project.md#이미지텍스트-인터랙션)에 반영한다. 승인된 기존 ADR 본문·보고서·사전의 값과 출처·기존 실행 데이터는 보존한다.

`hypotheses.py`와 소비자 서비스는 FEA 근거→PI 대안→비교 회차·상품/이미지 버전→응답을 연결한다. 미확인 가설은 확정 PI 제약과 분리하고, `consumer_comparisons`는 기존 CandidateSet에 FK로 연결한다. 응답은 서버가 미리 발행한 의미·binding snapshot을 사용하며 내부 `record_comparison` 한 batch로 선택 근거와 확인된 단기 해석을 저장한다. 소비자 상품 Map 생성·검색은 PI만 사용하고 기존 범용 PI·FEA 함수와 저장 자료는 자동 변환하지 않는다. 구체 필드·명령·제약은 [현재 실행 확장](../project.md#가설-비교-실행-확장)을 따른다.

검증은 직접 PI 보존, 가설 PI의 비확정·비필수 상태, 실제 포함/비포함 상품의 근거, 명확한 응답의 연결 확인, 모호한 선택·없음·모르겠음의 미확인 유지, 수정·삭제 후 오래된 비교 차단을 포함한다. 기존 단위·통합·브라우저 검증을 확장하되 합성 통과와 실제 모델·상품·사용자 효과를 구분한다.
