# 0017 · 질문 설계를 저장소 안 작업 공간과 파트별 브랜치로 진행한다

- Status: Proposed
- Date: 2026-11-25
- Related Work: 현재 요청(질문 설계 3갈래 분업의 Git 협업 구성)
- Approval: Git 브랜치·push로 협업한다는 방향은 2026-11-25 팀 판단(사용자 전달). 폴더 구조와 규칙은 미승인
- Supersedes: 없음

## 맥락

대화형 에이전트 전환([agent-pipeline.md](../specs/agent-pipeline.md))에서 질문 설계를 세 갈래로 나눴다. ① 질문 방식, ② 어떤 상황·의도에서 어떤 방식을 고를지, ③ 답을 어떻게 해석·반영할지다. 세 결정은 같은 근거를 이어 써야 하고, 근거 없이 정한 항목은 연구 한계로 드러나야 한다.

팀은 노션 대신 각자 브랜치에서 작업하고 push로 공유하기로 했다. 그런데 현재 문서 구조([문서 안내](../README.md))에는 근거 정리와 단계별 초안을 둘 자리가 없다. `docs/` 아래는 고정 이름만 허용되고, `docs/specs/`는 하위 폴더 없이 확정 계약만 둔다. 세 사람이 한 파일을 함께 고치면 충돌도 잦다.

## 결정

1. 질문 설계 작업은 `research/question-design/`에서 한다. 안내는 그 폴더의 [README.md](../../research/question-design/README.md)에 둔다.
2. 근거는 카드 1장을 파일 1개(`evidence/<카드 ID>.md`)로 둔다. 카드 ID는 `<첫 저자 성><연도>-<주장 요약>`이라 번호를 조율할 필요가 없다.
3. 파트 결과는 `1-modes.md`, `2-mapping.md`, `3-feedback.md`에 두고 각 파일은 주인만 고친다. 다른 사람은 PR 리뷰로 제안한다.
4. 작업은 `qd/<파트>-<이름>` 브랜치에서 하고, 첫 push 때 Draft PR을 연다. 리뷰어는 다른 파트 1명 이상이며, 머지 조건은 리뷰 승인과 `repository-checks` 통과다.
5. 확인 지점 A·B·C마다 세 사람의 PR을 main에 머지한다. B에서 질문 방식·선택 규칙을, C에서 반영 규칙을 별도 ADR로 남기고 [agent-pipeline.md](../specs/agent-pipeline.md)를 갱신한다. 이 폴더는 근거와 초안의 자리이고, 확정된 결정의 정본은 ADR과 specs다.
6. 근거를 못 찾은 항목은 표에 `가정`으로 표시해 연구 한계와 user study 검증 목록으로 쓴다.

## 대안

- 노션 DB: relation으로 근거 연결이 잘 보이지만 팀의 작업 방식(브랜치·push)과 따로 놀고, 결정과 근거가 저장소 밖에 남는다.
- `docs/specs/question-design.md` 한 파일: 기존 구조를 바꾸지 않지만 세 사람이 같은 파일을 고쳐 충돌이 잦고, 근거 카드를 둘 곳이 없다.
- Issue 댓글로 근거 공유: 검색과 재사용이 어렵고 파트 사이 참조가 끊긴다.

## 영향

- 이점: 각자 브랜치에서 충돌 없이 작업하고, PR 리뷰가 근거 카드의 검토 단계가 된다. 확정 전 초안과 확정된 결정(ADR·specs)이 분리된다.
- 비용·위험: 최상위 폴더 `research/`가 새로 생긴다. 아직 main에 없는 카드를 링크로 쓰면 CI 링크 검사가 실패하므로 백틱 ID로 참조해야 한다. 확인 지점에서 머지가 몰리면 리뷰 부담이 커진다.
- 후속 작업: 킥오프에서 담당자·확인 지점 날짜·채택 기준을 정한다. B·C에서 결정 ADR을 쓰면 이 폴더의 해당 파일에는 확정 버전과 ADR 링크만 남긴다.
- 검증: `python3 scripts/check_context.py`, `python3 scripts/check_repository.py`.
