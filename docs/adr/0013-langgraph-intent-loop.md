# 0013 · LangGraph 기반 의도 순환 추천으로 흐름 제어를 재구성한다

- Status: Proposed
- Date: 2026-11-18
- Related Work: 현재 대화의 파이프라인 재설계 요청, 재설계 메모(LUMI 파이프라인 재설계 메모), Issue [#7](https://github.com/jongrionro-debug/HCI_HANDSOME/issues/7)·[#1](https://github.com/jongrionro-debug/HCI_HANDSOME/issues/1)
- Approval: 설계 결정 Q1~Q28은 2026-11-18 대화에서 사용자 승인. 추출 출력 스키마·recall 우선 가설·8장 그리드·점수 이어받기·칩 고정·후보 분포 비공개, Codex(gpt-6.2-sol) 검수 반영 수정(거절 기억 경계·값 귀속·그리드 예외·상황 참조·칩 고정 권한·다중 선택 이벤트·재개 멱등)과 2차 검수 반영(상황 참조 실패 보류·대조 있는 값 갱신·종료 시 pending 처리·상품 단위 "별로"·일반 탐색 8장·참조 키·가격·필수 FEA)·3차 검수 반영(품목 범위 재사용 후보·이유 없는 "별로"의 값 비반영·숨김 해제·결정 15 분리)은 2026-11-19 대화에서 사용자 승인. 이 ADR의 Accepted 승인은 미승인
- Superseded by (부분): [ADR 0015](0015-top-memory-warm-start.md)가 결정 8의 점수 요청 한정과 결정 11의 `기타` 매칭 제외를 부분 대체

## 맥락

현재 흐름(`app.py`의 `_extract`/`_explore`)은 추출 → 확인 → context → 목표 제안을 직렬 관문으로 잇는다. 관문 하나라도 어긋나면 요청 전체가 멈춘다. 실제 DeepSeek 점검 4회에서 카드가 나온 요청은 최대 6/8이었고, FEA→PI 가설 비교는 32회 중 0회 나왔다. 원인은 통째 거부, 확인 전 탐색 불가, 상황의 문자열 일치, 구조까지 세는 6,000자 예산, 모델 자발성에 맡긴 가설 생성이다. 결정 기준도 코드에 노드로 드러나 있지 않다.

## 결정

1. 흐름 제어만 LangGraph StateGraph로 옮긴다. 저장 계약(`store_v1.apply_batch`, 확인·동의 분리)과 `ConsumerService`의 HTTP action·`ConsumerState`는 유지하고, 새 필드는 추가만 한다. 모델 호출은 기존 `llm.py`/`model_io.py` 어댑터를 쓴다. 새 의존성은 `langgraph`와 SqliteSaver용 `langgraph-checkpoint-sqlite`(둘 다 버전 고정)뿐이다.
2. 노드: parse_turn → update_intent → propose_hypotheses → route → (ask_clarify | retrieve → plan_probe) → compose_turn → interrupt → parse_turn 반복 | finalize.
3. 상태: 요청 안의 작업 상태(IntentState: PI hard/soft, FEA 요구, 상황, 값별 점수, 질문 큐, 가설)는 checkpointer(SqliteSaver), 기억 정본은 기존 메모리 SQLite에 둔다. 요청마다 `thread_id`를 하나 둔다. 재개 시 `interrupt()`가 있는 노드가 처음부터 다시 실행되므로, 사용자 이벤트는 명령 ID·상태 버전으로 한 번만 반영하고 저장 영수증 기준으로 재개한다. 재개할 때는 요청의 종료·삭제 상태를 영수증 재생보다 먼저 확인해, 종료·삭제된 요청에는 늦은 해석 결과를 붙이거나 카드를 다시 발행하지 않는다. 체크포인트·trace의 보관 기한과 삭제는 요청 데이터 삭제와 함께 처리한다.
4. 검증: 모델 응답은 항목별로 검증해 틀린 항목만 버리고 상태에 경고로 남긴다. 버린 항목을 참조하던 질문·상황 연결도 함께 버린다. hard 조건 해석이 실패하면 원문을 보존하고 확인 질문을 큐에 넣는다. JSON 파싱 실패·공급자 오류는 1회 재시도 후 같은 근거를 `pending`으로 남기거나 명시적 오류로 보인다. 사용자는 `pending`이 있어도 언제든 종료할 수 있다. 종료 시 선택 사실은 보존하고, 해석이 끝나지 않은 근거는 확정·동의 대상에서 뺀다([ADR 0007](0007-joint-feedback-and-end-consent.md)의 종료 후 늦은 해석 금지 유지). 상황 참조가 검증에 실패한 wish는 상황 없이 적용하지 않는다. 원문만 보존하고 적용·저장을 보류한 뒤 확인 질문을 큐에 넣는다. 응답 전체 거부는 권한·확정·동의 주장과 인용 위조에만 적용한다.
5. 탐색: 확인 전 조건도 soft로 탐색에 쓴다. hard 필터는 직접 말했거나 확인한 조건만 쓴다. 직접 말한 Type은 hard다. 상대 가격 표현은 Price 하위 구간 soft 선호로, 숫자 가격만 hard로 둔다. 숫자 가격은 사전 값으로 바꾸지 않고 원화 원값과 비교 경계(이하·미만·이상·범위)를 그대로 보존해 상품 판매가와 비교한다. 상품 PI로 확인할 수 없는 필수 FEA는 탐색 중 미해결로 표시하고, 추가 근거나 조건 조정 전에는 최종 확정을 보류한다(현재 동작 유지). 종료는 항상 가능하다. 품목만 있어도 카드를 보인다.
6. route는 코드 규칙이다. hard 충돌 → 질문, 품목 없음 → 질문, 그 밖에는 → 그리드 탐색이다. 가설 묶음이 있으면 8번 구성을 쓰고, 없으면 일반 탐색 카드를 보인다. 일반 탐색도 8장을 기본으로 하고 8번의 구성 예외를 같이 적용한다(현재 카드 플래너의 최대 4장은 확장한다). 질문은 하나의 큐에서 한 턴에 최대 1개만 보인다.
7. 가설: propose_hypotheses는 FEA 요구가 추가·삭제될 때마다 호출한다. 모델이 FEA 요구, 근거 문장, 사전 값을 읽고 PI 가설을 제안한다. 재고에 맞춘 가설을 피하려고 현재 후보의 축별 분포는 모델에 주지 않는다. 상품이 없는 값은 코드가 그리드 구성에서 제외한다. 사용자가 원하는 PI를 모르는 상태이므로 precision보다 recall을 우선한다. 가설은 참·거짓을 판정할 대상이 아니라 탐색 범위다. FEA 하나에서 축이 다른 가설 여러 개를 낼 수 있고 개수를 좁게 제한하지 않는다. 가설은 축 1개(Type·Color·Fit·Fabric·Detail), 사전 값 1개 이상, 이유, 근거 FEA ID로 이뤄진다. 사전 밖 값, 직접 PI가 있는 축, 제외된 값은 그 가설 또는 값만 버린다. 가설 묶음은 다음 FEA 변경까지 유지한다. 다시 만들 때 새 묶음에 남은 값의 점수는 이어받는다. 점수 키는 (대상 품목, 적용 범위, 축, 값)이다. 대상·상황이 정정되면 정정 전 근거에만 기대던 점수는 이어받지 않고 버린다.
8. 그리드 탐색: 매 턴 이미지 8장을 보이고 사용자는 마음에 드는 이미지를 여러 장 고른다.
    - 점수: 가설 묶음의 (축, 값)마다 Beta(α, β) 점수를 두고 Thompson sampling으로 상품을 고른다. 점수는 이번 요청에만 쓰며 hard로 자동 승격하지 않는다.
    - 구성: 수렴 칸(현재 점수 상위, 턴에 따라 2→4→6장), 탐색 칸(노출이 적어 불확실한 값), 대조 칸 1장(가설 값 없음). 같은 축의 값을 여러 이미지에 고르게 퍼뜨리고 특정 조합이 늘 함께 나오지 않게 한다.
    - 구성 예외: 조건에 맞는 상품이 8개보다 적으면 서로 다른 적격 상품만 보인다. 대조 칸은 이번 턴에 다루는 값의 비포함이 상품 정보로 확인된 상품만 쓰고, 없으면 탐색 칸으로 돌린다. 미확인 PI는 비포함 사례로 쓰지 않는다([ADR 0006](0006-fea-to-pi-hypothesis-comparison.md) 유지). 조건 때문에 후보가 0개면 조건 조정을 묻는다. 숨긴 상품 때문에 0개가 되면 숨김 해제나 종료를 제공한다. 한 턴에 노출하는 가설 축 수를 제한해 흔한 값이 노출만으로 점수를 얻지 않게 한다.
    - 값 귀속: 이미지 선택으로 값 점수를 갱신하려면 같은 대상 품목의 같은 축에서 선택한 쪽과 미선택 쪽의 값 차이가 상품 정보로 확인돼야 한다. 그때만 선택한 쪽에만 있는 값은 α를 올리고, 미선택 쪽에만 있는 값은 β를 약하게 올린다. 양쪽에 모두 있는 값은 중립이다. 전부 선택했거나, 전부 미선택이거나, 반대편 값이 미확인이면 값 점수는 바꾸지 않고 상품 순위 신호로만 쓴다. Fabric은 사진으로 확인할 수 없으므로 이미지 선택으로 갱신하지 않고, 소재를 지목한 이유 칩이나 텍스트가 있을 때만 갱신한다. 같은 노출은 한 번만 센다. 다중값 축은 이미지에 보이는 값과 상품 옵션 전체를 구분한다.
    - 다른 신호: 이유 없는 "별로"는 그 상품의 순위와 숨김 횟수에만 반영하고 값 점수는 바꾸지 않는다. 값 점수는 사용자가 이유 칩·텍스트로 속성을 지목했거나 위의 유효한 대조가 있을 때만 바꾼다. 신호가 애매할 때만 띄우는 "어디가 좋았어요?" 칩(코드가 이미지 간 PI 차이로 생성)은 사용자가 고른 축에만 반영한다. "이거랑 비슷한 거"는 그 상품과의 유사도 순위로 반영한다. "다 별로"는 수렴 칸을 줄이고 탐색 칸·대조 칸을 늘리며, 반복되면 FEA 해석을 텍스트로 묻는다. 갱신 크기와 Beta 사전값은 파일럿으로 정하는 초기 가정이다.
    - 제외: "별로"는 서로 다른 노출에서 그 상품에 누른 것만 횟수로 세며, 2회면 이번 요청에서 그 상품을 숨긴다. "다 별로"는 그리드 반응이며 숨김 횟수에 세지 않는다. 숨김은 이번 요청 안에서 해제할 수 있다. 값 제외는 사용자가 이유 칩·텍스트로 그 값을 지목해 거절했거나, 위의 값 귀속 조건을 만족하는 대조 노출에서 3턴 연속 선택되지 않았을 때만 센다. 그 값이 노출되지 않았거나 대조가 성립하지 않은 턴은 세지 않는다. 제외는 이번 요청의 탐색 범위에만 적용하고 되돌릴 수 있으며 기억을 만들지 않는다.
    - 다중 선택 이벤트: 한 턴의 다중 선택(최대 8장)·"별로"·이유 칩·텍스트는 하나의 원자적 피드백 이벤트로 접수한다. 서버가 발행한 카드·이미지·상품 버전과 선택한 부위가 그 이미지의 대상 품목에 속하는지를 검증하고, 선택 사실과 이유 해석을 분리하며, 해석 실패는 같은 근거를 `pending`으로 재처리한다. 현재 `submit_feedback`(선택 최대 4개)·`respond_comparison`(단일 선택)은 이 이벤트로 확장한다.
9. 이해 칩과 순환: 그리드 위에 점수가 오른 값을 "지금 이렇게 이해했어요" 칩으로 보인다. 칩 고정은 "이번 요청에서 필수로 적용"으로 표시하고, 서버가 표시된 칩 이벤트를 검증한 뒤 이번 요청의 hard 조건으로 쓴다. 고정은 언제든 해제할 수 있다. 칩 x는 그 값을 이번 요청의 탐색 범위에서 빼며 기억을 만들지 않는다. hard 권한은 사용자가 직접 말한 필수 조건·칩 고정·확인한 조건에만 있고, 모델이 낸 `strength=hard`는 서버가 원문으로 검증한 뒤에만 쓴다. 상위 후보가 2턴 연속 거의 같으면 수렴 상태로 표시하고 최종 선택을 권한다. 단, 후보가 부족하거나 같은 상품이 반복 노출된 경우는 수렴으로 보지 않는다. 순환은 사용자만 끊으며 최종 선택·종료를 항상 제공한다. 상호작용은 이미지 중심이고 텍스트 입력은 항상 열어 두되 필수가 아니다.
10. 거절 기억: 사용자가 이유로 대상과 싫은 속성을 밝혔거나, 시스템이 보인 비선호 해석을 사용자가 확인한 경우에만 MemoryItem(polarity=avoid, strength=soft, origin=inferred) 후보를 만든다. 미선택·"별로"·칩 x·8번 제외 규칙만으로는 만들지 않는다. 조건은 품목 + 정규화한 상황 + 근거 FEA다. 상황 참조 실패·`기타`·상황 없음은 구분한다. 참조 실패는 4번에 따라 보류한다. `기타`는 원문을 보존하되 다음 요청 매칭에 쓰지 않는다. 상황 없는 거절(`applies.mode=request`)을 품목 범위로 재사용하는 것은 사용자가 그 범위("바지는 다")를 직접 말하고 확인한 경우에만 동의 대상으로 올린다. 이렇게 확인한 품목 범위 거절은 기존 상황 조건 기억을 바꾸지 않고 별도 재사용 후보로 만들며, 다음 요청에서 상황과 무관하게 품목으로 매칭한다(현재 저장 계약이 요청 슬롯을 지우는 승격을 거부하므로 새 후보로 만든다). 무조건 비선호는 만들지 않는다. 단기 기억에는 바로 반영하고, 장기 기억은 종료 요약에서 조건을 포함한 문장으로 동의를 받는다([ADR 0007](0007-joint-feedback-and-end-consent.md) 유지). 다음 요청에서는 종료 후 동의한 항목만, 상황 조건 기억은 품목과 상황이 일치할 때, 품목 범위 재사용 후보는 품목이 일치할 때 soft 감점하고 같은 가설을 제외한다. 현재 저장 조건 키는 FEA를 받지 않으므로 FEA는 기억 내용·binding으로 남기고 매칭은 품목 + 상황으로 한다. 서로 다른 상황 2곳 이상에서 거절되면 일반화할지 사용자에게 묻는다. 연구 흐름에서는 온보딩·요청 1에서 참가자가 재사용 범위를 보고 동의한 기억이 요청 2에서 재사용되는 경로를 검증 시나리오에 포함한다.
11. 상황: 요청 안의 상황은 조건이 아니라 사실이다. 상황 키는 occasion·season·activity로 둔다(season 추가, goal은 매칭에서 제외). 현재 store·retrieval은 occasion·activity·goal만 받으므로 season 저장·검색과 기존 goal·`기타` 기억의 호환을 구현에 포함한다. 값은 닫힌 사전으로 정규화하고, 맞는 값이 없으면 `기타`로 두고 원문을 보존하며 매칭에 쓰지 않는다. 사전은 버전이 있는 JSON으로 관리한다. 초안 값은 다음과 같다.
    - occasion: 출근·발표/미팅·면접·데이트·하객·여행·주말 외출·운동·집
    - season: 봄·여름·가을·겨울
    - activity: 걷기 많음·오래 앉음·야외·실내
12. parse_turn 모델 출력은 `situations`·`wishes`·`questions` 세 필드로 나눈다. 상황은 선호 후보 틀에 넣지 않는다.
    - `situations`: 항목마다 `id`, `key`(occasion·season·activity), `value`(11번 사전 값 또는 `기타`), `raw`(원문 표현), `quote`, `source_ids`를 둔다. 상황 항목에는 polarity·strength·binding이 없다.
    - `wishes`: 선호·요구·비선호를 담는다. 항목마다 `key`(응답 안에서 유일, 서버가 요청 범위의 안정적인 ID로 바꿔 저장), `target_id`(서버가 넘긴 대상 품목 슬롯), 선택 부위 참조(이미지 근거일 때), `source_ids`(서버가 넘긴 근거 별칭), `quote`를 둔다. 근거가 정정·철회되면 그 근거에만 기대던 wish와 점수·질문 참조를 함께 무효로 한다. `polarity`는 prefer·avoid·indifferent이고, 요구는 `prefer` + `strength=hard`로 표현한다(`require` 폐지). 모델 출력에는 `kind`를 두지 않고 코드가 polarity·strength로 유도한다. binding은 `pi`(feature·values·match)와 `fea`(category·subcategory·tag) 목록으로 나누고, polarity·strength는 wish의 값을 물려받는다.
    - 상황 연결: wish는 자유 텍스트 조건 대신 `applies`로 적용 범위를 밝힌다. `applies`는 `{"mode": "situations", "situation_ids": [...]}`(상황에 묶임), `{"mode": "request"}`(상황 없는 이번 요청), `{"mode": "baseline"}`("원래·평소·항상"처럼 일반 취향이라는 명시적 신호) 중 하나다. 기본은 이번 요청의 상황에 묶고, 상황이 없으면 `request`다. `baseline`이 일반 취향을 뜻하므로 `scope_hint`는 두지 않는다. `situation_ids`는 같은 응답의 상황 항목 또는 서버가 입력에 넣어 준 이전 턴 상황의 버전 있는 참조만 쓸 수 있고, 코드가 존재를 검사한다. "출근이 아니라 주말"처럼 정정하면 기존 상황 사실을 교체한다. "출근할 땐 슬랙스, 주말엔 청바지"처럼 상황별 규칙은 상황 항목 여러 개와 각 wish의 참조로 표현한다. 10번 거절 기억의 상황 조건은 wish가 참조한 상황에서 가져온다.
    - `questions`: 모델이 해석이 애매해 되묻는 질문이며 최대 3개다. 항목마다 `text`(한국어 한 문장), `about`(같은 응답 또는 서버가 넘긴 이전 턴의 `wish_keys`·`situation_ids`), `reason`(ambiguous_need·unclear_situation·possible_correction·unstated_reason)을 둔다. 코드가 `about`의 키 존재를 검사하고, 틀린 질문은 그 질문만 버린다. 품목 누락과 hard 충돌 질문은 route가 만들므로 모델 `reason`에 두지 않는다. 모델 질문과 코드 질문은 6번의 같은 큐에 들어가며, 답은 parse_turn이 `about`의 대상에 반영한다.
    - 이미지 선택만 있는 턴은 서버가 선택 사건을 먼저 기록하며, 세 필드가 모두 빈 배열인 출력도 유효하다. 선택과 정정 문장이 함께 오면 정정을 먼저 해석한다.
    - 코드는 이 출력을 기존 MemoryItem(상황은 `kind=situation`과 `fact`)으로 변환해 저장한다. 확인·동의·삭제 경로는 공유한다.
13. 근거 예산 6,000자는 사용자 문장과 근거 원문만 센다. ID·참조·제약 사본은 세지 않는다.
14. 이행: `src/stylemate_memory/graph/`에 구현하고 `STYLEMATE_ENGINE=graph|legacy`로 선택한다. 평가에서 기존 경로 이상이고 hard 위반·동의 없는 기억 재사용·피드백 중복 반영이 0건이며, 실제 카탈로그에서 대조 칸 구성률과 잘못된 수렴을 확인한 뒤 legacy 흐름 코드를 삭제한다. RQ 판단은 중간보고서의 참가자 평가를 유지한다.
15. 남은 결정: 두 묶음으로 나눈다.
    - Accepted 전에 정할 것
        - 최종 선택: 그리드에서 코디 전체·부위·상품 중 무엇을 확정하는지는 실제 수집 이미지(코디컷·단품컷 구성)를 확인한 뒤 정하고, 현재 단일 카드 최종 선택 API의 확장 범위를 함께 정한다.
        - 전환·호환: legacy 전환의 비교 지표·분모·합격선, 기존 요청 데이터의 재개 호환 범위, 체크포인트·trace 보관 기간과 삭제 방법을 값으로 정하거나 적용할 기존 정책을 지정한다.
        - 연구 절차: 연구 세션 안의 요청별 종료, 개방형 질문의 "처음 보여준 5개" 문구를 "처음 보여준 후보"로 바꿔 실제 노출 수와 연결한 기록, 참가자 데이터·trace 기록 범위
    - 구현·파일럿에서 정할 것(Accepted 조건 아님)
        - 점수: Beta 사전값, 상품별 점수 결합식, 갱신 크기, 신호가 겹칠 때 우선순위, 재현용 난수 시드, 수렴과 후보 부족의 판정 기준
        - 질문: hard 충돌·모델 질문·이유 칩이 같은 턴에 경쟁할 때의 우선순위, 건너뛰기·정정·고정 해제 후 재계산 범위
        - 표시: Fit·Detail 모델 보완값의 "추정" 표시, Fabric은 원문 근거가 있을 때만 "소재 정보 기준"으로 표시하고 이미지 선택을 소재·기능 확인으로 해석하지 않음
        - 테스트로 고정: 카드·버전 변경이나 명령 재전송 시 "별로" 횟수 중복 방지, 원화 가격 비교 경계, 종료와 늦은 응답의 경합

## 대안

- 현재 직렬 구조에 임시 완화를 계속 추가: PR [#12](https://github.com/jongrionro-debug/HCI_HANDSOME/pull/12) 수정 후에도 6/8, 가설 0회로 구조적 원인이 남는다.
- LLM 라우터: 결정 기준을 테스트·연구 보고로 고정할 수 없다.
- FEA→PI 연결표를 사전에 두고 코드가 선택: 사용자 결정으로 채택하지 않았다. 모델이 FEA 맥락을 읽고 제안한다.
- 거절을 값 단위 비선호("와이드 싫음")로 저장: 상황에 따른 선호가 일반 취향으로 잘못 넓어진다.
- 거절 기억의 자동 장기 저장: ADR 0007의 종료 후 별도 동의, RQ1의 통제감과 충돌한다.
- 상황을 `kind=situation` 후보로 선호와 같은 목록에 유지: 의미 없는 고정값(polarity·strength·빈 binding)이 생기고 상황과 바람을 섞는 실수가 잦아 프롬프트 규칙이 늘어난다.
- wish마다 자유 텍스트 조건(`conditions`) 유지: 사전 밖 텍스트가 조건에 들어가 매칭이 흔들린다. 상황 ID 참조로 대체한다.
- 가설 포함/비포함 대비 쌍을 한 턴에 하나씩 비교: 신호는 깨끗하지만 한 턴에 축 하나만 확인해 넓은 가설 묶음을 다루기에 느리다.
- 미선택·"별로"·칩 x를 거절 기억으로 저장: 상품 전체에 대한 반응이나 탐색 조작을 특정 속성 비선호로 과하게 귀속하고, "미선택은 저장하지 않는다"와 충돌한다.
- 선택 이미지의 모든 값에 같은 가점: 선택·미선택 이미지에 함께 있는 값의 점수가 오히려 내려가는 등 값 효과를 식별할 수 없다.
- 저장 계층까지 LangGraph store로 교체: 검증된 확인·동의·삭제 계약을 다시 만들어야 한다.

## 영향

- 이점: 관문 하나로 요청 전체가 멈추지 않는다. 가설 비교가 전용 노드로 항상 시도된다. 피드백이 값별 가중치와 조건부 거절 기억으로 누적된다. 결정 기준이 route 표 테스트로 고정된다.
- 비용·위험: 저장소의 "추가 Python 의존성 없음" 원칙을 깬다(CI 설치 단계 필요). 확인 전 soft 탐색이 틀린 해석을 카드에 반영할 수 있다. Fabric 가설은 이미지로 확인할 수 없어 상품 원문 값만 비교 근거로 쓰고 "소재 정보 기준"으로 표시한다. 상황 사전 밖 표현은 매칭되지 않는다. 현재 카탈로그(29CM 정본 187개, 이미지 확인 179개)는 품목별 상품이 적어 8장·대조 칸을 채우지 못할 수 있으며, 수집 확대 전까지 8번 구성 예외로 처리한다.
- 후속 작업: [Issue #13](https://github.com/jongrionro-debug/HCI_HANDSOME/issues/13)에서 `STYLEMATE_ENGINE=graph` 선택 경로로 구현(상황 사전 JSON, 순수 로직·route 표 테스트, 각본 모델 통합 테스트, 그리드 브라우저 검사, [project.md](../project.md) 갱신). 상태는 15번의 Accepted 조건을 정할 때까지 Proposed로 둔다.
- 검증: 점검 시나리오 약 12개 × 3회 반복을 비율로 본다(카드 노출률, 가설 값 노출률, 버려진 항목 수·이유, 노드별 실패 위치, LangGraph trace). 기존 444개 테스트와 브라우저 검사 2종을 유지한다.
