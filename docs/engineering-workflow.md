# 개발 워크플로

이 문서는 로컬 조사·구현·검증과 요청받은 PR/리뷰 작업의 절차를 관리한다. **브랜치 관리는 사용자가 맡고 Codex는 현재 체크아웃에서 작업한다.** 새 브랜치·Issue·별도 계획 문서는 개발의 선행 조건이 아니다.

## 문서와 실행 기준

시스템·연구 설계는 [중간보고서](sources/Team4_mid-term_report.pdf)를 따른다. 원문·보조 자료의 우선순위는 [자료 안내](sources/README.md), 설계와 현재 코드의 차이는 [workflow](workflow.md), 현재 실행 계약은 [메모리 프로토타입](shopping-memory-prototype.md)에서 확인한다. 연구 작업은 보고서 2장·4~5장과 [master](master.md)를 따른다.

[archive](../archive/README.md)의 당시 설계·승인·검증은 역사적 기록이다. 현재 코드에 적용 중인 ADR과 보고서의 요구사항을 구분한다. 문서 지도는 [README](../README.md), 필수 작업 규칙은 [AGENTS.md](../AGENTS.md)를 따른다.

## 1. 범위 확인

- Git 상태·현재 브랜치·HEAD와 기존 변경을 확인한다. 브랜치 생성·전환·병합은 사용자에게 맡기고 현재 체크아웃에서 로컬 작업을 진행한다.
- 요청의 문제·목표·요구사항·완료 조건·제외 범위를 확인한다. 관련 Issue가 있으면 참고하되 Issue 등록·연결을 요구하거나 임의로 원격 작업을 만들지 않는다.
- 관련 진입점·핵심 로직·저장/외부 연동·테스트·실행 문서·ADR을 필요한 범위에서 읽는다.
- 의미 있는 변경은 바꿀 동작·지킬 동작·확인 방법을 채팅에 3줄 이내로 설명한다. 별도 기획·계획·탐색 문서는 필요하지 않다.
- 결과를 크게 바꾸는 불확실성만 질문한다. 제품 스택·서비스 경계·저장/삭제 정책·인증·공개 API 등의 중요한 변경은 대안·영향을 제안하고 승인 후 구현한다.

**진행 조건:** 범위와 관찰 가능한 완료 조건, 필요한 검증 방법이 있고 중요한 설계 변경은 승인됐다.

## 2. 구현

한 목적에 필요한 최소 변경으로 기존 구조·컨벤션을 따른다. 범위 밖 리팩터링·폴더 재배치·의존성 추가는 제외한다. 버그는 재현 조건과 회귀 위험을 보호하는 기존/새 검증으로 확인한다.

현재 동작이나 계약이 바뀌면 관련 실행 문서도 함께 갱신한다. 미구현 내용은 계획으로 표시한다. 보고서가 구체화하지 않은 로컬 파라미터를 새 확정 요구사항으로 만들지 않는다. 기존 문서를 우선 갱신하고 중요하지 않은 변경에 ADR을 만들지 않는다.

원본 PDF와 승인된 ADR 본문·과거 검증 기록은 보존한다. Markdown·HTML 쌍은 표시 본문과 내장 원문을 함께 맞추고 화면을 확인한다. 내장 원문 일치만으로 화면 정확성을 주장하지 않는다.

실행 DB·참여자 자료·동의서·원시 응답은 저장소 밖에 둔다. 비밀·자격 증명은 명시적인 비밀 관리 작업 외에는 접근하지 않는다. 실제 모델 호출은 사용자가 해당 실행을 요청한 범위에서만 한다.

## 3. 검증

공통 검사:

```sh
python3 scripts/check_repository.py
git diff --check
```

| 변경 | 추가 검증 |
|---|---|
| 문서·자료 정리 | 보고서 원문 대응, 관련 링크·앵커, 원본/보관 자료 보존 확인 |
| HTML·UI | 브라우저 본문·레이아웃·관련 조작. Markdown 쌍이 있으면 내장 원문도 확인 |
| 메모리 코드 | 기존 단위·SQLite·통합 테스트와 가상 데모, 변경한 경계의 회귀 검증 |
| 검사 로직·CI | 정상 입력과 오류 입력의 성공/실패, YAML 변경 시 구문 확인. 원격 적용은 별도 확인 |

현재 메모리 테스트와 데모:

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -q
PYTHONPATH=src python3 -m stylemate_memory.cli demo --synthetic
```

문서 검사기는 코드 블록 밖의 인라인 Markdown 링크·지원하는 제목 앵커, HTML의 내장 원문 쌍, 보존된 Issue/PR 템플릿의 기본 구성을 검사한다. `archive/`는 제외한다. 이미지·참조형 링크·HTML 링크·외부 URL·Figma 연결·YAML 전체 문법·화면 품질은 검사하지 않는다. 실제 Issue 등록·PR 형식도 강제하지 않는다.

문서 검사 통과, 오프라인 모델 fixture, 실제 모델 호출, 의미 품질·추천/사용자 효과의 검증을 구분한다. 필요한 검증은 생략하거나 약화하지 않는다. 실행 결과는 통과·실패·미실행·해당 없음으로 구분하고 미실행/해당 없음의 이유를 밝힌다.

## 4. 검토와 전달

diff와 미추적 파일을 검토해 의도한 변경만 남기고 기존 사용자 변경을 보존한다. 이번 작업의 임시 파일을 정리한다. 결과·핵심 위치·실제 검증과 한계·남은 점을 간결하게 전달한다. 별도 완료 보고서나 PR 본문 초안은 요청이 있을 때만 만든다.

PR·리뷰를 요청받으면 최신 변경과 완료 조건을 근거로 목적·핵심 변경·검증 결과·미완료/위험을 설명한다. Issue 연결·정형 체크리스트는 선택이다. 체크박스를 쓰면 실제 확인한 항목만 선택한다. [PR 안내](../.github/pull_request_template.md)를 참고할 수 있다.

리뷰는 결함·회귀·완료 조건 누락·검증 공백을 우선하고 심각도·파일 위치·발생 조건·영향을 제시한다. 수정 뒤 영향받는 검증과 최신 diff를 다시 확인한다. 필요한 검증이 실패/미실행이면 완료·병합 준비로 보고하지 않는다.

Commit·Push·PR/Issue 생성·원격 리뷰·병합·배포·원격 설정 변경은 작업 구현 요청만으로 허용되지 않는다. 요청 범위에서만 수행하며 사용자가 최종 검토와 병합 판단·실행을 맡는다. Codex 리뷰와 실제 GitHub 승인 리뷰를 구분한다.

## Architecture Decisions

구조·계약·운영에 지속적인 영향을 주는 선택이 필요할 때 기존 번호에 이어 `docs/decisions/NNNN-short-title.md`를 만든다. 오탈자·국소 UI 조정·문서 위치 정리·기존 패턴을 따르는 구현에는 형식적 ADR을 만들지 않는다.

```md
# NNNN · 결정 제목

- Status: Proposed / Accepted / Superseded
- Date: YYYY-MM-DD
- Related Work: 요청·논의 또는 PR (관련 Issue가 있으면 연결)
- Approval: 사용자 승인 근거와 날짜 (미승인 시 미승인)
- Applies to: 결정이 적용되는 구현·운영 범위
- Supersedes: 이전 ADR (있는 경우)

## Context
문제·요구사항·제약과 결정이 필요한 이유

## Decision
선택한 방향과 적용 범위

## Alternatives
대안과 채택하지 않은 이유

## Trade-offs
이점·비용·위험

## Consequences
구현·테스트·운영·마이그레이션과 후속 작업
```

중요한 변경은 승인 전까지 `Proposed`다. 승인된 본문은 역사적 기록으로 보존한다. 결정이 바뀌면 새 ADR에서 이전 결정을 참조·대체하고 이전 ADR에는 상태·관계 메타데이터만 갱신한다. ADR은 결정 이유이고 현재 실행 문서는 실제 동작을 설명한다.

## CI의 범위

현재 정의는 `repository-checks`의 문서·템플릿 검사와 `memory-tests`의 Python 3.11/3.14 오프라인 테스트·가상 데모다. 파일 존재나 로컬 검사만으로 실제 GitHub CI·브랜치 보호·승인 규칙이 활성화됐다고 보고하지 않는다. 원격 설정은 사용자가 관리한다.
