# 개발 워크플로

이 문서는 이 저장소의 개발 절차 정본이다. Issue → Planning → Implementation → Testing → Pull Request → Review → Merge 순서로 진행한다. 각 단계의 산출물과 완료 근거를 다음 단계에 전달한다.

## 저장소 분석과 적용 범위

2026-10-10 적용 전 로컬 저장소를 확인한 결과다. 원격 GitHub 설정은 조사하지 않았다.

| 항목 | 확인한 상태와 적용 방식 |
|---|---|
| 목적 | StyleMate의 선호 분리·사용자 제어·적응형 텍스트/이미지 상호작용 연구. `master.md`의 확정된 RQ를 유지한다. |
| 기술 스택 | 제품 코드·패키지 매니페스트 없음. 제품 스택 미정. 기존 문서는 Markdown과 CSS·JavaScript가 포함된 HTML이다. |
| 구조 | `docs/`에 연구 기준·제품 동작 설계·선행 연구 조사, `Assignment/`에 과제와 디자인 참조가 있다. |
| 기존 규칙 | `Assignment/Readme.md`의 과제 PDF 제외 규칙, `.gitignore`의 비밀·참여자 데이터 제외 규칙, 기존 문서의 사실/제안/미정 구분을 유지한다. |
| README·설계 | 루트 README 없음. `docs/workflow.md`는 제품 설계이며 개발 절차로 덮어쓰지 않는다. 기존 Markdown·HTML과 과제 자료를 보존한다. |
| 에이전트 지침 | 저장소 내부 루트·하위 `AGENTS.md` 없음. 세션에 적용된 사용자 지침과 상위 지침을 존중하며 루트 작업 규칙을 추가한다. |
| GitHub·테스트·CI | `.github/`, 테스트, CI, ADR 없음. Issue Forms, PR 양식, 문서·구성 검사 CI를 추가한다. 제품 테스트는 제품 구현 시 추가한다. |

문서의 역할과 읽기 순서는 [README](../README.md), Codex의 필수 작업 규칙은 [AGENTS.md](../AGENTS.md)를 따른다. 같은 내용을 여러 정본에 복제하지 않는다.

## 역할과 권한

| 담당 | 책임 |
|---|---|
| 사용자 · GitHub Desktop | 기준 브랜치 동기화, 작업 브랜치 선택·생성, diff 확인, Commit·Push |
| 사용자 · GitHub | Issue 등록·범위 확정, PR 생성, 원격 설정, 최종 검토·병합 |
| Codex | 로컬 조사·계획·구현·테스트·문서 갱신, PR 본문 초안, 코드 리뷰·수정 |

Codex의 원격 작업에는 별도의 명시적 요청이 필요하다. 작업 구현 요청만으로 Commit·Push·PR 생성·리뷰 게시를 허용하지 않는다. 중요한 아키텍처 변경은 사용자 승인 후 구현한다.

## 1. Issue

사용자는 Feature Request 또는 Bug Report 양식으로 문제와 완료 조건을 정의한다. 기능 Issue에는 Background, Goal, Requirements, Acceptance Criteria, Out of Scope, References를 작성한다. 버그에는 재현 절차, 기대/실제 동작, 환경, Acceptance Criteria를 작성한다.

Acceptance Criteria에는 `AC1`, `AC2`처럼 식별자를 붙이고, 입력·행동·관찰할 결과를 적는다. 예: “이번 요청에서만 적용한 색상 조건은 새 요청의 기본 취향에 나타나지 않는다.” 구현 기술을 미리 고정하기보다 해결해야 할 문제와 제약을 명확히 한다.

**다음 단계 조건:** 목표·범위·검증 가능한 완료 조건이 정해져 있고, 버그는 재현 정보 또는 재현 불가의 근거가 있다. Issue가 아직 없으면 Codex가 로컬 초안을 제시하고, 사용자가 PR 전에 등록한다.

## 2. Planning

1. 사용자: GitHub Desktop에서 기준 브랜치를 동기화하고 `codex/<Issue번호>-<설명>` 브랜치를 준비한다. 예: `codex/42-request-preferences`. 하나의 Issue는 하나의 작업 브랜치·PR을 기본으로 한다.
2. Codex: 사용자 변경, 해당 범위의 `AGENTS.md`, 관련 코드·설계·ADR을 읽는다. 문서의 제안을 기존 구현으로 가정하지 않는다.
3. Codex: 구현 단계, 영향받는 파일, 테스트·완료 조건 대응, 문서 변경, 위험을 제시한다. 관련 Issue의 논의 또는 로컬 대화에 계획을 남긴다. 원격 댓글은 사용자가 게시한다.
4. 중요한 선택은 대안과 Trade-offs를 제안해 사용자 승인 후 ADR로 기록한다. 요청 범위가 명확한 일반 구현은 계획 공유 후 진행한다.

**다음 단계 조건:** 필요한 정보가 확보되고, 검증 방법이 있으며, 중요한 설계 변경이 있으면 승인됐다. 계획이나 AC가 달라지면 사용자와 범위를 다시 확인한다.

## 3. Implementation

Issue 범위 안에서 기존 구조·컨벤션을 따르고 변경과 함께 테스트·현재 동작 문서를 갱신한다. 범위 밖 문제는 후속 Issue 초안으로 분리한다. 연구 기준 변경, 선호 저장 범위, API 계약 변경 등은 단순 구현 세부사항으로 처리하지 않는다.

기존 Markdown을 먼저 수정한다. 대응 HTML이 있는 문서 변경은 표시 본문과 내장 원문도 같은 작업에서 갱신한다. 생성기가 저장소에 없으므로 사용한 재생성 방법 또는 수동 갱신 방법을 PR에 기록한다. 내장 원문만 변경하면 화면 내용이 최신이라는 증거가 되지 않는다.

**다음 단계 조건:** 필요한 코드·문서·테스트 변경이 준비되고, 승인되지 않은 설계 변경이나 범위 밖 변경이 섞이지 않았다.

## 4. Testing

로컬에서 공통 검사를 실행한다.

```sh
python3 scripts/check_repository.py
git diff --check
```

| 변경 | 추가 검증 |
|---|---|
| Markdown·워크플로 구성 | 관련 내용·링크·양식 검토. 검사 도구는 로컬 Markdown 링크와 지원하는 앵커, 대응 HTML의 내장 원문 일치, 템플릿 기본 구성을 확인한다. |
| HTML | 브라우저에서 본문·레이아웃·관련 조작을 확인한다. 내장 원문 비교는 화면의 정확성을 보장하지 않는다. |
| 검사 도구·CI | 정상 실행과 의도적인 오류 입력의 실패를 확인한다. GitHub Actions 결과는 원격에서 별도로 확인한다. |
| 제품 기능·버그 | 구현 시 채택한 스택에 맞는 단위·통합·필요한 UI 테스트를 실행한다. 버그는 재현 조건이 해결되고 기존 동작이 유지되는지 검증한다. |

현재 앱의 실행·빌드·제품 테스트 명령은 없다. 처음 제품 코드를 도입하는 Issue에서 재현 가능한 실행·테스트 명령과 CI를 함께 정하고 README를 갱신한다. 문서 검사 성공을 제품 기능 테스트 성공으로 보고하지 않는다. 외부 URL의 접근성, Figma 연결, HTML 시각 결과는 공통 검사 대상이 아니다.

검사기는 코드 블록 밖의 인라인 Markdown 링크와 지원하는 제목 앵커를 확인한다. 이미지·참조형 링크·HTML 링크는 검사하지 않는다. Issue 양식 검사는 필수 항목과 기본 문자열 구성을 확인하며, 전체 YAML 문법이나 GitHub 화면의 동작을 검증하지 않는다. 양식·CI YAML 변경 시 별도로 구문을 확인하고 GitHub 적용 결과도 확인한다.

PR에 테스트 명령/환경, 실제 결과, AC와의 연결을 기록한다. `통과`, `실패`, `미실행`, `해당 없음`을 구분하고 뒤의 두 경우는 이유를 적는다. CI 결과도 실제 실행을 확인한 경우에만 통과로 기록한다.

**다음 단계 조건:** 완료 조건별 검증 근거가 있고 필요한 테스트가 통과했다. 필요한 검증이 실패했거나 미실행이면 Ready for review/병합 준비 완료로 보고하지 않고 Draft PR에서 상태와 해결 계획을 명시한다.

## 5. Pull Request

Codex는 diff와 미추적 파일을 검토하고 [PR 양식](../.github/pull_request_template.md)에 맞는 본문 초안을 작성한다. 사용자는 GitHub Desktop에서 의도한 파일만 Commit·Push한 뒤 GitHub에서 PR을 생성한다. 미완료 작업은 Draft로 연다.

Related Issue는 완료할 Issue에 `Closes #번호`, 일부 작업이나 참조에는 `Refs #번호`를 사용한다. AC별 변경·검증 근거, 테스트의 실제 결과, 문서 변경 또는 불필요 사유, ADR 여부와 근거, 위험·타협점·남은 작업을 기록한다.

체크박스는 실제 확인한 항목만 선택한다. 해당 없음은 이유를 적고, 체크 항목에 해당 없음까지 포함하는 경우에만 그 근거를 확인한 뒤 선택한다. 미실행 항목을 통과로 바꾸거나 체크박스를 일괄 선택하지 않는다.

**다음 단계 조건:** PR 범위가 Issue와 일치하고 본문이 실제 변경·검증을 설명하며, CI 결과가 확인됐다. 리뷰 요청 시 검토할 최신 변경과 기준 브랜치를 식별한다.

## 6. Review

사용자는 Codex에 관련 Issue, PR diff 또는 로컬 기준 브랜치, 테스트 결과를 전달해 리뷰를 요청한다. 로컬 예시는 다음과 같다.

> Issue #번호의 AC와 기준 브랜치 대비 최신 diff를 리뷰해 줘. 결함·회귀·테스트 공백·문서/ADR 불일치를 우선 확인하고, 발견 사항은 심각도·파일 위치·발생 조건·영향으로 정리해 줘. 리뷰 범위와 미실행 검증도 밝혀 줘. 파일 수정과 원격 리뷰 게시는 하지 마.

Codex는 계획이 아닌 최종 변경을 검토한다. 사용자는 차단 의견을 해결하거나 근거와 함께 수용할 위험을 기록한다. 수정한 검증을 다시 실행하고, 새 변경이 있으면 해당 변경을 다시 리뷰한다. 코멘트 해결 표시만으로 결함 해결을 주장하지 않는다.

**다음 단계 조건:** 최신 변경의 리뷰가 완료됐고 차단 결함이 해결됐으며, 남은 위험을 사용자가 이해·수용했다. Codex의 로컬 리뷰는 GitHub의 필수 승인 리뷰를 대신하지 않는다.

## 7. Merge

병합 판단은 사용자가 한다. 최신 변경의 AC 충족, 필요한 검사 성공, 문서·ADR 정합성, 리뷰 의견 처리, 남은 위험을 확인한 뒤 GitHub에서 병합한다. Codex는 별도 승인 없이 `main`에 병합하지 않는다.

필요한 미완료 작업이 있으면 병합하지 않는다. 별도로 합의한 후속 작업은 Issue로 추적하고 원래 완료 조건을 조용히 축소하지 않는다. 병합 뒤 사용자는 Issue 종료 여부를 확인하고 GitHub Desktop에서 기준 브랜치를 동기화한다. 브랜치 삭제도 사용자 판단으로 수행한다.

## Architecture Decisions

중요한 기술 선택이 실제로 필요할 때 첫 `docs/decisions/NNNN-short-title.md`를 만든다. 빈 ADR 폴더나 이번 개발 절차 자체에 대한 형식적 ADR은 만들지 않는다. 다음 형식을 사용한다.

```md
# NNNN · 결정 제목

- Status: Proposed / Accepted / Superseded
- Date: YYYY-MM-DD
- Related Issue: #번호
- Approval: 사용자 승인 근거와 날짜 (미승인 시 미승인)
- Supersedes: 이전 ADR 경로 (있는 경우)

## Context
문제, 요구사항, 제약, 결정이 필요한 이유

## Decision
선택한 방향과 적용 범위

## Alternatives
검토한 대안과 채택하지 않은 이유

## Trade-offs
이점, 비용, 위험과 감수한 타협점

## Consequences
구현·테스트·운영·마이그레이션에 미치는 영향과 후속 작업
```

중요한 변경은 사용자 승인 전까지 `Proposed`다. 승인된 ADR은 본문을 보존하며, 결정 변경은 새 ADR에서 이전 결정을 참조하거나 대체한다. 이전 ADR에는 상태와 대체 ADR 링크만 갱신한다. ADR은 결정의 이유이고 현재 동작은 관련 설계·API 문서에서 관리한다.

## 최초 적용과 GitHub 설정

아래는 사용자가 GitHub에서 적용할 절차다. 파일 작성만으로 서버 설정이 활성화되지는 않는다. 이번 작업에서는 원격 상태를 확인하거나 변경하지 않았다.

1. GitHub Desktop에서 워크플로 파일을 Commit·Push하고, 리뷰를 거쳐 기본 브랜치에 반영한다. Issue 양식과 기본 PR 양식이 새 작성 화면에 나타나는지 확인한다.
2. Actions 실행이 허용되는지 확인한다. PR 또는 수동 실행으로 `repository-checks` 결과를 한 번 확인한다. 로컬 검사와 원격 CI 결과를 구분한다.
3. `main`에 브랜치 보호 규칙 또는 ruleset을 설정한다. PR을 통한 변경, 필수 상태 검사 `repository-checks`, 대화 해결, 최신 기준 브랜치 반영을 요구하고 force push·브랜치 삭제를 허용하지 않는다. 관리자 우회 허용 여부도 검토한다. [GitHub 브랜치 보호 문서](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
4. 다른 리뷰어가 있는 경우 승인 리뷰 1개 이상과 새 변경 시 기존 승인 해제를 적용한다. **1인 개발에서는 PR 작성자가 자신의 PR을 승인할 수 없다.** 승인 리뷰를 강제하려면 별도 리뷰어가 필요하다. 별도 리뷰어가 없으면 필수 승인 수는 요구하지 않고, Codex 리뷰 기록과 사용자 최종 검토를 운영 규칙으로 유지한다. 이는 독립된 사람의 승인 강제와 동일하지 않다. [GitHub 승인 리뷰 문서](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)
5. 새 Issue → 작업 브랜치 → 작은 변경 → 검사 → PR → 리뷰 → 병합을 한 번 수행해 설정이 기대대로 작동하는지 확인한다. 불필요한 테스트용 파일을 병합하지 않는다.

브랜치 보호 사용 가능 여부는 저장소 공개 범위와 GitHub 요금제에 따라 다르다. 사용할 수 없으면 PR과 검토 절차를 수동으로 준수하되, 서버가 강제한다고 보고하지 않는다. [지원 범위](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#who-can-use-this-feature)

현재 CI는 문서·양식의 구조적 검증이다. Issue의 의미, 계획의 적절성, 사용자 승인, 제품 테스트의 충분성, PR 체크박스의 진실성은 사람과 Codex의 검토로 확인한다. 향후 제품 코드가 추가되면 그 스택의 검사·테스트를 같은 개발 절차에 통합한다.
