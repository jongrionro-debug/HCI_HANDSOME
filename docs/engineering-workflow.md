# 개발 워크플로

이 문서는 이 저장소의 개발 절차 정본이다. 팀원은 `main`을 기준으로 담당 작업의 새 브랜치를 준비하고, 기획·구현·검증 → PR → 팀원 리뷰·병합 순서로 진행한다. Issue 등록·연결, 별도 기획 문서, 정형 PR 문서·체크리스트는 필수가 아니다. 작업의 목표·범위·완료 조건과 실제 검증은 유지한다.

## 저장소 분석과 적용 범위

아래 표는 2026-10-10 최초 적용 전의 역사적 분석이다. 현재 상태는 [README](../README.md)와 실제 코드·문서를 따른다. 2026-10-14 사용자에게 전달받은 팀 합의에 따라 개발 절차를 담당 작업별 브랜치와 PR 중심으로 갱신했다. 이번 변경에서 원격 GitHub 설정은 확인하거나 변경하지 않았다.

| 항목 | 확인한 상태와 적용 방식 |
|---|---|
| 목적 | StyleMate의 선호 분리·사용자 제어·적응형 텍스트/이미지 상호작용 연구. `master.md`의 확정된 RQ를 유지한다. |

문서의 역할과 읽기 순서는 [README](../README.md), Codex의 필수 작업 규칙은 [AGENTS.md](../AGENTS.md)를 따른다. 같은 내용을 여러 정본에 복제하지 않는다.

## 역할과 권한

| 담당 | 책임 |
|---|---|
| 담당 팀원 | 최신 `main` 확인, 작업 브랜치 준비, 범위·완료 조건 합의, 기획·구현·검증, Commit·Push·PR 생성 |
| 팀 리뷰어·병합 담당자 | 변경 검토, 차단 의견 처리 확인, 최종 병합 판단·실행. 원격 설정은 권한 있는 담당자가 관리 |
| Codex | 로컬 조사·계획·구현·테스트·문서 갱신, 코드 리뷰·수정. 요청이 있으면 PR 본문 초안 작성 |

팀원은 GitHub Desktop이나 CLI 등 각자 사용하는 도구로 작업할 수 있다. Codex의 Commit·Push·원격 작업에는 별도의 명시적 요청이 필요하다. 작업 구현 요청만으로 PR 생성·리뷰 게시·병합을 허용하지 않는다. 중요한 아키텍처 변경은 사용자 승인 후 구현한다.

## 1. 작업 범위

담당 팀원은 해결할 문제·목표·요구사항·완료 조건·제외 범위를 작업 요청이나 팀 논의에서 확인한다. 버그는 재현 절차, 기대/실제 동작과 환경을 확인한다. 별도 문서나 정형 표는 요구하지 않는다.

완료 조건은 관찰할 수 있는 결과로 정한다. 예: “이번 요청에서만 적용한 색상 조건은 새 요청의 기본 취향에 나타나지 않는다.” 구현 기술을 미리 고정하기보다 해결해야 할 문제와 제약을 명확히 한다. 필요하면 기존 Issue 양식으로 작업을 추적할 수 있으며, 관련 Issue가 있을 때는 그 내용을 함께 확인한다.

**다음 단계 조건:** 목표·범위·검증 가능한 완료 조건이 정해져 있고, 버그는 재현 정보 또는 재현 불가의 근거가 있다. Issue가 없어도 진행한다.

## 2. Planning

1. 담당 팀원: 최신 `main`을 기준으로 담당 작업의 새 브랜치를 준비한다. 이름은 작업을 식별할 수 있게 정하며 Issue 번호나 특정 접두사는 필수가 아니다. `main`에서 직접 기획·구현 변경을 하지 않는다.
2. Codex: 사용자 변경, 해당 범위의 `AGENTS.md`, 관련 코드·설계·ADR을 읽는다. 문서의 제안을 기존 구현으로 가정하지 않는다.
3. Codex: 구현 단계, 영향받는 파일, 테스트·완료 조건 대응, 문서 변경, 위험을 제시한다. 대화나 기존 작업 논의에 계획을 남긴다. 별도 계획 문서를 만들 필요는 없으며 원격 댓글은 사용자가 게시한다.
4. 중요한 선택은 대안과 Trade-offs를 제안해 사용자 승인 후 ADR로 기록한다. 요청 범위가 명확한 일반 구현은 계획 공유 후 진행한다.

**다음 단계 조건:** 필요한 정보가 확보되고, 검증 방법이 있으며, 중요한 설계 변경이 있으면 승인됐다. 계획이나 완료 조건이 달라지면 사용자와 범위를 다시 확인한다.

## 3. Implementation

담당 작업 범위 안에서 기존 구조·컨벤션을 따르고 변경과 함께 테스트·현재 동작 문서를 갱신한다. 범위 밖 문제는 후속 작업으로 분리한다. 연구 기준 변경, 선호 저장 범위, API 계약 변경 등은 단순 구현 세부사항으로 처리하지 않는다.

기존 Markdown을 먼저 수정한다. 대응 HTML이 있는 문서 변경은 표시 본문과 내장 원문도 같은 작업에서 갱신한다. 생성기가 저장소에 없으므로 사용한 재생성 방법 또는 수동 갱신 방법을 PR에 기록한다. 내장 원문만 변경하면 화면 내용이 최신이라는 증거가 되지 않는다.

**다음 단계 조건:** 필요한 코드·문서·테스트 변경이 준비되고, 승인되지 않은 설계 변경이나 범위 밖 변경이 섞이지 않았다.

## 4. Testing

로컬에서 공통 검사를 실행한다.

```sh
python3 scripts/check_repository.py
git diff --check
```

| 변경 | 추가 검증 |
|---|---|
| Markdown·워크플로 구성 | 관련 내용·링크·양식 검토. 검사 도구는 로컬 Markdown 링크와 지원하는 앵커, 대응 HTML의 내장 원문 일치, 템플릿 기본 구성을 확인한다. |
| HTML | 브라우저에서 본문·레이아웃·관련 조작을 확인한다. 내장 원문 비교는 화면의 정확성을 보장하지 않는다. |
| 검사 도구·CI | 정상 실행과 의도적인 오류 입력의 실패를 확인한다. GitHub Actions 결과는 원격에서 별도로 확인한다. |
| 제품 기능·버그 | 구현 시 채택한 스택에 맞는 단위·통합·필요한 UI 테스트를 실행한다. 버그는 재현 조건이 해결되고 기존 동작이 유지되는지 검증한다. |

현재 Python 3.11+·SQLite 프로토타입의 오프라인 테스트와 가상 데모 명령은 다음과 같다. 기능 변경 시 영향받는 검증을 실행하고, 새 실행·테스트 명령이 생기면 README를 갱신한다.

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -q
PYTHONPATH=src python3 -m stylemate_memory.cli demo --synthetic
```

문서 검사 성공을 제품 기능 테스트 성공으로 보고하지 않는다. 외부 URL의 접근성, Figma 연결, HTML 시각 결과는 공통 검사 대상이 아니다.

검사기는 코드 블록 밖의 인라인 Markdown 링크와 지원하는 제목 앵커를 확인한다. 이미지·참조형 링크·HTML 링크는 검사하지 않는다. 보존한 Issue 양식의 필드·기본 문자열 구성과 PR 안내의 미리 체크된 체크박스를 검사하지만, 실제 Issue 등록·PR 연결·본문 형식은 강제하지 않는다. 전체 YAML 문법이나 GitHub 화면의 동작도 검증하지 않는다. 양식·CI YAML 변경 시 별도로 구문을 확인하고 GitHub 적용 결과도 확인한다.

PR에는 실제 검증 결과와 필요한 한계를 간단히 설명한다. `통과`, `실패`, `미실행`, `해당 없음`을 구분하고 뒤의 두 경우는 이유를 적는다. CI 결과도 실제 실행을 확인한 경우에만 통과로 기록한다. 별도 AC 추적 표는 요구하지 않는다.

**다음 단계 조건:** 완료 조건별 검증 근거가 있고 필요한 테스트가 통과했다. 필요한 검증이 실패했거나 미실행이면 Ready for review/병합 준비 완료로 보고하지 않고 Draft PR에서 상태와 해결 계획을 명시한다.

## 5. Pull Request

담당자는 diff와 미추적 파일을 검토하고 의도한 파일만 Commit·Push한 뒤 PR을 생성한다. 변경 목적·핵심 변경·검증 결과를 작업 규모에 맞게 간단히 설명한다. 미완료 작업은 Draft로 연다. Codex는 요청이 있을 때만 별도 PR 본문 초안을 작성한다.

Issue 연결·정형 문서·체크리스트는 필수가 아니다. [PR 안내](../.github/pull_request_template.md)는 선택적으로 참고한다. 관련 Issue를 연결할 경우 완료할 Issue에는 `Closes #번호`, 일부 작업이나 참조에는 `Refs #번호`를 사용할 수 있다. 검토에 필요한 위험·미완료 작업·미실행 검증과 중요한 ADR이 있으면 함께 알린다.

체크박스를 사용하는 경우 실제 확인한 항목만 선택한다. 미실행 항목을 통과로 바꾸거나 체크박스를 일괄 선택하지 않는다.

**다음 단계 조건:** PR 범위가 합의한 작업과 일치하고 필요한 변경·검증 정보를 전달했다. 병합 준비가 됐다고 보고하려면 필요한 CI 결과도 확인한다. 리뷰 요청 시 검토할 최신 변경과 기준 브랜치를 식별한다.

## 6. Review

팀원은 PR의 최신 변경과 검증 결과를 리뷰한다. Codex 리뷰를 요청할 때는 합의한 작업 범위, PR diff 또는 로컬 기준 브랜치, 테스트 결과를 전달한다. 관련 Issue가 있으면 함께 제공한다. 로컬 예시는 다음과 같다.

> 이번 담당 작업의 목표·완료 조건과 main 대비 최신 diff를 리뷰해 줘. 결함·회귀·테스트 공백·문서/ADR 불일치를 우선 확인하고, 발견 사항은 심각도·파일 위치·발생 조건·영향으로 정리해 줘. 리뷰 범위와 미실행 검증도 밝혀 줘. 파일 수정과 원격 리뷰 게시는 하지 마.

Codex는 계획이 아닌 최종 변경을 검토한다. 사용자는 차단 의견을 해결하거나 근거와 함께 수용할 위험을 기록한다. 수정한 검증을 다시 실행하고, 새 변경이 있으면 해당 변경을 다시 리뷰한다. 코멘트 해결 표시만으로 결함 해결을 주장하지 않는다.

**다음 단계 조건:** 최신 변경의 리뷰가 완료됐고 차단 결함이 해결됐으며, 남은 위험을 사용자가 이해·수용했다. Codex의 로컬 리뷰는 GitHub의 필수 승인 리뷰를 대신하지 않는다.

## 7. Merge

병합 판단과 실행은 팀의 담당자가 한다. 최신 변경의 완료 조건 충족, 필요한 검사 성공, 문서·ADR 정합성, 리뷰 의견 처리, 남은 위험을 확인한 뒤 `main`에 병합한다. Codex는 별도 승인 없이 병합하지 않는다.

필요한 미완료 작업이 있으면 병합하지 않는다. 별도로 합의한 후속 작업은 팀이 사용하는 방식으로 추적하고 원래 완료 조건을 조용히 축소하지 않는다. 병합 뒤 담당자는 기준 브랜치를 동기화하고 관련 Issue가 있을 때만 종료 여부를 확인한다. 브랜치 삭제도 사용자 판단으로 수행한다.

## Architecture Decisions

중요한 기술 선택이 실제로 필요할 때 기존 번호에 이어 `docs/decisions/NNNN-short-title.md`를 만든다. 빈 ADR 폴더나 개발 절차 자체에 대한 형식적 ADR은 만들지 않는다. 다음 형식을 사용한다.

```md
# NNNN · 결정 제목

- Status: Proposed / Accepted / Superseded
- Date: YYYY-MM-DD
- Related Work: 작업 설명·논의 또는 PR 링크 (관련 Issue가 있으면 함께 연결)
- Approval: 사용자 승인 근거와 날짜 (미승인 시 미승인)
- Supersedes: 이전 ADR 경로 (있는 경우)

## Context
문제, 요구사항, 제약, 결정이 필요한 이유

## Decision
선택한 방향과 적용 범위

## Alternatives
검토한 대안과 채택하지 않은 이유

## Trade-offs
이점, 비용, 위험과 감수한 타협점

## Consequences
구현·테스트·운영·마이그레이션에 미치는 영향과 후속 작업
```

중요한 변경은 사용자 승인 전까지 `Proposed`다. 승인된 ADR은 본문을 보존하며, 결정 변경은 새 ADR에서 이전 결정을 참조하거나 대체한다. 이전 ADR에는 상태와 대체 ADR 링크만 갱신한다. ADR은 결정의 이유이고 현재 동작은 관련 설계·API 문서에서 관리한다.

## 최초 적용과 GitHub 설정

아래는 팀이 필요에 따라 검토할 설정 안내다. 저장소 파일 작성만으로 서버 설정이 활성화되지는 않으며, 이번 개발 절차 변경에서 원격 상태를 확인하거나 변경하지 않았다. 필수 승인 수 등은 별도 팀 합의로 정한다.

1. 워크플로 파일을 Commit·Push하고 리뷰를 거쳐 기본 브랜치에 반영한다. 제공한 Issue 양식·PR 안내는 선택 도구로 사용한다.
2. Actions 실행이 허용되는지 확인한다. PR 또는 수동 실행으로 `repository-checks` 결과를 한 번 확인한다. 로컬 검사와 원격 CI 결과를 구분한다.
3. `main`의 브랜치 보호 규칙 또는 ruleset에서 PR·필요한 상태 검사·대화 해결 요구와 관리자 우회·force push·브랜치 삭제 정책을 검토한다. [GitHub 브랜치 보호 문서](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
4. 팀원 승인 리뷰의 필수 수와 새 변경 시 승인 해제 여부를 정할 수 있다. Codex 리뷰와 팀원의 승인은 구분한다. [GitHub 승인 리뷰 문서](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)
5. 실제 담당 작업의 브랜치 → 기획·구현 → 검사 → PR → 리뷰·병합 흐름에서 설정이 기대대로 작동하는지 확인한다. 불필요한 테스트용 파일을 병합하지 않는다.

브랜치 보호 사용 가능 여부는 저장소 공개 범위와 GitHub 요금제에 따라 다르다. 사용할 수 없으면 PR과 검토 절차를 수동으로 준수하되, 서버가 강제한다고 보고하지 않는다. [지원 범위](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#who-can-use-this-feature)

현재 CI 정의에는 `repository-checks`의 문서·양식 검사와 `memory-tests`의 Python 3.11/3.14 오프라인 테스트·가상 데모가 있다. 계획의 적절성, 승인, 테스트의 충분성과 실제 연구 효과는 팀원과 Codex의 검토로 확인한다. 새 제품 기능이 추가되면 그 스택의 검사·테스트를 같은 개발 절차에 통합한다.
