이번 요구는 구분합니다.

LUMI는 평소 취향과 지금 필요한 옷의 조건을 함께 반영하는 패션 추천 에이전트 연구 프로젝트입니다. 사용자는 처음부터 모든 조건을 설명하지 않아도, 대화와 이미지 비교로 원하는 스타일을 구체화합니다.

구현됨 · 로컬 프로토타입

입력 접수 → 기억 확인 → 목표 생성 → 상품 검색·비교 → 피드백 → 종료 후 장기 활용 동의까지 코드가 연결되어 있습니다.

실제 품질·효과는 별도 검증

현재 근거는 합성 입력·가상 모델·SQLite·브라우저 검사입니다. 실제 상품 수집, 한국어 해석 품질, 추천 품질과 사용자 연구는 남아 있습니다.

어떤 문제를 푸는가

마음에 드는 옷을 알아보는 것과, 그 옷을 찾을 조건을 말하는 것은 다릅니다. “편한데 단정한 바지”처럼 느낌으로 시작할 수도 있고, 평소 와이드핏을 좋아해도 발표 날에는 슬림핏이 필요할 수 있습니다.

LUMI는 대화로 조건을 받고, 이미지로 해석을 확인하며, 기억의 적용 범위를 나누는 방식으로 이 과정을 돕습니다. 시스템이 추정한 이유를 사용자 취향으로 바로 확정하지 않고, 최종 선택과 기억의 이후 활용은 사용자가 결정합니다.

사용 흐름 따라가기

한 요청은 아래 순서로 이어집니다. 이미지 선택과 재탐색은 반복할 수 있고, 모든 속성을 채우지 않아도 종료할 수 있습니다.

  1. 1원하는 옷 이야기하기

    새 요청에 아이템과 상황을 입력합니다. 온보딩에서 평소 취향을 먼저 말하거나 바로 시작할 수도 있습니다.

  2. 2이해한 내용 확인하기

    기억할 문장과 적용 대상을 확인합니다. 문장의 의미와 사전 속성 연결은 구분해 검토합니다.

  3. 3상품 이미지 비교하기

    직접 말한 조건은 유지하고, 추상적인 요구를 어떤 PI 값으로 구현할지 비교합니다.

  4. 4선택과 수정 반영하기

    선택과 선택 사항인 이유를 함께 제출합니다. 글만 보내거나 없음·모르겠음으로 답할 수도 있습니다.

  5. 5결정하거나 탐색 끝내기

    조건을 고쳐 더 보거나 상품을 결정합니다. 상품을 고르지 않고 종료할 수도 있습니다.

  6. 6다음 활용을 따로 정하기

    종료 요약에서 기존 후보를 확인하고, 재사용할 항목과 동의를 직접 선택합니다. 저장 없이 끝낼 수 있습니다.

내부 처리
발화 근거를 접수하고 기억 후보를 만듭니다. 네이비·슬랙스는 직접 PI, 편안함은 FEA 연결 후보로 구분합니다.
기억 상태
아직 확인하지 않은 단기 후보입니다. 장기 기억은 생성되지 않습니다.

“편안함 = Wide”는 아직 사실도, 확정된 사용자 조건도 아닙니다.

실제 탐색 화면은 큰 화면에서 왼쪽에 상품·이미지, 오른쪽에 대화를 배치합니다. 반영 정보 상세에는 이번 요청·참고한 평소 취향·확인 중인 해석을 구분하며, 내부 Feature Map 전체를 기본 화면에 펼치지 않습니다.

조건을 이해하는 방식: PI, FEA, 연결 가설

Feature Map은 원하는 옷과 공급된 상품을 같은 속성 이름으로 비교하기 위한 표현입니다. 사용자의 목표와 실제 상품은 역할이 다릅니다.

사용자 목표 Map

원하는 상품의 PI + FEA 요구를 담습니다. FEA를 어떤 PI로 구현할지에 대한 연결 가설은 별도로 관리합니다. 각 값에는 대상·조건·근거와 지정/추론 상태가 붙습니다.

상품 Map

공급 자료에서 확인한 PI를 담습니다. 사용자의 바람이 아닌 상품의 관찰 정보입니다. 현재 소비자 경로는 상품별 FEA 30개를 채워 비교하는 구조가 아닙니다.

FEA는 “어떤 옷인가”보다 “왜 원하는가”를 정리합니다

Functional 8개는 보온·신축성·편안함 같은 기능 요구, Expressive 13개는 업무복·하객복 같은 표현·상황 요구, Aesthetic 9개는 실루엣 연출·다른 아이템과의 매칭 같은 미적 요구입니다. 합계 30개 태그이며 PI와 합쳐 37개의 동등한 상품 속성으로 취급하지 않습니다.

직접 조건과 가설의 차이
“네이비 슬랙스를 편하게” → Color=Navy·Type=Slacks는 직접 PI입니다. “편안함(Ease)을 Fit=Wide로 구현하면 좋을까?”는 확인할 가설입니다. 가설은 확정 필터에 넣지 않고, Navy/Wide와 Navy/Straight의 비교로 이번 해석을 확인합니다.

현 가설 구현은 Type·Color·Fit·Detail 중 한 값을 선호하는 soft 제안입니다. 같은 축에 직접 PI 조건이 있으면 그 축의 가설은 제외합니다. “편안함”과 Wide는 일대일 정답 관계가 아니며, 사진에서 Wide를 골랐어도 실제 착용 편안함이 입증되지는 않습니다.

모르는 목표 값은 미정으로 남깁니다. 미정, 추론, 지정, 상관없음, 비적용, 미지원, 상충을 구분하며, 값과 상태를 임의로 채우지 않습니다. “빈티지한 느낌”처럼 사전에 정확히 연결되지 않는 표현도 원래 문장과 근거로 보존할 수 있습니다.

현재 지원 범위는 여성 바지 자료를 바탕으로 한 Pants 매핑입니다. 프로젝트의 연구 목표는 패션 아이템·코디 탐색이지만, 현재 사전 실행이 상의·아우터·드레스나 완성 코디 추천까지 지원한다는 뜻은 아닙니다.

기억은 내용·적용 범위·동의를 함께 저장합니다

기억의 정본은 속성값 하나가 아닌 최소 자연어 내용 + 원래 근거 + 대상·상황 + 확인·동의 상태입니다. PI/FEA 연결은 그 위에 붙는 선택적 해석입니다. “이 문장이 맞다”와 “이 문장을 이 속성으로 해석해도 된다”는 구분합니다.

구분단기 기억장기 기억
무엇을 담나이번 요청의 요구·상황·선택·수정·해석 후보내용 확인과 별도 재사용 동의를 받은 취향
어디에 쓰나같은 요청 안에서만. 미확인 후보는 확정 조건에서 제외대상·상황·기간이 맞는 다음 요청에서 참고
언제 생기나입력·피드백을 접수하고 후보를 만들 때소비자 서비스의 세션 종료 후 요약에서 동의할 때
무엇이 아닌가새 요청으로 자동 복사되는 임시 취향반복 선택·상품 확정·내용 확인만으로 자동 생성되는 취향

평소 취향과 이번 예외가 충돌하면

  1. 평소 취향이미 확인·동의한 장기 기억: “바지는 Navy와 Wide를 선호한다.”
  2. 이번 발표 요청“이번 발표에는 Slim으로.” → 이번 목표는 Navy + Slim. 충돌하는 Wide만 이번 검색에서 제외하고 장기 원본은 보존합니다.
  3. 새 일상 요청발표 전용 Slim은 넘어오지 않습니다. 유효한 평소 Navy + Wide를 다시 참고합니다. 같은 요청을 재개하는 경우와 구분합니다.

네 가지 결정을 분리합니다

내용 확인은 시스템이 정리한 문장이 맞다는 결정, 속성 연결 확인(binding)은 그 문장을 어떤 PI/FEA로 해석할지에 대한 결정입니다. 상품의 최종 선택은 이번 탐색 결과의 결정이고, 이후 활용 동의는 확인한 내용을 다음에도 사용할 수 있다는 별도 결정입니다.

장기 활용 항목과 동의 체크는 기본 해제입니다. 종료 전에 접수·해석된 후보는 종료 요약에서 확인할 수 있지만, 종료 후 새 입력이나 늦은 모델 추출 결과를 더하지 않습니다. 요청 전용 slot이 붙은 항목을 자동으로 일반 취향으로 넓히지 않으며, 현 재사용 목록에서도 제외합니다.

기억 항목과 근거에는 구체적으로 무엇이 남나요?

항목·사용자·요청 ID, 버전, 문장, 대상 옷과 slot, 상황 조건, 긍정/회피·필수/선호, 적용·보관 시한, 직접 발화/추론의 출처, 근거 참조, 확인 이벤트, 동의한 내용·범위 snapshot, 교체·파생 관계가 연결됩니다. 전체 채팅을 그대로 장기 취향으로 저장하는 방식이 아닙니다.

화면 뒤에서는 이렇게 처리합니다

브라우저 → 로컬 HTTP 서버 → ConsumerService가 한 요청을 조율합니다. 모델은 후보를 제안하고, Python 코드가 근거·상태·범위를 검증하며 SQLite가 저장을 맡습니다. 아래 단계는 별도 AI 에이전트 일곱 개를 뜻하지 않습니다.

  1. 1화면에서 명령 전송

    시작·선택·수정·확인·종료를 명령으로 보냅니다. 서버는 현재 화면에 제시한 내용과 버전을 확인합니다. 브라우저가 임의의 동의·저장 명령을 직접 만들게 하지 않습니다.

    consumer.html / consumer.js / consumer-http.js → consumer.py
  2. 2근거 접수·후보 추출

    실제 발화·선택을 먼저 접수합니다. 모델은 기억 문장·대상·상황과 선택적 PI/FEA 연결을 제안하고, 코드는 인용·허용값·참조를 검사해 미확인 후보로 저장합니다.

    app.py: ConsumerService._extract → model_io.py / llm.py
  3. 3확인·저장 상태 관리

    사용자에게 보여준 내용의 확인 이벤트를 받아 활성화합니다. 근거·기억·binding·가설·관계·동의 snapshot을 버전과 함께 관리합니다.

    store.py / store_v1.py / store_feedback.py → 메모리 SQLite
  4. 4관련 기억 조회

    현재 요청에 쓸 수 있는 기억을 먼저 가립니다. 사용자·확인·동의·기간·대상·상황을 검사한 뒤 구조와 키워드로 관련 후보와 근거를 묶습니다. 관련성이 높아도 동의·범위를 넘어갈 수 없습니다.

    retrieval.py: build_context_v1
  5. 5목표·연결 가설 생성

    직접 PI와 확인한 조건을 보존해 목표를 만들고 FEA→PI 가설을 분리합니다. 출처 없는 값, 사전 밖 값, 추론을 필수 조건으로 바꾸는 제안은 적용하지 않습니다.

    inference.py: infer_v1 / hypotheses.py: infer_with_hypotheses
  6. 6검색·비교 발행

    공급 상품 PI로 필수 조건을 먼저 검사한 뒤 선호에 따라 순서를 정합니다. 확인된 대안이 있으면 가설 비교를 구성하고 상품·이미지·후보 묶음 버전을 고정해 발행합니다.

    catalog.py / product_search.py / comparison.py / hypotheses.py
  7. 7피드백·재탐색

    선택과 선택 사항인 이유를 같은 근거 묶음으로 접수합니다. 필요한 확인을 거친 뒤 이번 조건을 갱신해 4~6단계를 반복합니다. 종료 후에만 별도 장기 활용 동의를 받습니다.

    app.py: command / hypotheses.py: respond_comparison
핵심 경계: 모델이 “이 사용자는 Wide를 좋아한다”고 출력해도 그것만으로 DB의 확정 상태나 장기 동의가 생기지 않습니다. 모델 출력·사용자 확인·저장 권한을 코드에서 분리합니다.
실행 구성과 인터페이스 보기

실행 의존성은 Python 3.11+ 표준 라이브러리입니다. 화면은 HTML/CSS/JavaScript이며, 메모리 DB와 상품 DB는 서로 다른 SQLite 파일로 저장소 밖에 둡니다. 로컬 이미지는 별도 외부 디렉터리에서 제공합니다.

  • ConsumerService.state()는 화면 상태, command()는 사용자 명령의 진입점입니다.
  • HTTP: GET /api/state, POST /api/command, GET /api/images/{image_id}?version=N.
  • contracts.py가 객체·명령 계약을, registry.py가 속성 사전을 정의합니다.
  • 저장 계약 lumi-memory-v1과 속성 사전 park-2025-source-v1의 버전은 별개입니다.
  • 현재 서비스는 127.0.0.1:8766의 단일 신뢰 테스터용입니다. 공개 로그인·다중 사용자 서비스·구매 결제는 구현 범위 밖입니다.

상품 검색과 이미지 비교는 어떻게 다른가

먼저 실제로 공급된 상품을 검색합니다

상품은 출처·수집 시각·제목·설명·메타데이터·이미지 참조·라벨이 있는 JSON/JSONL로 가져옵니다. 현재 크롤러는 없고, 공급 메타데이터의 정확한 사전 값을 정규화해 상품 PI를 만듭니다. 이미지에서 모든 속성을 자동 추출하는 완성된 비전 파이프라인도 아닙니다.

검색은 필수 조건 필터 → 선호 일치에 따른 정렬 순서입니다. 미확인·추정·상충한 상품 값은 확인된 필수 조건 충족으로 보지 않습니다. 초기 정렬은 soft 조건의 일치를 사용하는 기준 구현이며 학습된 추천 정확도를 뜻하지 않습니다. 적합 상품이 없으면 조건 유지·조정·종료를 제시하고 자동으로 조건을 풀지 않습니다.

그다음, 확인할 가설에 맞는 비교를 구성합니다

“편안함에는 Wide가 맞을까?”를 묻기 위해 확인된 Wide 상품과 확인된 다른 핏 상품을 찾습니다. 핏을 모르는 상품은 “Wide가 아닌 상품”이 아닙니다. 직접 조건은 그대로 지키고, 상품·이미지 중복을 줄이며, 가능한 범위에서 다른 속성의 차이를 줄입니다.

대안을 확보하지 못하면 가설을 확정하지 않고 일반 탐색을 유지합니다. 코드의 기본 3개·세밀 비교 2개·두 축 비교 4개는 파일럿 가정이며, 없는 상품 조합을 만들거나 숫자를 맞추려고 부적합 상품을 채우지 않습니다.

응답시스템이 반영하는 것자동 확정하지 않는 것
명확한 가설 비교에서 선택만서버가 미리 표시한 해당 PI 해석을 확인. 추론 출처와 soft 강도는 유지실제 편안함·모든 상품 속성·지속 취향·장기 동의
선택 + 이유·수정 텍스트선택·텍스트를 함께 해석해 독립 기억 후보 생성 → 내용·속성 연결 확인텍스트와 충돌할 수 있는 원래 PI 가설의 즉시 확정
일반 이미지·부분 선택선택한 대상과 실제 텍스트의 근거를 보존하고 필요한 해석을 확인이미지의 모든 속성 선호·미선택 상품의 비선호
없음 / 모르겠음 / 건너뛰기각 반응을 구분하고 해당 해석을 미확인으로 유지전 속성 비선호·질문에 대한 동의
이미지는 성능 검증이 아닙니다. 필수 보온·방수·편안함을 현재 PI만으로 확인할 수 없으면 미해결로 남깁니다. 비교는 계속할 수 있지만, 현재 소비자 서비스는 필수 FEA가 해결·조정되기 전 최종 상품 선택을 보류합니다.

소비자 화면은 준비된 로컬 이미지 파일을 제공합니다. 원격 URL 참조를 가져와도 서버가 자동 다운로드·표시하지 않으며, 없거나 원격인 이미지는 미제공으로 표시합니다.

실패하거나 정보가 바뀌면

비동기로 모델을 기다리는 동안 사용자가 수정·삭제·종료할 수 있습니다. 그래서 모델 응답을 받았다는 이유만으로 반영하지 않고, 적용 직전 요청·기억·프로필·사전·색인·상품·이미지 버전을 다시 검사합니다.

상황현재 처리
입력은 받았지만 해석 실패근거는 보존하고 interpretation_pending으로 표시합니다. 같은 피드백을 재처리하며 원문·선택을 중복 생성하지 않습니다.
오래된 응답·카드수정·철회·삭제·만료·종료 뒤의 늦은 응답은 반영하지 않습니다. stale 상태와 재탐색을 사용합니다.
조회·필수 근거 부족blocked로 보류합니다. 실제 검색 결과가 0건인 no_results와 구분하고 필수 조건을 잘라내지 않습니다.
모델 오류·시간 초과오류를 표시합니다. 다른 모델이나 규칙 엔진의 성공으로 자동 대체하지 않습니다.
같은 명령 재전송동일 batch·본문은 최초 처리 결과를 재사용하고, 같은 ID의 다른 본문은 충돌로 거부합니다. 한 batch는 전체 성공 또는 rollback입니다.
철회·삭제철회는 즉시 조회 제외. 삭제는 관련 근거 부분·복제/파생 항목·비교 자료·색인 등을 정리하며 실패를 완료로 표시하지 않습니다.
재시작·새 요청같은 요청의 최소 근거·상태를 DB에서 복원합니다. 새 요청에는 이전 단기 기억·가설을 자동 이월하지 않습니다.

요청 삭제와 장기 기억 삭제도 구분합니다

요청을 삭제해도 별도로 동의한 장기 항목은 동의한 범위의 독립 최소 snapshot으로 남을 수 있습니다. 그 장기 기억 자체를 삭제하면 관련 승격·복제·파생 자료에도 전파합니다. 관리 DB의 삭제는 사용자가 만든 사본·OS 백업·저장매체 전체 소거를 뜻하지 않습니다.

현재 보관 설정과 로컬 HTTP 경계

로컬 프로토타입의 요청 보관은 비활동 30일·생성 90일 중 이른 시한, 활성 장기는 동의 후 365일입니다. 철회·교체 내용은 기존 시한과 비활성 30일 중 이른 시한을 씁니다. 정리는 명시적 prune_expired() 호출이며 예약 실행을 설치하지 않습니다. 이는 최종 서비스 보관 정책을 확정한 것이 아닙니다.

HTTP는 루프백·Host/동일 Origin·JSON·24,000바이트 입력 상한과 패키지 자산 allowlist를 검사합니다. 이미지 경로는 설정한 외부 root 안의 파일로 제한합니다. 소비자 화면에서 사용자 ID·provider·임의 파일 경로·StoreAction을 받지 않습니다.

연구에서는 무엇을 확인하나

LUMI는 구현 자체보다 사용자가 취향을 표현하고 추천을 통제하는 경험을 평가하려는 HCI 프로젝트입니다. 아래는 중간보고서의 계획이며 수행 결과가 아닙니다.

RQ1
장·단기 기억과 확인·수정을 제공할 때, 한 세션의 두 요청에서 통제감과 최종 코디 적합성(취향 반영·상황 적합성)이 Baseline보다 나아지는가? 기억 충실도는 LUMI 전용 평가입니다.
RQ2
이미지 선택·선택적 확인 질문·자유 입력을 통해 표현 부담을 줄이고, 스타일 구체화와 이해받는 느낌을 높일 수 있는가?
참여자·조건
온라인 패션 구매 경험이 있는 성인 20~24명의 참가자 내 비교. LUMI와 ChatGPT + Musinsa Baseline의 순서·상황을 교차 균형화합니다.
과제
조건마다 같은 세션에서 자유 요청 1회 + 상황 요청 1회. LUMI는 평소 취향 등록과 이후 활용할 항목 선택을 포함합니다.
측정·분석
조건 간 대응 문항, LUMI 전용 문항, 두 조건의 Raw NASA-TLX, LUMI의 SUS, 개방형 응답. 대응 비교·중립점 비교·RQ별 Holm 보정과 효과크기를 구분합니다.

Baseline은 계획상 ChatGPT 메모리·개인화·이미지 생성·웹 검색을 끄고, Musinsa는 비로그인 검색·필터만 사용합니다. 이는 현재 외부 서비스 설정을 검증했다는 뜻이 아닙니다.

이 설계는 메모리·이미지·질문의 개별 효과를 각각 분리하는 실험이 아닙니다. 일시 요구가 다음 요청에 넘어가지 않는 동작은 코드로 검사하지만, 추가 요청이 필요한 해당 항목은 보고서의 현 사용자 연구 측정에서 제외되어 있습니다. 아직 사용자 효과나 추천 정확도 향상을 주장할 수 없습니다.

hard는 반드시 지킬 제약, soft는 선호·순위 판단입니다. 가설의 soft 선호를 자동으로 hard로 승격하지 않습니다.
