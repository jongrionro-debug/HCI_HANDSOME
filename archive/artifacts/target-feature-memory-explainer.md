사용자의 취향과 이번 상황을 기억합니다. 그 기억으로 LLM이 원하는 옷의 목표 조건을 제안합니다.

## A 우리가 만드는 것은 무엇인가요?

**우리의 작업은 LLM에 전달할 기억과 맥락을 만드는 것입니다.**

```flow
장단기 기억 -> LLM: 맥락과 Feature Map 전달
LLM -> 목표 조건: 값과 근거를 제안
```

Feature Map은 어떤 속성과 값을 사용할지 알려주는 사전입니다.
맥락은 그 값 중 사용자가 무엇을 원하는지 판단할 근거입니다.
이 페이지는 계획 설명입니다. 아래 예시는 실제 실행 결과가 아닙니다.
## B 장기와 단기는 무엇이 다른가요?

가상의 사용자가 기본 취향을 확인하고 저장했다고 가정합니다.
이번에는 고객 미팅에서 입을 바지를 요청합니다.

| 기억 | 사용자의 말 | 적용 범위 |
|---|---|---|
| 장기 취향 | 평소 바지는 여유핏인 Relaxed를 선호해요 | 이후 요청에도 참고 |
| 장기 취향 | 바지는 네이비를 좋아해요 | 이후 요청에도 참고 |
| 단기 조건 | 이번 바지는 Slim으로 입고 싶어요 | 이번 요청에 적용 |
| 단기 상황 | 고객 미팅에서 입을 옷이에요 | 이번 요청에 적용 |

**이번 목표는 Slim입니다. 기본 Relaxed 취향은 유지합니다.**
새 요청에는 이전의 Slim 조건을 자동으로 가져오지 않습니다.
장기 저장에는 내용 확인과 이후 활용 동의가 필요합니다.

## C 기억 하나에는 무엇을 담나요?

한 기억에는 독립적으로 수정할 수 있는 한 가지 뜻을 담습니다.

| 항목 | 예시 |
|---|---|
| 내용 | 이번 바지는 Slim을 원함 |
| 대상 | 바지 |
| 선호와 강도 | Slim 선호. 꼭 지켜야 하는지는 별도로 기록 |
| 상황과 기간 | 이번 고객 미팅 요청 |
| 적용 범위 | 단기 |
| 근거 | 사용자의 현재 발화와 확인한 내용 |

**대상을 함께 기억해야 합니다.**
흰 셔츠와 네이비 재킷은 서로 다른 옷의 색 조건입니다.
두 조건을 한 옷의 색상 충돌로 처리하지 않습니다.

## D LLM에는 어떤 기억을 주나요?

context는 LLM에 전달하는 **이번 요청의 맥락 묶음**입니다.
대화 전체를 그대로 보내는 대신 쓸 수 있는 정보를 고릅니다.

```flow
현재 요청과 대상 -> 유효한 기억: 소유권과 기간 확인
유효한 기억 -> 이번에 쓸 조건: 대상별 예외와 충돌 처리
이번에 쓸 조건 -> *맥락 묶음: 의미와 근거 보존
```

| 맥락 묶음의 내용 | 이번 바지 예시 |
|---|---|
| 목표와 대상 | 고객 미팅용 바지 |
| 사용할 기본 취향 | Navy 선호 |
| 이번 조건 | Slim 선호 |
| 직접 대응한 값 | Visual Fit은 Slim |
| 미정 사항 | 소재와 혼용률은 아직 모름 |
| 근거 | 사용한 기억의 식별자와 버전 |

이번에 대체된 기본 핏은 실행 조건에서 뺍니다.
미확인 후보와 철회·삭제·만료된 기억도 제외합니다.
같은 대상의 조건이 해결되지 않으면 질문으로 남깁니다.

## E Feature 값은 어떻게 정하나요?

**명확한 값은 보존하고, 해석이 필요한 값은 제안합니다.**

| 입력 근거 | 목표 Feature와 값 | 처리 |
|---|---|---|
| 이번 바지는 Slim | Visual Fit = Slim | 명시값 보존 |
| 저장된 네이비 선호 | Primary Color = Navy | 기억 활용 |
| 고객 미팅에서 입을 옷 | Formality Level = 3~4 | 추론 제안 예시 |
| 혼용률 정보 없음 | Fiber Composition | 미정 유지 |

격식 3~4는 설명용 예시입니다. 고객 미팅의 고정 정답이 아닙니다.
LLM의 추론에는 근거와 짧은 이유를 붙입니다.
추론한 값은 사용자가 확정한 값과 구분합니다.

```callout info 값이 하나일 필요는 없습니다
검정 회피는 Black 제외 조건입니다.
슬림 또는 레귤러 허용은 두 값의 집합입니다.
격식 3~4 허용은 범위 조건입니다.
```

핏 선택만으로 바짓단 모양·색·소재 선호까지 확정하지 않습니다.
아이템의 격식과 코디 전체의 격식도 각각 다룹니다.
## F 추론한 값은 언제 기억이 되나요?

LLM의 제안은 검증을 거쳐 사용자에게 보여줍니다.
허용값, 적용 대상, 필수 조건, 근거를 확인합니다.
시스템은 사용자가 명시한 조건을 결과에 보존합니다.

```flow
LLM 제안 -> 검증: 값과 근거 확인
검증 -> 사용자 확인: 목표 조건 보여주기
사용자 확인 -> 이번 요청 반영: 새 확인 근거
이번 요청 반영 -> 장기 활용 선택: 항목별 동의
장기 활용 선택 -> [(장기 기억)]: 선택한 항목만 저장
```

**모델 제안만으로 장기 기억을 바꾸지 않습니다.**
같은 대상의 필수 조건이 충돌하면 사용자에게 확인합니다.
틀린 값과 근거 없는 확정값은 결과에 적용하지 않습니다.

## G 무엇부터 구현하나요?

```timeline v
1 | Feature 사전 | 속성·허용값·적용 대상을 정리합니다.
2 | 기억 연결 | 기억의 뜻을 정확한 속성과 대상에 연결합니다.
3 | 맥락 조립 | 기본 취향·이번 조건·미정 사항·근거를 묶습니다.
4 | 가상 검증 | 예외·충돌·새 요청·삭제 사례를 확인합니다.
5 | LLM 연결 | 모델을 선택한 뒤 실제 해석 품질을 평가합니다.
```

사전은 아이템 속성 65개와 코디 속성 9개를 담는 계획입니다.
첫 동작 검증은 명시된 단일 아이템으로 시작합니다.
핏·색·패턴·스타일·분위기·격식을 먼저 확인합니다.

| 현재 구분 | 상태 |
|---|---|
| 기존 메모리의 동의·범위·저장 규칙 | ok 승인된 설계 |
| Feature 연결과 맥락·출력 계약 | warn 검토용 Proposed 계획 |
| 실행 코드와 실제 LLM 품질 | 아직 구현·검증 전 |

전체 계획에는 속성별 연결표와 입력·출력 예시가 있습니다.
