> 평소에는 여유 있는 핏을 좋아하는 사람이 오늘 발표에는 슬림 핏을 원합니다. 오늘의 선택을, 내일도 기억해야 할까요?

## 1. 오늘의 선택이 평소 취향을 바꿀까?
```flow LR
*기본 취향 -> 오늘 추천: 평소 여유 핏
*이번 요청 -> 오늘 추천: 오늘 발표 · 슬림 핏 우선
기본 취향 -> 새 요청: 기본 취향 유지
새 요청 -> 다음 추천: 이전 단기 자동 이월 없음
기본 취향 -> 다음 추천: 여유 핏을 다시 기본으로
```
> 먼저 [기본 취향]을 보죠. 사용자가 이미 확인하고 저장한 여유 핏은, 평소 추천의 출발점입니다.
> 그런데 [이번 요청]에는 발표라는 상황이 붙습니다. 오늘만 슬림하게 입겠다는 명시적인 조건이, 같은 핏 항목의 기본값을 일시적으로 대신합니다.
> 이때 기본 취향 자체를 고치지는 않습니다. [새 요청]을 시작하면, 저장된 여유 핏은 그대로 남아 있습니다.
> [새 요청]은 새로운 경계입니다. 앞선 발표 요청의 임시 조건을, 다음 요청에 자동으로 가져오지 않습니다.
> 그래서 [다음 추천]은 다시 여유 핏을 기본으로 시작합니다. 같은 요청을 재개할 때는, 남아 있는 조건의 기간과 상황을 다시 확인합니다.

## 2. 기억을 작은 주장으로 쪼개기
```tree
기억 한 항목
  내용과 속성 | 여유 핏 · 부정과 강도 보존
  적용 범위 | 장기 또는 요청별 단기
  조건과 기간 | 고객 미팅 때 · 오늘만
  확인과 근거 | 현재 발화 · 선택한 이미지 요소
```
> 그럼 기억의 단위는 무엇일까요? [기억 한 항목]은 사용자가 따로 확인하고, 수정하고, 활용을 철회할 수 있는 하나의 주장입니다.
> [내용과 속성]에는 사용자의 문장과 최소한의 구조를 함께 둡니다. 여유 핏을 좋아한다는 말과, 여유 핏을 피한다는 말을 섞지 않습니다.
> [적용 범위]는 장기와 요청별 단기로 나눕니다. 장기로 쓰려면 그 항목에 대한 내용 확인과 이후 활용 동의가 필요합니다.
> [조건과 기간]도 기억의 일부입니다. 고객 미팅 때 정장 느낌을 피한다는 조건은, 모든 상황에서 정장을 싫어한다는 뜻이 아닙니다.
> [확인과 근거]는 해석이 어디서 왔는지를 연결합니다. 이미지에서 핏만 골랐다면, 색과 소재까지 좋아한다고 확정하지 않습니다.

## 3. 맞아요와 다음에도 써 주세요
```flow LR
이번 요청 -> 내용 확인: 해석 확인
내용 확인 -> 이번 요청: 맞아요 · 이번 적용
내용 확인 -> 항목별 저장 선택: 내용·조건·기간
항목별 저장 선택 -> 기본 취향: 이후 활용 동의
항목별 저장 선택 -> 이번 요청: 닫기·미선택
```
> 이제 [내용 확인]을 봅시다. 시스템이 해석한 핏이 맞는지 확인하는 단계입니다. 아직 미래의 활용을 허락한 것은 아닙니다.
> 내용 질문에 맞아요라고 답하면, 확인한 조건을 [이번 요청]에 사용할 수 있습니다. 반복해서 골랐다는 이유만으로 장기 기억이 되지는 않습니다.
> [항목별 저장 선택]에서는 다음에도 쓸 문장과 조건, 기간을 보여 줍니다. 체크는 처음에 비워 두고, 기억해 달라는 대상이 모호하면 질문합니다.
> 사용자가 항목의 내용과 이후 활용에 명시적으로 동의하면, [기본 취향]에 저장할 수 있습니다. 대화 중 저장도 같은 계약을 따릅니다.
> 선택하지 않거나 창을 닫으면, [이번 요청]의 조건으로만 남습니다. 처음부터 취향을 저장하지 않고, 빈 프로필로 시작해도 됩니다.

## 4. 제안에서 저장으로, 저장에서 추천으로
```flow LR
*AI 제안
AI 제안 -> 시스템 검증: 근거·동의
시스템 검증 -> SQLite 저장: 전체 성공·실패
SQLite 저장 -> 문맥 조회: 활용 가능성
문맥 조회 -> 추천 패널: 적용 이유
```
> AI는 [AI 제안]을 만듭니다. 무엇을 의미하는지 추정할 수 있지만, 그 추정만으로 기억을 바꾸지는 못합니다.
> [시스템 검증]은 현재 사용자의 근거와 정확한 동의 대상을 검사합니다. 오래된 응답이나 저장 화면은, 버전이 맞지 않으면 반영하지 않습니다.
> [SQLite 저장]은 후속 구현할 저장 경계입니다. 한 번의 저장에서 고른 항목들은 전부 성공하거나 전부 실패하고, 같은 요청의 재시도는 중복 반영하지 않습니다.
> [문맥 조회]는 기억을 모두 꺼내는 과정이 아닙니다. 사용자와 요청, 상태와 기간, 적용 조건을 먼저 확인하고 관련된 기억을 고릅니다.
> [추천 패널]에는 실제 사용한 항목과 제외한 이유가 연결됩니다. 같은 우선순위에서 충돌하면 질문하고, 조건이 바뀌면 기존 추천에 갱신이 필요하다고 표시합니다.

## 5. 쓰지 않기, 보관하기, 지우기
| 대상·조작 | 추천 활용 | 보관·처리 |
|---|---|---|
| 요청 종료 | 해당 단기 중단 | 비활동 30일·생성 90일 |
| 활성 장기 | 동의 범위만 | 명시 동의 + 365일 |
| 활용 철회 | 즉시 제외 | 비활성 최대 30일 |
| 기록 삭제 | 우선 접근 차단 | 원문·사본·근거·파생·참조 소거 |
| 같은 요청 재개 | 유효 조건 재확인 | 날짜 지난 조건 제외 |
> 요청을 끝내면 단기의 추천 적용을 멈춥니다. 원문은 재개를 위해 제한적으로 보관합니다. 승인된 초기 정책은 비활동 삼십 일, 생성 후 최대 구십 일입니다.
> 활성 장기 기억은 마지막으로 명시적인 활용 동의를 한 날부터 삼백육십오 일입니다. 추천에 다시 썼다고 보관 기간을 늘리지는 않습니다.
> 활용 철회는 즉시 추천에서 빼는 조작입니다. 비활성 내용은 최대 삼십 일만 남길 수 있으며, 원래 보관 시한이 더 이르면 그 시한을 따릅니다.
> 기록 삭제는 원문과 동일 사본, 근거와 파생 데이터, 남은 참조까지 지우는 작업입니다. 삭제에 실패하면 활용 차단을 유지하고, 완료됐다고 표시하지 않습니다.
> 같은 요청을 다시 열어도 지난 날짜를 오늘로 바꾸지 않습니다. 이 기간들은 승인된 초기 설계 정책이며, 현재 서버의 운영이나 법적 기준을 뜻하지 않습니다.

## 6. 설계에서 구현과 연구로
```timeline v
현재 · P0 | 설계 승인 완료 | D01–D12 · 계약·가상 정책 검증 자료
P1 | 계약과 요청 경계 | 새 요청 · 재개 · 시간대 · 입력 근거
P2–P3 | 저장과 조회 | Python과 SQLite · 동의 · 버전 · 충돌
P4–P5 | 보관·삭제·가상 연결 | 실제 DB 검증 · 규칙·가상 어댑터
P6 · 별도 범위 | UI·인증·추천 모델·사용자 연구 | RQ1 사용자 주도성 · RQ2 의도 표현
```
> 지금 완성된 것은 승인된 설계와 구현 계획입니다. 계약과 가상 정책을 검증한 자료가 있으며, 실행 제품은 아직 없습니다.
> 먼저 요청 경계와 입력 근거를 구현합니다. 새로운 요청과 재개를 구분하고, 시간대와 유효 기간을 실제 동작으로 확인합니다.
> 그다음 파이썬과 SQLite로 저장과 조회를 연결합니다. 동의, 버전 충돌, 전체 실패, 같은 요청의 재시도를 실제 데이터베이스에서 검증합니다.
> 이어서 보관과 삭제, 가상 화면 연결을 확인합니다. 현재 가상 검증이 실제 디스크 삭제나 모델의 이미지 이해를 입증한 것은 아닙니다.
> 실제 화면과 인증, 추천 모델과 사용자 연구는 별도 범위입니다. 연구는 사용자 주도성과 의도 표현을 평가하며, 무엇을 기억할지는 사용자가 결정합니다.
