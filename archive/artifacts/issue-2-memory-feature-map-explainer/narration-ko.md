## 00:00 · 기억에서 목표 Feature Map까지

**00:00–00:12**

평소에는 여유 있는 바지를 좋아하지만, 오늘 발표에는 슬림하게 입고 싶다고 해 봅시다. 스타일메이트가 두 조건을 기억하고, 이번에 원하는 옷의 속성으로 바꾸는 과정을 따라가겠습니다.

## 00:13 · 1. 오늘의 예외와 평소 취향

**00:13–00:25 · 강조: 기본 취향**

기본 취향은 사용자가 이후에도 참고하라고 확인한 기억입니다. 여유 있는 핏을 좋아한다는 말과, 그 내용을 앞으로 사용해도 된다는 동의가 함께 있어야 장기로 저장됩니다.

**00:25–00:36 · 강조: 이번 조건**

여기에 이번 조건인 오늘만 슬림하게가 들어옵니다. 평소 취향과 현재 요청의 예외를 따로 두면, 사용자가 원하는 적용 범위를 유지할 수 있습니다.

**00:36–00:45 · 강조: 이번 목표**

같은 바지의 핏에서는 현재 예외를 적용해 이번 목표를 슬림으로 만듭니다. 이 과정에서 장기 기억의 여유 있는 핏을 바꾸지는 않습니다.

**00:45–00:55 · 강조: 다음 요청**

다음 요청은 새로운 요청 번호로 시작합니다. 이전 요청의 임시 조건을 자동으로 가져오지 않으므로, 여유 있는 핏을 다시 기본으로 사용할 수 있습니다.

**00:56–01:07**

이런 원칙을 설계한 것이 이슈 1이고, 저장과 목표 추론을 구현한 것이 이슈 2입니다. 연결된 PR 3은 10월 14일 병합됐지만, 이슈 1은 별도로 열린 상태입니다.

## 01:08 · 2. Feature Map은 무엇을 표현하나

**01:09–01:22**

처음 계획은 아이템 65개와 코디 9개 속성이었지만, 현재 구현은 쇼핑용 17개로 줄였습니다. 사전은 각 속성의 이름과 허용값, 값의 타입과 적용 대상을 정합니다.

**01:22–01:35**

여기서 만드는 Feature Map은 이번에 원하는 옷의 목표 조건입니다. 실제 상품의 사진과 정보를 분석해 얻는 상품 Feature Map은 별도의 과정이며, 현재 추출기는 구현되지 않았습니다.

**01:35–01:48**

예를 들어 편안하게 입고 싶다는 말만으로 원단이나 섬유 혼용률을 확정할 수는 없습니다. 사진에서 핏만 좋다고 선택했다면, 색과 소재까지 좋아한다는 기억으로 확대하지 않습니다.

**01:48–02:01**

스타일과 분위기는 여러 값을 가질 수 있고, 격식은 1부터 5까지 표현합니다. 단정하지만 정장 같지는 않게라는 말의 해석은 모델의 제안이며, 사용자가 이미 확정한 사실과 구분합니다.

**02:02–02:14**

비를 맞아도 되는 옷을 원한다면 방수 기능을 목표로 제안할 수 있습니다. 그 목표만으로 실제 상품의 방수 성능이 확인되는 것은 아니며, 모든 미정 속성을 채울 필요도 없습니다.

## 02:15 · 3. 기억 하나를 저장하는 과정

**02:16–02:29**

각 기억에는 짧은 문장과 속성 값, 선호 방향과 강도, 대상과 조건을 함께 둡니다. 현재 코드는 신뢰된 로컬 호출자가 구조화한 입력과 확인 및 동의 참조를 받아 처리합니다.

**02:29–02:41 · 강조: 단기 후보**

단기 후보는 아직 확인하지 않은 해석이므로 확정 조건에 넣지 않습니다. 내용이 맞다고 확인하면 이번 조건으로 쓸 수 있지만, 앞으로도 사용하라는 동의와는 별개입니다.

**02:41–02:54 · 강조: 장기 기억**

장기 기억에는 확인된 내용과 이후 활용 동의의 근거가 모두 필요합니다. 승격은 확인된 단기에서 새 장기 항목을 만들며, 요청 전용 대상을 지워 동의 범위를 자동으로 넓히지 않습니다.

**02:54–03:08 · 강조: SQLite**

SQLite에는 요청, 기억, 프로필 버전, 처리 결과와 최소 변경 이력을 보관합니다. 전체 대화나 이미지, 모델 응답 원문을 쌓는 대신 적용 기간과 확인 및 동의 참조를 남깁니다.

**03:08–03:23 · 강조: SQLite**

SQLite 저장 계층은 생성, 확인, 승격, 교체, 철회, 삭제를 명령으로 다룹니다. 한 묶음은 전부 성공하거나 되돌리고, 버전 충돌과 같은 명령의 재시도로 인한 중복 반영을 막습니다.

## 03:24 · 4. 저장된 기억을 context로 좁히기

**03:25–03:39 · 강조: 유효 기억**

유효 기억을 고를 때 사용자와 현재 요청, 활성 상태와 내용 확인, 유효 기간을 먼저 검사합니다. 다른 사용자의 기억이나 이전 요청의 단기, 후보와 철회 및 만료 항목은 확정 조건에서 제외합니다.

**03:39–03:52 · 강조: 대상별 조건**

대상별 조건을 먼저 나누면 흰 셔츠와 네이비 재킷이 충돌하지 않습니다. 미팅일 때만 적용하는 취향도 그 대상의 확인된 상황과 대조하고, 조건을 판단할 수 없으면 보류합니다.

**03:52–04:05**

같은 대상의 현재 예외는 기본 취향을 일시적으로 대신합니다. 같은 우선순위의 조건이 서로 충돌하면 순서대로 하나를 고르지 않고 질문하며, 승격 관계의 사본은 한 번만 반영합니다.

**04:06–04:20 · 강조: context**

context에는 직접 조건과 상황, 근거가 함께 들어갑니다. 검정을 피한다는 방향과 필수 여부, 하나면 되는지 모두 필요한지, 격식의 범위를 보존하며 특정 대체색을 임의로 확정하지 않습니다.

**04:20–04:35 · 강조: context**

context에 넣는 장기는 12개, 단기는 20개이며 사용자 내용과 조건에는 6천 자 예산을 적용합니다. 이는 전체 모델의 토큰 한도가 아니며, 필수 조건을 담지 못하면 조용히 누락하는 대신 추론을 보류합니다.

## 04:36 · 5. context에서 목표값을 만드는 과정

**04:37–04:49 · 강조: 모델 제안**

사용자가 명시한 슬림 핏은 시스템이 직접 대응해 보존합니다. 모델 제안은 확인된 상황에서 필요한 스타일이나 격식을 부드러운 목표로 제안하며, 저장 권한은 갖지 않습니다.

**04:50–05:04 · 강조: 검증기**

검증기는 속성의 허용값과 타입, 적용 대상, 근거가 현재 context에 있는지 검사합니다. 모델이 다른 옷의 기억을 인용하거나 명시된 값과 회피 및 매칭 연산을 바꾸면 결과를 거부합니다.

**05:04–05:19 · 강조: 이번 목표**

이번 목표에는 지정됨, 추론 제안, 미정, 비적용, 충돌이라는 다섯 상태가 있습니다. 모델이 빠뜨린 직접 조건도 보존하고, 바지의 넥라인 같은 비적용과 아직 모르는 값, 로고 없음 같은 실제 값은 구분합니다.

**05:20–05:34**

응답 뒤에는 최신 SQLite 상태로 context를 다시 구성합니다. 기다리는 동안 요청이 닫히거나 기억이 수정, 철회, 삭제, 만료되어 결과의 기준이 달라졌다면 오래된 결과를 폐기합니다.

**05:34–05:47**

연결 코드는 정해진 JSON 형식과 응답 시간 제한, 거부 및 오류 처리를 갖췄습니다. 실제 모델 호출은 아직 진행하지 않았고, 이번 실행 예시는 규칙과 가상 응답으로 확인했습니다.

## 05:48 · 6. 활용과 삭제, 검증의 경계

**05:49–06:02**

기본 취향으로 저장하지 않아도 확인한 조건은 현재 요청에 사용할 수 있습니다. 목표값을 다시 기억으로 쓰려면 새로운 사용자 확인을 거쳐야 하며, 장기 활용에는 별도 동의가 필요합니다.

**06:02–06:14**

활용 철회는 추천에서 빼는 조작이고, 실제 삭제와 효과가 다릅니다. 의미를 바꾸는 교체에는 새 항목과 필요한 새 동의를 사용하며, 승격 사본은 함께 철회하거나 삭제합니다.

**06:15–06:30**

실제 삭제는 관리 DB의 내용과 관련 이력 및 처리 결과를 정리합니다. 내용 없는 삭제 재시도 경계는 24시간 유지하지만, 사용자 사본이나 운영체제 백업과 저장매체의 완전 소거까지 보장하지는 않습니다.

**06:30–06:45**

요청은 비활동 30일과 생성 후 90일, 활성 장기는 동의 후 365일, 비활성 내용은 최대 30일의 보관 한계를 적용합니다. 적용 유효 기간은 별도이며, 만료된 내용은 제외하고 호출자가 정리합니다.

**06:45–06:59**

현재 코드의 79개 오프라인 테스트와 오늘 슬림, 다음 요청 여유 핏의 데모가 통과했습니다. 실제 모델 품질과 제품 UI, 상품 추출, 사용자 연구 효과는 앞으로 확인해야 합니다.
