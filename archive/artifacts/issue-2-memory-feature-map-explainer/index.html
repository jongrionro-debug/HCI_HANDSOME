기억이 목표 조건이 되는 과정

메모리는 저장한 취향과 요청 조건입니다. context는 이번 아이템에 사용할 유효한 기억을 모은 묶음입니다. 목표 feature는 원하는 옷의 속성입니다. 예를 들어 바지의 핏과 색입니다.

기억을 선별할 때 아래 조건을 확인합니다.

  • 같은 사용자이며, 이번 요청에 사용할 수 있는가?
  • 확인된 활성 기억이며, 아직 유효한가?
  • 이번 아이템과 상황에 적용되는가?
  • 현재 예외나 충돌 때문에 따로 처리해야 하는가?

예를 들어 셔츠는 흰색, 바지는 네이비라는 조건을 대상별로 나눕니다. 철회·삭제·만료된 기억과 다른 요청의 단기 기억은 제외합니다.

이번 조건과 기본 취향은 어떻게 저장하나요?

확인된 단기 기억 이번 요청에서 사용할 조건 내용 확인
장기 기억 이후 요청에도 사용할 기본 취향 내용 확인 + 이후 활용 동의

확인과 장기 활용 동의는 별개입니다. 명시한 취향을 처음부터 장기로 저장할 때도 둘 다 필요합니다. 사용자는 항목을 교체하거나, 활용을 철회하거나, 삭제할 수 있습니다.

저장을 지키는 규칙

여러 변경은 모두 성공하거나 모두 취소됩니다. 중간 실패로 일부만 저장되지 않습니다. 같은 저장 명령을 재시도해도 중복 적용하지 않습니다. 오래된 버전으로 수정하면 충돌을 알립니다.

현재 구현에서는 호출 코드가 확인·동의의 근거를 전달합니다. 확인 화면과 로그인은 후속 구현 범위입니다.

모든 속성을 채울 필요는 없습니다. 관련된 조건만 사용하고 나머지는 미정으로 남깁니다. 원래 계획의 아이템 65개·코디 9개 속성을 일반 쇼핑용 17개로 축소했습니다.

이 분류는 설명을 위한 묶음입니다. 코드의 속성 사전은 registry.py 한 곳에서 관리합니다.

상황과 목표 속성도 구분합니다. 미팅·활동·쇼핑 목적은 상황 정보입니다. “미팅”이라는 이유만으로 사용자의 필수 조건을 자동으로 만들지 않습니다. “방수 기능을 원함”은 목표 조건이며, 실제 상품의 방수 성능을 확인한 결과는 아닙니다.

같은 우선순위의 조건이 충돌하면 충돌 상태와 확인 질문을 남깁니다. 임의로 하나를 고르지 않습니다. 이 충돌 동작은 데모 표와 별도로 테스트했습니다.

목표 조건은 상품 검색의 입력이 됩니다

반환값은 아이템별 속성·제약·근거·질문입니다. 실제 상품 목록이나 완성된 코디를 반환하는 기능은 이번에 구현하지 않았습니다.

상황 구현된 처리

응답을 기다리는 동안 기억이 철회·변경·만료됨 최신 context와 비교해 오래된 결과를 폐기

모델의 결과는 약한 추론 제안으로 다룹니다. 사용자의 확인이나 필수 조건으로 승격하지 않습니다.

기본 실행은 오프라인 규칙을 사용합니다. OpenAI 연결 코드는 만들었으며, 가상 HTTP 응답으로 검사했습니다. 실제 모델 호출과 언어 해석 품질 평가는 남아 있습니다.
