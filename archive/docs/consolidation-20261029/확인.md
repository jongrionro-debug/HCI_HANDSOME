**추천 구성은 3조건 참가자 내 비교, 조건마다 3개의 연속 요청이다.** 표현 방식의 기여와 메모리 관리의 기여를 따로 비교한다. 메모리는 적용 범위·확인·동의를 기준으로 관리하고, 원래 발화·이미지 선택·해석을 연결한다. 이 페이지는 수정한 설계와 실험 제안이며, 구현 완료나 검증된 효과를 보고하는 문서가 아니다.

## A 이번에 정리한 목표와 RQ
### 연구 목표
본 연구는 이미지 선택과 대화로 패션 취향의 표현 부담을 줄이고, 평소 취향과 현재 쇼핑 상황을 구분해 함께 반영하는 패션 추천 에이전트 LUMI를 설계·평가한다.

### RQ1 — 취향·쇼핑 목표의 표현
**이미지 후보 선택과 텍스트·선택적 확인을 결합한 상호작용은, 텍스트 중심 상호작용과 비교하여 사용자가 자신의 취향과 쇼핑 목표를 더 적은 부담으로 전달하고 원하는 스타일을 구체화하도록 돕는가?**

평가할 대상은 입력창 하나가 아니라 이미지 선택, 텍스트 수정, 필요한 경우의 짧은 확인을 묶은 상호작용이다. 주 지표는 표현 부담이고, 스타일 구체화와 이해받는 느낌은 보조 지표다.

### RQ2 — 기억의 적용 범위와 상황 적응
**장·단기 메모리를 구분하는 에이전트는 대화 이력만 활용하는 에이전트보다, 상황이 달라져도 확인된 평소 취향을 유지하면서 현재 조건을 반영하고 일시 요구의 자동 이월을 줄이는가?**

평소 취향이 다음 요청에 쓰이는지, 이번 예외가 필요한 순간에 반영되는지, 예외가 끝난 뒤 다음 요청에 잘못 남지 않는지를 구분해 본다. 통제감은 이를 사용자가 확인·수정할 수 있는지 설명하는 보조 지표다.

| 구분 | 이번 반영 |
|---|---|
| 사용자와 합의한 표현 | “이미지 후보 선택과 텍스트·선택적 확인을 결합한 상호작용”을 RQ1에 사용 |
| 메모리 설계 | 보고서의 범위·확인·별도 동의 원칙을 유지하고 저장 표현·조회·수정 흐름을 구체화 |
| 새 실험 제안 | 기존 2조건·조건별 2요청에서 3조건·조건별 3요청으로 확장 |
| RQ 번호 | 이 검토안은 표현을 RQ1, 메모리를 RQ2로 통일. 현재 보고서의 번호와 반대이므로 후속 문서 반영 때 가설·설문·분석을 함께 변경 |

## B 가장 적절한 비교 — 3조건 참가자 내 실험
**같은 참여자가 A·B·C를 모두 사용한다.** 개인마다 다른 패션 취향과 표현 능력의 영향을 줄이면서, 전체 LUMI와 한 요소만 다른 조건을 비교할 수 있다.

| 조건 | 취향을 전달하는 방식 | 과거 정보를 다루는 방식 | 비교 목적 |
|---|---|---|---|
| A · 텍스트 중심 + 구조화 메모리 | 텍스트로 요구·수정을 전달. 상품 사진은 볼 수 있지만 이미지 선택을 취향 입력으로 사용하지 않음 | C와 같은 장·단기 구분, 적용 범위, 확인·동의, 조회 규칙 | C ↔ A로 표현 상호작용의 기여 평가 |
| B · 이미지 상호작용 + 대화 이력 | C와 같은 이미지 후보 선택·텍스트·선택적 확인 | 이전 요청을 포함한 대화 이력을 사용. 별도의 장기 프로필·요청별 메모리 조회는 없음 | C ↔ B로 구조화된 메모리 관리의 기여 평가 |
| C · 전체 LUMI | 이미지 후보 선택·텍스트·선택적 확인 | 장·단기 메모리와 근거·적용 범위를 구분해 조회·갱신 | 두 비교의 기준 조건 |

A도 모호한 텍스트에는 일반적인 확인 질문을 할 수 있다. 이미지 선택 이유를 가설로 만들고 비교 이미지·간단한 선택지로 확인하는 상호작용만 제공하지 않는다. 내용 확인·재사용 동의에 필요한 공통 조작은 A와 C에 동일하게 둔다.

**B는 기억력이 없는 챗봇으로 만들지 않는다.** 같은 초기 취향과 이전 대화를 볼 수 있고, 현재 요구를 우선하라는 공통 지침도 받는다. B가 대화만으로 올바르게 처리하면 성공으로 평가한다. 일부러 취향을 잊거나 일시 조건을 이월하도록 만들지 않는다.

요청 1에서 사용자가 이후에도 활용할 선호라고 확인한 내용은 B에도 대화로 남긴다. 다만 B에 구조화된 장기 프로필을 저장·조회한다고 안내하지 않는다. 장기 취향 목록·적용 범위 수정·동의 같은 관리 기능은 구조화 메모리 조건의 일부로 평가한다.

### 세 조건에서 맞출 것
같은 모델·버전·생성 설정, 상품 데이터 스냅샷, 상품 속성 근거, 목표 조건 형식, 검색·랭킹 로직, 결과 표시 수, 시간 제한을 사용한다. 공통 상품 카드에는 세 조건 모두 사진·가격·속성을 제공한다. A에서 사진까지 제거하면 표현 방식과 상품 판단 정보가 함께 달라진다.

초기 취향 P0는 사용자가 한 번 확인한 동일한 내용이다. A·C는 이를 같은 구조의 초기 프로필로 사용하고, B는 같은 내용을 첫 대화 입력으로 받는다. 조건이 바뀌면 P0에서 다시 시작하며, 다른 조건에서 추가된 기억·대화·선택 이력은 가져오지 않는다. B의 이전 대화를 임의로 잘라 C에 유리하게 만들지 않는다.

### 이 구성을 추천하는 이유
기존 ChatGPT+Musinsa 비교는 실제 도구 조합과의 경험 차이를 보기 좋지만, 모델·쇼핑몰·상품 풀·화면 차이도 함께 들어간다. 이번 두 RQ의 주 실험은 위의 통제된 세 조건으로 진행하고, 기존 도구 조합과의 비교는 후속 현장 평가로 두는 편이 해석이 명확하다.

이 설계는 완전한 2×2 요인 실험은 아니다. 이미지·텍스트·확인 각각의 독립 효과나 두 요인의 상호작용은 주장하지 않는다. 표현 방식의 차이는 구조화 메모리가 있는 상황에서, 메모리 관리의 차이는 이미지 상호작용이 있는 상황에서 해석한다.

## C 참여자·과제·순서·시간
### 참여자와 과제 범위
온라인 패션 구매 경험이 있는 성인 **24명 완료를 목표로 제안**한다. 약 3명의 별도 파일럿으로 과제 난도·조작·시간·설문 이해를 먼저 점검한다. 24명은 수업 운영 규모와 6가지 순서의 균형을 고려한 수이며 검정력 확보의 근거는 아니다. 파일럿과 최소 의미 효과를 바탕으로 필요 표본을 다시 산정한다. 표본을 늘릴 수 없다면 작은 효과에 대해서는 탐색적 근거로 보고한다.

실험은 요청마다 **지정된 카테고리의 아이템 1개를 선택**하도록 통제하는 것을 제안한다. 같은 참여자의 세 조건에서는 같은 카테고리를 유지한다. 전체 코디를 매번 완성하게 하는 기존 계획보다 표현·상황 조건의 처리를 관찰하기 쉽다. 이 변경을 채택하면 “최종 코디 적합성” 문항도 “추천 아이템의 취향·상황 적합성”으로 맞춘다. 실험 결과를 코디 전체의 완성도까지 일반화하지 않는다.

참여자의 실제 평소 취향 2~3개를 확인하고, 그중 하나와 다른 선택도 현실적으로 가능한 상황을 준비한다. 예컨대 평소 여유핏을 선호해도 특정 행사에서는 다른 핏을 받아들일 수 있는지 확인한다. 참여자가 원하지 않는 취향을 연기하게 하지 않는다.

### 조건마다 수행할 3개의 요청
```flow LR
[동일한 초기 취향 P0] -> [요청 1 — 평소 목적]
[요청 1 — 평소 목적] -> [요청 2 — 이번만의 예외]
[요청 2 — 이번만의 예외] -> [요청 3 — 새로운 일상 목적]
```

| 단계 | 참여자가 하는 일 | 관찰할 동작 |
|---|---|---|
| 요청 1 · 평소 목적 | 자신의 취향으로 아이템 탐색. 새로 확인한 취향의 이후 활용 여부를 선택 | 표현 부담, 취향 구체화, 현재 적용과 이후 활용의 구분 |
| 요청 2 · 일시 예외 | 자신의 취향과 일부 다른 조건이 필요한 상황에서 탐색 | 현재 예외를 적용하면서 충돌하지 않는 평소 취향을 유지하는가 |
| 요청 3 · 예외가 끝난 새 요청 | 새로운 일상 목적을 제시하고 탐색 | 장기 취향을 재사용하고 요청 2의 일시 조건을 자동 이월하지 않는가 |

네이비·여유핏 → 이번 발표는 슬림핏 → 다음 주말용 옷은 설명용 예시다. 실제 시나리오는 참여자의 확인된 취향으로 구성한다. 요청 3에서 연구자가 네이비·여유핏 정답을 다시 입력해 주지 않는다. 참여자가 자발적으로 반복 설명하거나 조건을 수정하는 것은 허용하고 그 부담을 기록한다.

요청 2의 예외가 본인에게도 “이번만의 조건”인지 확인한다. 사용자가 평소 취향까지 바꾸겠다고 선택했다면 다음 요청의 적용을 이월 오류로 세지 않는다. 이 경우는 일시 예외 조작이 성립하지 않은 사례로 구분해 유효 n과 해석의 한계를 보고한다.

기억의 기계적 적용은 **요청 2·3에서 사용자가 결과를 수정하기 전 첫 목표 조건**을 기준으로 코딩한다. 최종 선택만 보면 사용자가 여러 번 고친 뒤의 성공을 에이전트의 첫 처리 성공으로 오인할 수 있다.

### 순서와 시나리오 배정
A→B→C, A→C→B, B→A→C, B→C→A, C→A→B, C→B→A에 4명씩 배정한다. 참여자는 준비된 배정 슬롯에 무작위로 들어간다. 과제 세트 X·Y·Z는 모두 평소 목적 → 예외 → 새로운 일상 목적 구조를 가지며, 상품 범위·예외 강도·가능한 정답 수를 파일럿에서 맞춘다.

각 순서 집단의 첫 세 슬롯에는 과제 세트 순서를 XYZ·YZX·ZXY로 한 번씩 배정한다. 네 번째 슬롯은 아래처럼 배정한다.

| 조건 순서 | 인원 | 네 번째 슬롯의 과제 세트 순서 |
|---|---:|---|
| A→B→C | 4명 | Z→X→Y |
| A→C→B | 4명 | Y→Z→X |
| B→A→C | 4명 | Z→X→Y |
| B→C→A | 4명 | Y→Z→X |
| C→A→B | 4명 | X→Y→Z |
| C→B→A | 4명 | X→Y→Z |

이 24개 배정에서는 각 조건이 각 순서 위치에 8번, 각 과제 세트와 8번 결합한다. 시나리오 난도는 배정만으로 같아지지 않으므로 파일럿이 필요하다. 균형화도 학습·이월 효과를 완전히 없애지는 않는다. [참가자 내 설계와 순서 효과에 대한 연구자 설명](https://www.yorku.ca/mack/RN-Counterbalancing.html)

### 시간 예산 — 약 82분, 파일럿 후 확정
| 절차 | 제안 시간 |
|---|---:|
| 설명·동의·사전 설문 | 6분 |
| 평소 취향 등록·참여자 확인 | 6분 |
| 공통 조작 연습 | 4분 |
| 조건별 3요청·평가 | 18분 × 3조건 = 54분 |
| 조건 사이 휴식 | 2분 × 2회 = 4분 |
| 사후 비교·인터뷰 | 8분 |
| 합계 | 82분 |

조건당 18분은 요청 3회 × 탐색 최대 4분, 요청 직후 간단 평가 총 1.5분, 조건 평가 4.5분의 예산이다. 제한 시간 도달·상품 없음·선택 미완료는 별도로 기록한다. 실패를 숨기고 완료 과제만 비교하지 않는다. 전체 코디 탐색을 유지해야 한다면 이 시간 예산을 그대로 쓰지 말고 파일럿에서 다시 산정해야 한다.

## D 무엇을 측정하고 어떻게 분석할까
### 주요 비교와 지표
| RQ | 주요 지표 | 측정 시점·비교 | 주 분석 |
|---|---|---|---|
| RQ1 | 취향·요구 전달의 표현 부담 | 세 요청 직후 점수의 참여자별 조건 평균. C ↔ A | Wilcoxon signed-rank |
| RQ2 | 평소 취향 반영 | 요청 3 직후 아이템의 취향 적합성. C ↔ B | Wilcoxon signed-rank |
| RQ2 | 현재 상황 적합성 | 요청 2 직후 아이템의 상황 적합성. C ↔ B | Wilcoxon signed-rank |
| RQ2 | 기억 범위 처리 성공 여부 | 요청 2·3의 수정 전 목표 조건. 참여자·조건마다 성공/실패 1개. C ↔ B | 정확 McNemar 검정 |

표현 부담은 기존 대응 설문에 있는 전달 용이성 문항을 활용한다. 높은 점수가 쉬움을 뜻하면 5점 척도에서 6−응답으로 바꿔 높은 값이 큰 부담이 되도록 한다. 취향·상황 문항은 기존 대응 문항의 조건명과 아이템 범위를 맞춘다. 이 자체 문항들을 검증된 표준 척도로 소개하지 않는다.

기억 범위 처리 성공은 세 기준을 모두 충족한 경우다. 요청 2의 명시적 일시 요구를 목표에 반영해야 한다. 요청 3에서는 유효한 관련 평소 취향을 반영해야 한다. 이전의 일시 요구를 새로운 근거 없이 요청 3의 필수 조건이나 선호로 설정하지 않아야 한다. 각 실패 유형도 따로 제시한다.

단순히 슬림핏 상품이 다시 보였다는 이유만으로 이월 오류로 코딩하지 않는다. 실제 목표 조건과 원래 근거를 확인한다. 코딩의 기준은 참여자가 확인한 원래 취향·요구·적용 범위다. 에이전트가 만든 기억을 정답으로 삼지 않는다. 조건 이름을 가린 공통 출력 형식으로 두 연구자가 독립 코딩하고 불일치를 확인한다.

### 통계 처리
주요 검정은 위의 **4개로 미리 고정**하고 이 4개의 p값에 Holm 보정을 적용한다. 양측 검정, 전체 유의수준 .05를 사용한다. RQ1의 주 지표와 RQ2의 주 지표를 구분해 보고하며, RQ2의 일부 결과만 좋아지면 어느 측면이 지지됐는지 한정한다.

Wilcoxon은 개인별 대응 자료를 사용한다. 차이 분포의 대칭성·이상치·동점·0 차이와 유효 쌍 수를 보고한다. 동점이 많은 작은 표본에서 단순 exact 계산을 무조건 적용하지 않고 적절한 순열 계산을 사용한다. 심한 비대칭에 대한 부호검정 민감도 분석을 사전 지정한다. 정규성 검정 결과 하나로 유리한 검정을 골라 바꾸지 않는다. [Wilcoxon의 가정과 계산 방법](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.wilcoxon.html)

McNemar는 같은 참여자의 성공/실패 쌍을 분석한다. 불일치 쌍이 적을 수 있으므로 정확 검정을 사용한다. 양쪽 모두 성공한 참여자를 독립 표본 두 개로 계산하지 않는다. 불일치가 없으면 관찰된 차이를 검정할 정보도 적다는 점을 보고한다. [정확 McNemar 검정](https://www.statsmodels.org/stable/generated/statsmodels.stats.contingency_tables.mcnemar.html)

점수는 분포·중앙값·사분위수와 효과크기를, 성공률은 대응 표와 성공률 차이를 제시한다. 95% 신뢰구간을 추정할 때 재표집 단위는 참여자다. 요청 수 216개를 독립 참여자 수로 취급하지 않는다. 주요 검정의 보정과 효과크기·구간 추정을 구분한다. [Holm 보정](https://www.statsmodels.org/stable/generated/statsmodels.stats.multitest.multipletests.html)

미완료·오류·결측의 이유와 각 비교의 유효 n을 보고한다. 실패를 임의로 중립 응답으로 대체하지 않는다. 실패 때문에 적합성 응답이 빠졌다면 완료율과 함께 해석하고, 성공 과제만의 결과라는 한계를 명시한다. 순서·과제 세트에 따른 효과크기 분포도 확인하되, 작은 집단의 비유의 결과로 순서 효과가 없다고 결론내리지 않는다.

## E 메모리 설계 — 무엇을 어떻게 저장하도록 구체화했나
### 구분 기준은 기간보다 적용 범위와 재사용 동의
장기는 “오래된 정보”, 단기는 “최근 정보”가 아니다. 이번 요청만의 요구인지, 이후에도 적용할 선호로 확인·동의했는지가 기준이다.

| 내용 | 기본 처리 | 장기 활용이 가능한 경우 |
|---|---|---|
| “바지는 평소 여유핏이 좋아요” | 확인된 취향 후보로 정리하고 이번 요청에 활용 | 내용·대상·이후 활용에 동의 |
| “이번 발표에는 슬림핏으로” | 현재 요청의 예외 | 사용자가 “발표할 때마다” 활용하도록 별도로 확인·동의하면 상황 조건이 붙은 장기 선호로 저장 가능 |
| “이 이미지가 좋아요” | 이미지 선택 사실을 현재 요청에 기록 | 무엇을 좋아하는지 확인하고 이후 활용에도 별도로 동의한 내용만 저장 |
| “빈티지한 느낌” | 원래 표현과 맥락을 보존 | 모호함을 그대로 표시한 표현도 재사용 동의를 받을 수 있으나, 특정 색·원단의 확정 선호로 바꾸지 않음 |

장기에도 상황 조건이 붙을 수 있다. 발표와 관련된 정보라고 무조건 단기로 분류하지 않는다. 반대로 여러 번 선택했다는 이유만으로 장기로 바꾸지 않는다.

### 선택 사실과 해석의 차이
사용자가 이미지 P를 선택했다는 사실은 직접 관찰할 수 있다. “P의 넓은 핏이 좋아서 골랐다”는 설명은 사용자가 말하지 않았다면 가설이다. P의 색·원단·핏을 모두 선호한다고 저장하지 않는다. 선택하지 않은 이미지도 자동으로 비선호가 되지 않는다.

“색 때문에 골랐나요, 핏 때문인가요?”의 답에 따라 다음 검색 조건이 달라질 때만 확인한다. 답을 얻지 못하면 선택 사실을 유지하고 이유는 미확인으로 둔다. 미확인 해석은 비교 후보·보조 탐색에 참고할 수 있지만 확정 필수 조건이나 장기 취향을 대신하지 않는다.

## F 에이전트가 기억을 읽고 쓰는 구체적 순서
### 입력 → 해석 → 현재 적용 → 별도 장기 동의
```flow TB
[발화·이미지 선택] -> [원래 근거 기록]
[원래 근거 기록] -> [의미·대상·범위 해석]
[의미·대상·범위 해석] -> [필요한 확인]: 모호한 해석
[필요한 확인] -> [확인된 현재 조건]
[의미·대상·범위 해석] -> [확인된 현재 조건]: 명확한 직접 요구
[확인된 현재 조건] -> [목표 조건과 추천]
[확인된 현재 조건] -> [이후 활용할 내용 제시]
[이후 활용할 내용 제시] -> [장기 프로필 갱신]: 별도 동의
```

명확한 직접 요구는 사용자 발화 근거와 대상·값·범위를 검증해 이번 조건으로 반영한다. 매번 같은 확인을 강요하지 않는다. 해석이 모호하거나 적용 범위가 불분명하면 짧게 확인한다. 현재 조건을 확인했다는 사실과 이후에도 사용할 동의는 별개다.

실행 모델은 기억 후보·해석·갱신안을 제안한다. 확인 상태와 장기 동의는 신뢰된 사용자 이벤트를 근거로 앱이 검증한다. 모델 출력이나 최종 상품 선택만으로 장기 쓰기를 실행하지 않는다.

### 조회·결합 규칙
1. 현재 사용자·요청·대상 아이템을 확인한다. 철회·만료·삭제·미동의 장기 항목은 제외한다.
2. 현재 요청의 유효한 단기 조건과, 대상·상황에 맞는 확인된 장기 선호를 조회한다.
3. 요청이 바뀌면 이전 요청의 단기를 자동으로 가져오지 않는다. 같은 요청의 이어지는 수정은 유지한다.
4. 현재 명시 요구와 장기 선호가 충돌하면 이번 목표에서만 현재 요구를 우선한다. 장기 원본을 덮어쓰지 않는다.
5. 충돌하지 않는 장기 선호는 함께 유지한다. 같은 수준의 현재 요구끼리 모순되면 입력 순서로 임의 선택하지 않고 확인한다.
6. 필수 조건·선호·추론을 구분한 목표 Item Feature Map을 만들고 각 값의 근거를 연결한다.
7. 실제 상품의 확인된 속성과 비교한다. 미확인 상품 속성을 조건 충족으로 처리하지 않는다.
8. 출력 직전 요청·기억 버전을 다시 확인한다. 사용자가 수정·철회한 뒤 도착한 오래된 응답은 폐기하고 다시 조회한다.

자유 표현의 관련성 검색을 추가하더라도 먼저 범위·동의·대상 자격을 검사한다. 의미가 비슷하다는 이유만으로 다른 요청의 일시 요구를 되살리지 않는다. 이 설계가 벡터 DB나 특정 검색 모델을 필수로 요구하는 것은 아니다.

| 이유 확인 | “색은 좋고 핏은 좀 더 여유롭게” | 변화 없음 | 색 선호와 현재 핏 수정을 구분해 재검색 |
| 탐색 종료 | 이번 요청을 닫음 | 별도 동의한 내용만 추가·교체 | 선택·종료가 자동 저장 동의가 되지 않음 |
| 새 일상 요청 | 새 요청의 조건으로 시작 | 유효한 네이비·여유핏 참조 | 발표 전용 슬림핏이 자동 이월되지 않음 |

“이번만”과 “앞으로도” 중 사용자가 앞으로도 바꾸겠다고 선택하면 새 내용·대상·범위를 확인하고 새 동의로 장기 취향을 교체한다. 이전 항목은 활성 조회에서 제외하고 기존 보관·삭제 규칙에 따라 관리한다.

### 한 에이전트와 역할이 나뉜 도구
| 판단 상황 | 에이전트의 다음 행동 | 앱이 지킬 경계 |
|---|---|---|
| 추천에 필요한 정보가 충분함 | 관련 기억 조회 → 목표 구성 → 상품 검색 | 필수 현재 조건과 근거 보존 |
| 선택 이유가 모호하고 다음 검색이 달라짐 | 짧은 질문 또는 비교 이미지 제시 | 미확인 가설을 확정 선호로 쓰지 않음 |
| 상품이 없거나 사용자가 수정함 | 조정할 조건을 묻고 목표를 다시 구성해 검색 | 사용자의 필수 조건을 조용히 완화하지 않음 |
| 장기 활용 후보가 생김 | 이후에 사용할 내용·범위 제시 | 동의 이벤트 검증 후에만 쓰기 |
| 사용자가 선택·종료함 | 결과 정리·요청 종료 | 최종 결정과 저장 여부는 사용자에게 있음 |

조회·검색·질문은 에이전트가 상태에 따라 선택할 수 있게 하고, 장기 쓰기는 사용자 승인과 앱 검증을 통과해야 한다. 제안한 도구의 역할이지 현재 구현된 공개 API 목록은 아니다. [에이전트의 도구 사용·피드백 반복에 대한 설명](https://www.anthropic.com/research/building-effective-agents)

## G 기존 구현과 이번 구체화의 차이
**장·단기 분리와 별도 동의는 새로 발명한 부분이 아니다.** 보고서와 기존 프로토타입에 이미 있는 원칙을 유지한다. 이번에는 실제 표현을 잃지 않는 저장 방식과 에이전트의 조회·질문·검색 연결을 구체화했다.

| 영역 | 현재 코드에서 확인한 내용 | 이번 설계의 추가·확장 | 상태 |
|---|---|---|---|
| 메모리 기록 | feature·values가 필요하고 지원 속성·값을 검증 | 자유 표현·선택 사실은 원래 의미로 보존하고 속성 연결을 선택적으로 둠 | 설계 제안, 코드 미변경 |
| 발화·해석 근거 | 최소 content·evidence_ref는 SQLite에 기록. 전체 대화·확인 힌트는 프로세스 상태 | 필요한 원문 구간·이미지 선택·해석과 확인 이벤트를 지속 연결 | 확장 필요 |
| 현재 적용·장기 동의 | 후보 확인·승격·별도 동의·철회·버전 관리 | 명확한 직접 요구와 모호한 해석을 구분해 확인 부담을 줄이는 소비자 흐름 | 원칙 유지, UI·의미 검증 확장 필요 |
| 요청별 조회 | 현재 요청·대상·상황 필터와 현재 예외 우선 적용 | 자유 표현·이미지 근거까지 동일한 범위 규칙 안에서 조회 | 구조화 항목 기반은 있음 |
| 응답 최신성 | 변경·종료·만료 뒤 늦은 응답을 stale_context로 거부 | 이미지 선택·상품 재검색·새 기록 형식에도 같은 원칙 적용 | 기존 기반 확장 |
| 상품·피드백 에이전트 | 실제 상품 검색·이미지 피드백·소비자 추천 UI는 아직 없음 | 선택 이유 확인 → 목표 수정 → 검색·재검색 → 별도 장기 저장 연결 | 미구현 |

근거 위치: [store.py](src/stylemate_memory/store.py)의 _validate_memory_payload·apply_batch, [inspector.py](src/stylemate_memory/inspector.py)의 chat·new_request, [context.py](src/stylemate_memory/context.py)의 build_context·_resolve_bindings, [app.py](src/stylemate_memory/app.py)의 infer_request. 현재 문서는 [실행 계약](docs/shopping-memory-prototype.md)과 [단계별 구현 상태](docs/workflow.md)를 따른다.

기존 [context 테스트](tests/test_context.py)는 현재 예외와 다음 요청의 경계를 다루고, [app 테스트](tests/test_app.py)는 추론에 의한 메모리 변경 금지와 오래된 응답 거부 등을 다룬다. 이번에는 테스트의 코드와 명세를 확인했으며 메모리 테스트를 새로 실행하거나 기능을 추가하지 않았다. 자유 표현·이미지 근거가 추가되면 해당 경계의 회귀 검증과 별도의 의미 품질 평가가 필요하다.

현재의 Python·SQLite·17개 속성·보관 기간·조회 예산을 최종 제품 요구사항으로 새로 확정하지 않는다. 저장 형태의 실제 변경은 기존 데이터·동의·삭제 기록의 마이그레이션을 검토한 뒤 진행해야 한다.

## H 네이버 데이터·실험 준비·주장의 범위
### 네이버 쇼핑 데이터의 연결 위치
네이버 쇼핑 데이터에서 상품 ID·이미지·검증 가능한 속성의 고정 스냅샷과 상품별 Item Feature Map을 만든다. 세 조건은 이를 같은 검색·랭킹 도구로 조회해 추천한다. 수업에서 제공받을 데이터인지, 어떤 이용 경로와 필드가 있는지는 아직 확인하지 않았다.

실험 전에 시나리오별로 실제 선택 가능한 상품이 있는지 확인한다. 필수 조건의 근거가 없는 상품은 충족으로 세지 않는다. 세 조건에서 같은 데이터 기준을 사용하고, 실험 중 가격·후보 변화가 결과에 섞이지 않도록 스냅샷을 고정한다. 이 페이지 작성 중 데이터 수집·크롤링·모델 호출은 수행하지 않았다.

### 실행 순서 제안
1. 자유 표현·선택 근거를 보존할 기록 계약과 확인·동의 흐름을 구체화한다.
2. 같은 상품 스냅샷·목표 형식·검색 도구 위에서 A·B·C의 두 차이만 전환할 수 있게 구현한다.
3. 파일럿 약 3명으로 임시 예외가 실제로 발생하는지, 4분 탐색이 가능한지, 순서·문항·로그 코딩이 작동하는지 확인한다.
4. 주요 지표·분석·결측·코딩·표본 계획을 고정한 뒤 본 실험을 진행한다.

### 이 실험이 답할 수 있는 범위
평소 취향과 일시 요구를 짧은 세션의 여러 요청에서 구분해 활용하는지 평가한다. 며칠·몇 달 동안 자연스럽게 취향을 학습하거나 실제 구매가 좋아지는 효과는 입증하지 않는다. 이를 주장하려면 별도의 반복 사용·현장 평가가 필요하다.

현재 보고서의 2조건·2요청·50~60분 계획은 원본에 보존했다. 이 페이지의 3조건·3요청·약 82분과 아이템 단위 과제는 후속 실험 제안이다. 실제 코드, 원본 PDF, 정본 연구 안내는 이번 작업에서 변경하지 않는다.
