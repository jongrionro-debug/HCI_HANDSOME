## 00:08–00:54 · 1. 오늘의 선택이 평소 취향을 바꿀까?

화면: 기본 취향 → 오늘 추천 위에 이번 요청이 나타난다. 기본 취향 노드는 유지한 채 새 요청과 다음 추천으로 이동한다. 근거: D02·D07.

**00:09–00:16**

먼저 기본 취향을 보죠. 사용자가 이미 확인하고 저장한 여유 핏은, 평소 추천의 출발점입니다.

**00:17–00:27**

그런데 이번 요청에는 발표라는 상황이 붙습니다. 오늘만 슬림하게 입겠다는 명시적인 조건이, 같은 핏 항목의 기본값을 일시적으로 대신합니다.

**00:27–00:35**

이때 기본 취향 자체를 고치지는 않습니다. 새 요청을 시작하면, 저장된 여유 핏은 그대로 남아 있습니다.

**00:36–00:43**

새 요청은 새로운 경계입니다. 앞선 발표 요청의 임시 조건을, 다음 요청에 자동으로 가져오지 않습니다.

**00:43–00:53**

그래서 다음 추천은 다시 여유 핏을 기본으로 시작합니다. 같은 요청을 재개할 때는, 남아 있는 조건의 기간과 상황을 다시 확인합니다.

## 00:54–01:42 · 2. 기억을 작은 주장으로 쪼개기

화면: 기억 한 항목 아래에 내용, 적용 범위, 조건·기간, 근거가 차례로 펼쳐진다. 각 항목을 확대한다. 근거: D01·D05.

**00:54–01:03**

그럼 기억의 단위는 무엇일까요? 기억 한 항목은 사용자가 따로 확인하고, 수정하고, 활용을 철회할 수 있는 하나의 주장입니다.

**01:04–01:13**

내용과 속성에는 사용자의 문장과 최소한의 구조를 함께 둡니다. 여유 핏을 좋아한다는 말과, 여유 핏을 피한다는 말을 섞지 않습니다.

**01:13–01:22**

적용 범위는 장기와 요청별 단기로 나눕니다. 장기로 쓰려면 그 항목에 대한 내용 확인과 이후 활용 동의가 필요합니다.

**01:22–01:31**

조건과 기간도 기억의 일부입니다. 고객 미팅 때 정장 느낌을 피한다는 조건은, 모든 상황에서 정장을 싫어한다는 뜻이 아닙니다.

**01:32–01:41**

확인과 근거는 해석이 어디서 왔는지를 연결합니다. 이미지에서 핏만 골랐다면, 색과 소재까지 좋아한다고 확정하지 않습니다.

## 01:42–02:32 · 3. 맞아요와 다음에도 써 주세요

화면: 내용 확인과 항목별 저장 선택을 서로 다른 노드로 보여 준다. 저장 경로와 이번만 적용하는 경로를 나눈다. 근거: D03·D04.

**01:43–01:51**

이제 내용 확인을 봅시다. 시스템이 해석한 핏이 맞는지 확인하는 단계입니다. 아직 미래의 활용을 허락한 것은 아닙니다.

**01:51–02:01**

내용 질문에 맞아요라고 답하면, 확인한 조건을 이번 요청에 사용할 수 있습니다. 반복해서 골랐다는 이유만으로 장기 기억이 되지는 않습니다.

**02:02–02:12**

항목별 저장 선택에서는 다음에도 쓸 문장과 조건, 기간을 보여 줍니다. 체크는 처음에 비워 두고, 기억해 달라는 대상이 모호하면 질문합니다.

**02:13–02:22**

사용자가 항목의 내용과 이후 활용에 명시적으로 동의하면, 기본 취향에 저장할 수 있습니다. 대화 중 저장도 같은 계약을 따릅니다.

**02:22–02:32**

선택하지 않거나 창을 닫으면, 이번 요청의 조건으로만 남습니다. 처음부터 취향을 저장하지 않고, 빈 프로필로 시작해도 됩니다.

## 02:32–03:27 · 4. 제안에서 저장으로, 저장에서 추천으로

화면: 사용자 입력에 대한 AI 제안 → 시스템 검증 → 저장 → 조회 → 추천을 단계적으로 연결한다. 모델의 제안과 시스템의 쓰기 경계를 구분한다. 근거: D06·D08·D09·D11.

**02:33–02:41**

AI는 AI 제안을 만듭니다. 무엇을 의미하는지 추정할 수 있지만, 그 추정만으로 기억을 바꾸지는 못합니다.

**02:42–02:52**

시스템 검증은 현재 사용자의 근거와 정확한 동의 대상을 검사합니다. 오래된 응답이나 저장 화면은, 버전이 맞지 않으면 반영하지 않습니다.

**02:52–03:04**

SQLite 저장은 후속 구현할 저장 경계입니다. 한 번의 저장에서 고른 항목들은 전부 성공하거나 전부 실패하고, 같은 요청의 재시도는 중복 반영하지 않습니다.

**03:04–03:14**

문맥 조회는 기억을 모두 꺼내는 과정이 아닙니다. 사용자와 요청, 상태와 기간, 적용 조건을 먼저 확인하고 관련된 기억을 고릅니다.

**03:14–03:26**

추천 패널에는 실제 사용한 항목과 제외한 이유가 연결됩니다. 같은 우선순위에서 충돌하면 질문하고, 조건이 바뀌면 기존 추천에 갱신이 필요하다고 표시합니다.

## 03:27–04:24 · 5. 쓰지 않기, 보관하기, 지우기

화면: 요청 종료, 장기 보관, 활용 철회, 기록 삭제, 재개를 표의 행별로 보여 준다. 모든 기간은 승인된 초기 정책이다. 근거: D02·D05·D10.

**03:27–03:39**

요청을 끝내면 단기의 추천 적용을 멈춥니다. 원문은 재개를 위해 제한적으로 보관합니다. 승인된 초기 정책은 비활동 삼십 일, 생성 후 최대 구십 일입니다.

**03:40–03:50**

활성 장기 기억은 마지막으로 명시적인 활용 동의를 한 날부터 삼백육십오 일입니다. 추천에 다시 썼다고 보관 기간을 늘리지는 않습니다.

**03:50–04:00**

활용 철회는 즉시 추천에서 빼는 조작입니다. 비활성 내용은 최대 삼십 일만 남길 수 있으며, 원래 보관 시한이 더 이르면 그 시한을 따릅니다.

**04:00–04:12**

기록 삭제는 원문과 동일 사본, 근거와 파생 데이터, 남은 참조까지 지우는 작업입니다. 삭제에 실패하면 활용 차단을 유지하고, 완료됐다고 표시하지 않습니다.

**04:13–04:23**

같은 요청을 다시 열어도 지난 날짜를 오늘로 바꾸지 않습니다. 이 기간들은 승인된 초기 설계 정책이며, 현재 서버의 운영이나 법적 기준을 뜻하지 않습니다.

## 04:24–05:18 · 6. 설계에서 구현과 연구로

화면: 현재 P0와 후속 P1–P6을 수직 시간선으로 보여 준다. 현재 설계 검증, 후속 제품 검증, 사용자 연구를 구분한다. 근거: D11·D12.

**04:25–04:34**

지금 완성된 것은 승인된 설계와 구현 계획입니다. 계약과 가상 정책을 검증한 자료가 있으며, 실행 제품은 아직 없습니다.

**04:34–04:44**

먼저 요청 경계와 입력 근거를 구현합니다. 새로운 요청과 재개를 구분하고, 시간대와 유효 기간을 실제 동작으로 확인합니다.

**04:44–04:55**

그다음 파이썬과 SQLite로 저장과 조회를 연결합니다. 동의, 버전 충돌, 전체 실패, 같은 요청의 재시도를 실제 데이터베이스에서 검증합니다.

**04:56–05:06**

이어서 보관과 삭제, 가상 화면 연결을 확인합니다. 현재 가상 검증이 실제 디스크 삭제나 모델의 이미지 이해를 입증한 것은 아닙니다.

**05:06–05:18**

실제 화면과 인증, 추천 모델과 사용자 연구는 별도 범위입니다. 연구는 사용자 주도성과 의도 표현을 평가하며, 무엇을 기억할지는 사용자가 결정합니다.
## 설명에서 생략한 세부 계약

- 조회 초기 상한은 장기 12개, 단기 20개, 문자 예산 6,000이다. 정밀 정책·조건별 점수·예산 제외는 설계 정본을 따른다.
- 의미 수정은 새 ID와 새 확인·동의가 필요하다. 같은 의미의 승격 사본은 한 번만 반영하며 함께 활용을 철회한다.
- 장기에는 동의한 취향과 반복 상황도 들어갈 수 있다. 일회성 일정·날씨는 기본 장기 저장 후보에 섞지 않는다.
- 삭제는 동일 의미의 사본과 파생 데이터에 전파한다. 독립 동의가 있는 새 의미의 항목은 삭제 범위를 따로 제시한다.
- RQ1은 비분리 방식과 분리·확인·수정 방식의 결합 효과를 비교한다. RQ2는 텍스트만, 고정 텍스트·이미지, 선택적 텍스트·이미지 제공을 비교한다.
- 현재 비교 어댑터는 가상 사례 전용이다. 실제 사용자 연구의 과제·동의·배정·효과 검증은 별도 범위다.
