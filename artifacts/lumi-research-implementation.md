기존 메모리 기반에 실제 상품 LOOK과 이미지 선택을 연결했습니다. 사용자는 필요한 확인을 거쳐 추천을 조정합니다. 장기기억은 저장할 내용을 고르고 별도로 동의할 때만 바뀝니다.

## A 이번에 무엇이 달라졌나요?

이전에는 기억을 저장하고 원하는 아이템의 목표 속성을 확인했습니다. 이제는 그 결과로 상품 코디를 보여줍니다. 선택과 재추천도 한 화면에서 이어집니다.

| 영역 | 이전 구현 | 이번에 연결한 기능 |
|---|---|---|
| 메모리 | 장·단기 분리와 확인·동의 | 선택한 선호의 저장 검토와 다음 요청 활용 |
| 선호 해석 | 아이템 목표 속성 17개 | 선택 근거·잠정 가설·이번에 확인한 선호 |
| 상품 | 추천 경로가 없었음 | 공식 상품을 참조한 셔츠 6개·바지 6개 |
| 코디 | 화면 후보가 없었음 | 가능한 상품 조합으로 LOOK 구성 |
| 상호작용 | 개발자용 기억 확인 | 전체·부분 선택과 필요한 질문·재추천 |

```callout info 이번 구현의 목표
연구용 전체 흐름을 실행할 수 있게 만들었습니다. 고정 상품을 이용합니다. 추천 품질과 사용자 연구 효과는 별도로 검증해야 합니다.
```

[연구 화면 열기](http://127.0.0.1:8766/) · 현재 실행 계약 (개발 브랜치의 `docs/research-prototype.md`)

## B 사용자는 어떤 순서로 이용하나요?

```flow
(현재 요청) -> 조건 검토: 적용할 내용 선택
조건 검토 -> 상품 LOOK: 확인한 조건 반영
상품 LOOK -> 이미지 선택: 전체 또는 일부 선택
이미지 선택 -> 재추천: 가설 또는 확인한 선호 활용
재추천 -> 상품 LOOK: 탐색 계속
이미지 선택 -> (확정 또는 중단): 사용자가 결정
(확정 또는 중단) -> 저장 검토: 저장은 선택
저장 검토 -> (요청 닫기): 저장 또는 건너뛰기
```

처음에는 LOOK을 최대 5개 제시합니다. 조건에 맞는 상품이 부족하면 후보 수가 줄어듭니다. 부족한 조건을 몰래 완화하지 않습니다.

전체 룩과 개별 상품을 함께 선택할 수 있습니다. 마음에 드는 것이 없다는 응답도 가능합니다. 사용자는 질문 중에도 현재 코디를 확정하거나 중단할 수 있습니다.

## C 선호·후보·상품 속성을 왜 구분하나요?

“내가 원하는 것”과 “보여준 것”과 “상품의 속성”은 다릅니다. 이 정보를 섞으면 추천 결과가 사용자 취향으로 잘못 저장될 수 있습니다.

| 구분 | 담는 내용 | 예시 |
|---|---|---|
| 사용자 선호 상태 | 이번 조건, 관련 기억, 확인한 선호, 가설 | 이번에는 갈색 바지가 필요함 |
| 후보 LOOK | 추천기가 구성한 상품 조합 | 베이지 셔츠와 갈색 바지 |
| 상품 속성 | 상품 정보와 그 근거 | 바지 색상은 갈색이라는 공식 표기 |

```callout warn 선택한 사실과 선택 이유는 다릅니다
룩을 고르면 그 조합에 대한 긍정 근거를 남깁니다. 그 안의 색상·핏·소재를 모두 좋아한다고 확정하지 않습니다. 상의를 고른 근거를 하의 취향으로 확대하지 않습니다.
```

선택하지 않은 상품은 싫어함으로 기록하지 않습니다. 모델이 제안한 이유는 확인 전까지 가설입니다.

상품 정보도 근거를 구분합니다. 공식 표기, 이미지 관측, 추론, 가상 검증값을 별도로 표시합니다. 이번 스타일 라벨은 Codex가 작성한 추론값입니다. 사람의 라벨 검수 결과가 아닙니다.

## D 갈색 바지 요청은 어떻게 기억으로 이어지나요?

다음은 실제 브라우저 검증에서 확인한 흐름을 요약한 예시입니다. 참여자 연구 결과는 아닙니다.

```timeline v
1 | 현재 요청 | “갈색 바지가 필수인 코디를 추천해줘.”
2 | 조건 확인 | 사용자가 갈색 바지 조건을 확인합니다.
3 | 첫 추천 | 갈색 바지를 포함한 LOOK 5개를 보여줍니다.
4 | 상의 부분 선택 | 사용자가 마음에 드는 셔츠만 고릅니다.
5 | 이유 가설 | 시스템은 여유 있는 셔츠 핏을 좋아하는지 묻습니다.
6 | 이번에 적용 | 사용자가 맞다고 답합니다. 이번 추천의 선호를 갱신합니다.
7 | 저장 검토 | 코디를 확정하고 저장할 셔츠 핏 선호를 고릅니다.
8 | 별도 동의 | 다음 추천에 활용하는 데 동의한 뒤 저장합니다.
9 | 새 요청 | 갈색 바지 조건은 이월하지 않습니다. 동의한 셔츠 핏은 활용합니다.
```

| 정보 | 이번 요청에서의 역할 | 다음 요청에서의 역할 |
|---|---|---|
| 갈색 바지 필수 | 현재 요청의 조건 | 저장하지 않았으므로 적용하지 않음 |
| 선택한 셔츠 | 해당 상품의 긍정 근거 | 선택 기록을 자동 이월하지 않음 |
| 여유 있는 셔츠 핏 | 이유 확인 후 이번 추천에 반영 | 별도 저장 동의가 있을 때 활용 |
| 셔츠의 다른 속성 | 상품 정보 | 선택만으로 사용자 취향이 되지 않음 |

## E 기억은 어떤 조건에서 저장되나요?

```sequence num
participants: 사용자, 화면, 저장소
사용자 -> 화면: 확정 또는 중단
화면 --> 사용자: 저장할 내용 표시
사용자 -> 화면: 항목 선택과 활용 동의
화면 -> 저장소: 선호 저장
저장소 --> 화면: 저장 결과
화면 -> 저장소: 요청 닫기
```

저장하지 않기를 고르면 장기기억을 바꾸지 않습니다. 코디 확정도 자동 저장 동의가 아닙니다.

기존 선호를 대체할 때는 그 내용을 화면에 표시합니다. 사용자가 해당 항목을 선택하고 별도로 동의해야 대체합니다. 다른 아이템이나 조건부 기억은 조용히 바꾸지 않습니다.

```callout info 종료와 요청 닫기는 순서가 다릅니다
먼저 추천 탐색을 마칩니다. 다음으로 선택적 저장을 처리합니다. 마지막으로 저장 계층의 요청을 닫습니다. 요청을 먼저 닫으면 새 저장 작업이 거부됩니다.
```

선택 근거·가설·세션 선호는 실행 중인 메모리에 둡니다. 확인한 요청 조건과 동의한 장기 선호는 기존 SQLite 저장 계약을 따릅니다.
## F 모델과 정책은 각각 무엇을 맡나요?

| 역할 | 담당하는 일 | 처리 경계 |
|---|---|---|
| 요청 해석 | 원문에서 조건 후보를 추출 | 사용자가 확인한 조건만 적용 |
| 선택 이유 해석 | 선택한 상품에서 이유 가설을 제안 | 허용값·대상·선택 근거를 검사 |
| 추천기 | 상품 조건 검사와 조합·정렬 | 필수 조건과 회피 조건을 유지 |
| 행동 정책 | 질문·비교·재추천·종료 제안을 선택 | 질문 예산과 사용자 결정권을 유지 |
| 메모리 저장소 | 확인·동의·버전과 저장을 관리 | 모델이 직접 쓰지 못함 |

기본 화면은 오프라인 사전과 규칙을 사용합니다. 실제 모델 모드는 기존 Codex CLI를 사용합니다. 실제 모드는 요청 해석, 목표 속성 추론, 선택 이유 해석을 수행합니다.

- 초기 LOOK 구성은 기본 2:1:2 전략을 사용합니다. 관련 장기기억이 없으면 장기기억 기반이라고 표시하지 않습니다.
- 질문 예산 기본값은 3입니다. 이유 질문·보조 질문·이미지 비교를 합산합니다.
- “잘 모르겠어요”에는 같은 속성의 이유 질문을 반복하지 않습니다. 비교할 상품이 있을 때만 이미지 비교를 제공합니다.
- 추론으로 붙인 상품 속성은 필수 조건 충족의 근거로 쓰지 않습니다. 확인할 수 없는 속성은 조건 검사에서 통과시키지 않습니다.
- 이전 회차 응답과 위조한 근거를 거부합니다. 모델 실패 때는 조건과 선택을 유지하고 재시도·종료를 제공합니다.

후보 비율·질문 예산·거리 가중치·종료 제안은 연구용 규칙입니다. 가장 좋은 정책이라는 실험 결과는 아직 없습니다.

코드: 흐름 조정 (개발 브랜치의 `src/stylemate_memory/research.py`) · 코드: 상품 추천 (개발 브랜치의 `src/stylemate_memory/research_catalog.py`) · 구현 결정 (개발 브랜치의 `docs/decisions/0004-research-loop.md`)

## G 무엇을 검증했고 무엇이 남았나요?

아래 결과는 앞선 구현 작업에서 실제로 실행한 검증입니다. 이번 설명 페이지를 만들면서 제품 테스트를 다시 실행한 것은 아닙니다.

| 검증 | 결과 | 확인한 범위 |
|---|---|---|
| Python 3.11 | ok 147개 통과 | 기존 메모리와 새 연구 흐름의 오프라인 테스트 |
| Python 3.14 | ok 147개 통과 | 같은 테스트의 버전 호환성 |
| 실제 gpt-6-luna | ok 연결 확인 | 합성 요청의 추출·목표 추론·부분 선택 해석 |
| 실제 상품 화면 | ok 표시 확인 | LOOK 5개와 이미지 10개 로드 |
| 브라우저 상호작용 | ok 흐름 확인 | 선택·확인·재추천·확정·동의 저장·새 요청 |
| 화면과 설치 | ok 검증 완료 | 데스크톱·390px 모바일·오프라인 패키지 설치 |

첫 실제 모델 호출에서는 불필요한 조건 때문에 추천이 보류됐습니다. 현재 요청과 조건부 기억을 구분하도록 지시문을 보완했습니다. 보완 후 같은 합성 흐름이 통과했습니다.

```callout warn 테스트 통과와 연구 효과는 구분합니다
현재 결과는 코드 연결과 처리 경계를 확인합니다. 일반적인 취향 해석 정확도를 입증하지 않습니다. 사용자 취향 재현과 표현 부담 감소도 별도의 연구로 평가해야 합니다.
```

남은 작업은 상품 라벨과 코디 품질의 검수입니다. 다음으로 질문·비교·종료 정책을 파일럿으로 평가해야 합니다. RQ1·RQ2의 대조 조건과 평가 프로토콜도 합의해야 합니다.

실시간 재고·가격·사이즈·구매 연동은 후속 범위입니다. 전체 코디의 장기 저장과 다중 사용자 서비스도 후속 결정입니다.
