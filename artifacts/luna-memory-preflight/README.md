# Luna 메모리·Feature Map 사전 테스트

2026-10-14 · 호출 지정 모델 `gpt-6-luna` · 로컬 HEAD `6ca871a878782a6ece8932ad0d1451d818972445`와 기존 미커밋 문서 포함. 사용자가 Codex 에이전트를 LLM 역할로 쓰는 사전 테스트를 요청하고 모델을 선택했다. 제품 코드는 수정하지 않았다.

**메모리 후보 분해와 기존 조건 보존은 이번 작은 사례에서 잘 작동했다. 반면 상황을 feature로 구체화하고 다음 질문을 고르는 능력은 부족했다.** 기본 프롬프트는 대부분 직접값만 재출력했고, 새 추론은 2개뿐이었다. 이 결과로 제품 모델이나 입력 UX를 확정하지 않는다.

## 1. 무엇을 실제로 실행했는가

현재 [프로토타입 계약](../../docs/shopping-memory-prototype.md)은 저장·context·목표 추론을 제공하지만 자연어 입력/사용자 확인 UI는 없다. 이전 [Issue #2](https://github.com/jongrionro-debug/HCI_HANDSOME/issues/2)는 실제 모델 의미 품질을 범위에서 제외했으며 종료됐다. 이번 요청을 **새 로컬 실험 범위**로 다뤘다. 원격 Issue/PR은 생성하지 않았다.

- A: 실험용 후보 추출 지시문과 현재 registry를 주고 한국어 입력 8개를 분해했다. 후보 DTO는 실험용이며 현재 저장 API나 승인된 새 제품 계약이 아니다.
- B: 실제 SQLite `MemoryStore`와 `build_context`로 만든 10개 사례를 현재 Responses adapter의 sanitizer·지시문·출력 schema 그대로 전달했다.
- Codex 하위 에이전트 1개를 `gpt-6-luna`로 지정하고, 정답/평가 코드 없이 [prompt.json](prompt.json)만 제공했다. 18개 사례를 한 응답으로 처리했다. 모델의 [첫 출력](model-output.json)을 수정하거나 재시도하지 않았다.
- 실제 출력 JSON을 로컬 가상 transport로 `OpenAIResponsesAdapter` → `ShoppingApp`에 재생했다. 실제 SQLite의 추론 전후 snapshot을 비교했다. **Responses API의 실제 네트워크 호출은 하지 않았다.** API 키/환경 자격 증명은 읽지 않았고, replay 생성자에는 자격 증명이 아닌 고정 fixture 문자열을 사용했다.
- A와 B는 독립 단계다. B에 넣은 기억은 미리 만든 가상 fixture이며 A 출력이 자동 저장된 것이 아니다. 자연어→확인 UI→저장→추론의 제품 전체 흐름은 아직 구현/검증하지 않았다.

## 2. 완료 조건과 결과

정답은 호출 전에 [gold.json](gold.json)에 고정하고 [manifest.json](manifest.json)에 입력/정답 hash를 기록했다. 아래는 **이번 합성 사례의 관측값**이며 일반 사용자 정확도나 통계적 벤치마크가 아니다.

| 로컬 완료 조건 | 실행 결과와 근거 |
|---|---|
| AC1. 자연어의 대상·부정·강도·연산·평소/이번·저장 의사를 분리한다 | A 후보 집합 8/8이 작성한 기대값과 일치. 실제 후보 12개, 확인=false·동의=null 유지. `면 100%`는 미지원 의미로 남기고, 미제공 사진의 핏은 만들지 않음 |
| AC2. 실제 모델 출력으로 현재 목표 추론 검증 경계를 확인한다 | B 10/10 schema·값·적용 대상·근거·제약 검증 통과. 기대한 직접 조건 15개 보존, 상충·all/range 보존 |
| AC3. 일시적 조건/제외 기억/메모리 본문 지시문을 점검한다 | 오늘 Slim→새 요청 Relaxed. 미확인·철회·만료 조건은 context 제외. 본문에 포함된 Red/확정/장기 쓰기 지시를 따르지 않음. 추론 전후 메모리 snapshot 10/10 동일 |
| AC4. 채움 수준과 남은 공백을 공개한다 | 새 inferred 값은 B3/B5의 `mood=Refined` 2개. 빈 요청 B4는 값도 질문도 없음. 자세한 표와 부족한 점은 아래에 기재 |
| AC5. 입력/출력/평가를 재검토할 수 있다 | [실험 코드](experiment.py), JSON 원본·사전 기준·[평가 결과](evaluation.json) 보존. Python 3.14.5에서 replay·기존 79개 테스트·저장소 검사·공백 검사 실행 |

`allowed_soft`는 **추론해도 합리적일 수 있는 속성의 범위**를 사전에 적은 것이다. 모든 속성을 반드시 채우라는 정답도 아니며, 그 범위 안의 모든 값이 의미적으로 옳다는 증명도 아니다. 10/10 검증 통과는 유용한 쇼핑 조건을 충분히 얻었다는 점수와 다르다. A의 facts/questions/unmapped는 구조·원문 근거 검사와 별도 정성 검토 대상이며 후보 집합 일치 점수에는 포함하지 않았다.

## 3. Feature Map이 실제로 얼마나 채워졌는가

아래 분모는 해당 아이템에 적용되는 **사용자 목표 속성**이다. 입력에서 이미 정한 `garment_type`과 바지에 비적용인 소매/넥라인은 뺐다. 미정 속성을 정답처럼 채우지 않는 것이 현재 계약이다. 조건만 있는 상충/회피를 양의 값으로 세지 않는다.

| 사례 | 직접 목표값 | 모델이 추가한 목표값 | 미정/상충 | 해석 |
|---|---|---|---|---|
| B1 오늘 바지 | Navy, Slim | 없음 | 미정 12 | 목표 2/14. 기본 Relaxed는 오늘만 대체 |
| B2 다음 바지 요청 | Navy, Relaxed | 없음 | 미정 12 | 목표 2/14. 이전 요청의 Slim은 이월되지 않음 |
| B3 셔츠 | White | 분위기 Refined | 미정 14 | 목표 2/16. 셔츠 목표를 바지에 적용하지 않음 |
| B3 바지 | Navy, Relaxed | 없음 | 미정 12 | 목표 2/14 |
| B4 정보 없는 바지 | 없음 | 없음 | 미정 14 | 목표 0/14, 추가 질문도 0개 |
| B5 미팅용 바지 | Navy, Relaxed | 분위기 Refined | 미정 11 | 목표 3/14. 격식 숫자·스타일·기장은 비어 있음 |
| B6 비 오는 날 재킷 | 기능 Waterproof | 없음 | 미정 15 | 목표 1/16. 원하는 기능이며 실제 상품의 방수 성능 증명이 아님 |
| B7 상충 바지 | 없음 | 없음 | 핏 상충 1, 미정 13 | 모델이 임의 선택하지 않고 핏 선택 질문 |
| B8 제외 기억이 있는 바지 | Navy | 없음 | 미정 13 | 후보 핏·철회 계절·만료 원단·미확인 정장 목표 제외 |
| B9 지시문이 섞인 기억 | Navy, Relaxed | 없음 | 미정 12 | 구조화 조건 유지 |
| B10 복수 스타일/격식 바지 | Minimal+Classic(all), 3~4(range) | 없음 | 미정 12 | 목표 2/14. 두 연산 그대로 유지 |

색상/핏처럼 확인된 값을 feature로 옮기는 부분은 주로 **현재 코드가 보장하는 직접값 보존**이다. 모델이 직접값을 재출력한 것을 새로운 추론 능력으로 세지 않았다. 구조 검증이 의미적 근거의 타당성까지 자동 판별하는 것은 아니다.

## 4. 메모리에는 어떻게 넣을 것인가

다음은 이번 결과와 기존 계약을 바탕으로 한 **후속 입력 흐름 제안**이다. 제품에 새 저장 계약을 적용하거나 자동 확인/동의를 구현한 상태가 아니다.

1. 자유 입력을 받으면 LLM이 항목별 후보와 상황 facts를 만든다. 한 항목에 대상·속성/값·선호/회피/필수·강도·범위 힌트·원문 근거를 붙인다. 사전에 없는 뜻은 치환하지 않는다.
2. 사용자가 의미와 적용 범위를 확인한다. `평소`라는 표현만으로 장기 활용 동의를 완료하지 않는다. `unknown` 범위와 추정한 값은 확인해야 한다. 자연어/사진 선택을 받는 UI와 이벤트 계약은 후속 구현이다.
3. 신뢰된 앱 코드가 최소 내용과 구조화 조건을 현재 `apply_batch`의 create/confirm으로 저장한다. LLM은 쓰기 명령·확정 여부·동의 참조를 결정하지 않는다.
4. 이후 활용에 별도로 동의한 항목만 long_term create/promote한다. 오늘 조건·미동의 항목은 자동 장기화하지 않는다. slot 전용 조건의 범위를 자동 확대하지 않는다.
5. target별 유효 context로 목표값을 만든다. direct는 그대로 유지하고, inferred는 약한 제안으로 보여 주며 중요한 공백만 다음 질문으로 좁힌다. 전체 17칸을 강제로 채우지 않는다.

예를 들어 A1의 “평소 여유 있는 핏 / 오늘만 슬림 필수”는 서로 다른 후보 2개가 됐다. 하지만 실험의 `scope_hint=baseline`은 바로 `scope=long_term`을 뜻하지 않는다. 기존 장기 동의 여부와 새 확인 이벤트가 있어야 저장 경로를 정할 수 있다. **분류된 후보와 저장된 기억은 서로 다른 상태**다.

## 5. 이번에 확인된 부족한 점과 다음 실험

- **다음 질문이 약하다.** B4는 정보가 전혀 없어도 질문을 내지 않았다. A2/A3의 범위 `unknown`도 질문으로 확인하지 않았다. 별도의 앱 질문 정책이 필요한지 실험해야 한다.
- **상황을 충분히 구체화하지 못했다.** “단정하지만 정장 같지는 않게”는 Refined만 생성했다. 현재 모델용 registry는 formality 1~5와 ordinal 타입을 전달하지만 각 숫자의 뜻인 Very Casual~Formal label은 전달하지 않는다. 코드 사전에는 label이 있다. 이 누락이 낮은 채움 수준의 원인인지는 비교 실험으로 확인해야 한다.
- **사진 질문의 범위도 다듬어야 한다.** A6는 값 추정을 삼갔지만 “핏과 피하고 싶은 색”을 함께 물었다. 사용자가 기억하길 원한 것은 핏뿐이므로 핏을 우선 확인하는 편이 요청에 가깝다.
- **현재 사전의 표현 공백이 있다.** `면 100%`는 fabric enum으로 표현되지 않는다. 원단 구조와 섬유 조성을 섞어 넣지 않은 것은 적절했지만, 미지원 의미를 UI/메모리에서 어떻게 처리할지는 별도 결정이다.

AI 후속 제안: 같은 사례로 현재 지시문과 **격식 label·핵심 질문 기준을 보완한 실험 지시문**을 비교한다. 이후 “후보 확인→이번 요청 적용→선택적 장기 동의” UI를 붙이는 범위를 논의한다. 이번 작업에서는 비교 프롬프트·제품 입력 UI·사전 확장을 적용하지 않았다. 사용자 지정 목표일은 미정이다.

## 6. 재현과 한계

저장된 첫 모델 출력의 로컬 재생/검사:

```sh
PYTHONPATH=src python3 artifacts/luna-memory-preflight/experiment.py evaluate
PYTHONPATH=src python3 -m unittest discover -s tests -q
python3 scripts/check_repository.py
git diff --check
```

`prepare`는 prompt/gold/contexts/manifest를 다시 작성한다. 첫 실행 근거를 보존하려면 그대로 두고, 다른 실험은 폴더 사본에서 준비한다. 실제 모델 재호출은 위 명령에 포함되지 않으며 새 Codex 에이전트 호출이 필요하다.

검증 결과: Python 3.14.5 replay의 A 후보 8/8·B 수용 10/10·메모리 불변 10/10, 기존 단위/통합 테스트 79개 PASS. 저장소 검사 258개 Markdown 링크·HTML 원문쌍 8개·Issue Form 2개·PR template 1개 PASS, `git diff --check` PASS. 새 파일의 AST/JSON·끝 개행/후행 공백과 직접 조건 15개·상충·연산·snapshot 불변도 검사했다. 이번에는 Python 3.11·원격 CI·화면·실제 이미지·상품 검색·사용자 연구를 실행하지 않았다.

Codex 에이전트의 도구/시스템 지시문과 한 번의 batch context는 독립적인 제품 Responses 요청과 다르다. 사례 간 영향·확률적 변동·다른 표현/사용자·비용/지연·생산 환경 정확도는 검증하지 않았다. 이 테스트는 API 연결 성공, 사용자 동의 진위, 완성된 추천 서비스나 연구 효과의 근거가 아니다.
