부분 실패를 전체 성공으로 보고하지 않고 재처리할 레코드를 식별해라. 같은 원자료/버전의 처리 재시도가 중복 상품을 만들지 않으며 실제 Map 내용이 바뀌면 비교 후보의 최신성에 반영돼야 한다.

완료 조건: 직접 라벨 경로와 fake model 경로, 잘못된 인용/enum/출처 거부, 모르는 속성 유지, 사진/추론만으로 성능 hard 충족 금지, 실패/재시도/버전 변경. 공급해야 할 필수 데이터와 사람 검토가 필요한 미확인 사례를 A에 전달해라.

=== TASK B3 / 세션 B / 비교 회차·선택과 텍스트의 원자적 접수 ===

선행: 묶음 2 GATE 통과.

ComparisonRound/CandidateSet/Feedback 및 질문 상태를 A0 계약대로 저장해라. 후보 묶음은 발행 뒤 불변이고 교체는 새 set과 회차 version 증가로 표현한다. product_id/candidate_id/target_id를 구분해라.

submit_feedback 하나로 선택·부분 선택·같은 회차의 텍스트 최소 근거를 원자적으로 접수해라. selected/none/unsure/text_only/question_skipped를 구분하고 초기 텍스트의 null round/set을 지원한다. 선택 순서를 순위로 만들지 마라. 빈 text/null, 질문 참조, 상한, 이미지 부분 box/region을 검증한다.

선택한 카드뿐 아니라 발행된 모든 카드의 상품 Map·이미지 버전을 확인한다. 다른 회차/대상/소유자의 선택, 바뀐 후보 묶음, 오래된 표시 snapshot의 확인/동의를 거부해라. 상품 최신성 조회는 D의 고정 인터페이스를 사용하고 상품 DB 쓰기를 맡지 마라.

신뢰된 사용자 조작 이벤트를 A0 규칙대로 기록·검증해라. 선택·내용 확인·future_reuse·최종 선택·종료를 서로 대체하지 않는다. 질문 표시나 건너뛰기로 동의/답변을 만들지 마라.

접수 성공과 해석 진행을 분리하고 해석 실패는 pending으로 조회 가능하게 해라. 같은 Evidence로 재처리하며 접수 영수증을 뒤늦게 해석 성공으로 변조하거나 원문을 복제하지 마라.

완료 조건: 선택+텍스트 동시 rollback/멱등, 부분 좌표·질문·오래된 모든 카드 버전 검증, 새 set 불변성, 재시작 뒤 회차/선택/질문 복원, 접수 성공 후 모델 실패와 안전한 재처리. UI는 아직 연결 완료가 아니다.

=== TASK C3 / 세션 C / 근거 기반 목표 Feature Map ===

선행: 묶음 2 GATE 통과.
담당: inference.py, 목표 모델 schema/prompt에 필요한 llm.py/codex_llm.py 수정, tests/test_inference.py와 관련 모델 테스트. app.py의 서비스 연결은 A2 책임이다.

C2 근거 묶음과 A1 사전으로 v1 TargetMap을 생성해라. 모델 출력은 suggestions/questions만 받고 직접 제약은 코드가 결합한다. 모든 PI/FEA 항목의 값 필드와 status를 계약대로 제공하며 모르는 값은 null로 둔다.

specified/inferred/unspecified/indifferent/not_applicable/unsupported/conflict, polarity/strength, any/all 연산을 보존해라. 회피-only 조건을 긍정값으로 바꾸지 않고 indifferent가 기존 hard 조건을 지우지 않게 해라. 문장 확인만으로 binding을 specified로 만들지 마라.

어떤 현재 요구/장기 취향을 적용·제외·일시 대체·상충했는지 근거에 연결한다. 사용한 evidence/memory/binding·request/profile·registry·index 버전의 basis를 반환하고 A2가 응답 적용 직전 다시 확인할 수 있게 해라. TargetMap이나 과거 요약을 새 사용자 근거로 저장하지 마라.

완료 조건: Navy/Wide 장기 + 이번 Slim → 현재 Navy/Slim, 새 요청에서 장기 유지; “빈티지” 임의 소재/색 채움 금지; 대상 격리·미확인 조건·hard 보존·충돌·null 상태·모델의 확정/권한 필드 거부; 유효하지 않은 source의 목표 반영 금지. adapter는 fake를 사용하고 stale 검증 인터페이스를 A에 전달해라.

=== TASK D3 / 세션 D / 상품 검색·랭킹·비교 후보 ===

선행: 묶음 2 GATE 통과. TargetMap은 A0 계약 fixture를 사용해 C3와 독립 개발한다.
담당: product_search.py, comparison.py 등 상품 검색/후보 모듈, 관련 테스트와 합성 상품 fixture. 회차 저장/사용자 memory/모델 gateway는 수정하지 않는다.

상품 Map과 TargetMap을 비교해 대상 적합성·확정 hard 조건을 먼저 필터링하고 soft 선호로 순위를 정해라. 가격 경계·FEA 성능 등 실행 의미/근거가 없는 조건을 충족으로 간주하지 않는다. 연산 정본은 constraints이며 평탄한 표시값만으로 any/all을 실행하지 마라.

필터 후 미정/미확인 요소를 구체화할 비교 묶음을 만든다. 기본 3개, 필요한 2축 비교 4개, 세부 비교 2개는 조정 가능한 초기 가정이다. 핵심 1~2개 축의 실제 차이·중복·상품 Map 근거를 연결하고 부적합한 상품으로 개수를 채우지 마라. 없는 조합이나 통제된 비교를 꾸미지 않는다.

후보가 없을 때 제약을 자동 완화하지 않고 유지/사용자 조정/종료를 위한 구조화 결과를 반환해라. 선택 이유 가설을 확정 필터로 사용하지 않는다. 각 카드의 stable candidate_id, target/product/map/image version과 생성 basis를 B3가 저장할 수 있게 반환해라.

완료 조건: hard 위반 및 unknown 제외, 조건 만족 상품만 soft ranking, 모든 상품 탈락, 중복/적은 후보/없는 조합, 여러 target 간 격리, 변경된 상품/이미지의 basis 차이. 상품 검색을 사용자 기억 검색과 별도로 측정해라.

=== TASK B4 / 세션 B / 철회·삭제·만료와 파생 자료 정리 ===

선행: 묶음 3 GATE 통과.

v1 전체 저장 객체를 대상으로 기존 보관/삭제 계약을 완성해라. 요청 삭제와 별도 동의된 장기 기억 삭제를 구분하고 장기 독립 snapshot만 필요한 범위에서 유지한다. 장기 삭제/철회는 promote 가족·snapshot·사본·해당 파생 참조에 전파한다.

supports와 복제/derived_from 삭제 관계를 구분해 무관한 기억의 연쇄 삭제를 막아라. 혼합 Evidence/요약/피드백에 삭제 대상 내용이 남으면 필요한 부분을 제거하고 유효한 근거로만 재구성한다. 삭제된 내용을 목표·색인·캐시·과거 모델 응답에서 재유입하지 못하게 해라.

원본 동의·scope·retention은 조회/재색인/요약으로 연장하지 않는다. 원본 version과 다른 색인 적중은 배제한다. 파생 저장소나 SQLite 정리가 실패하면 삭제 완료를 반환하지 말고 재시도 가능한 상태를 정확히 표현해라. 아직 존재하지 않는 색인 제품을 만들 필요는 없지만 현재 파생 인터페이스의 실패는 fake로 검증한다.

기존 24시간의 내용 없는 삭제 영수증·요청 tombstone·동일/다른 본문 재시도를 유지한다. 삭제 영수증에 원문/대상 ID/일반 payload digest를 새로 남기지 마라. 실제 사용자 DB가 아닌 임시 합성 DB만 사용한다.

완료 조건: 요청 삭제 후 독립 장기 유효성, 장기 삭제 후 가족/사본/파생 제거, supports 비연쇄 삭제, 혼합 근거 처리, 만료/재시작/재색인/늦은 응답에서 재유입 없음, 정리 실패·rollback·재시도. 저장매체/사용자 백업 소거까지 보장했다고 보고하지 마라.

=== TASK A2 / 세션 A / 로컬 서비스와 실행 경로 연결 ===

B/C/D 모듈을 하나의 실제 흐름으로 연결해라: 사용자 피드백 원자 접수 → 추출 → 후보 저장 → 필요한 내용/binding 확인 → 유효 기억 조회 → 목표 Map → 상품 검색/후보 발행 → 피드백 반복. 온보딩·동일 요청 재개·새 요청·최종 선택·종료·별도 장기 활용·기억 수정/철회/삭제도 연결한다.

접수 실패, 접수 성공+해석 pending, 목표 보류, 상품 없음, provider 실패를 구분해라. 사용자가 재시도할 때 같은 근거·batch를 중복 작성하지 않는다. 모델 실패를 rule의 실제 성공으로 자동 전환하지 마라.

로컬 전용 서버의 기존 Host/Origin/요청 크기/오류 노출 경계를 유지하고 임의 파일 읽기나 공개 사용자 API로 넓히지 마라. 소비자 정적 자산 제공과 E1의 command/state를 연결하되 E 화면 파일의 기능 수정은 E2에 맡겨라. inspector의 개발자 관찰 기능도 실제 적용 계약에 맞춰 최소 보완한다.

외부 DB/상품 데이터 경로와 provider/model을 설정으로 공급하게 해라. 기본 실행은 fake, openai는 명시적 선택일 때만 구성한다. import/demo/test는 실제 OPENAI_API_KEY나 로그인 파일을 읽지 않는다. 사용자가 향후 설정할 환경변수 이름과 데이터 가져오기/Map 생성/서버 실행 명령을 master에 정확히 문서화해라. 이 작업에서는 실제 키를 설정/열람하거나 openai 호출을 실행하지 마라.

완료 조건: fake transport+합성 상품으로 텍스트→추천→피드백→확인→재검색→종료/별도 저장의 서비스 통합 통과; 재시작/새 요청/삭제/늦은 응답 검증; 기존 CLI/관찰 경로 및 패키징 검증. UI 클릭 완주는 E2에서 확인한다.

=== TASK E2 / 세션 E / 실제 로컬 API 연결과 브라우저 완주 ===

선행: A2 통합 검증 통과.
담당: E1의 소비자 화면 자산, UI 전용 브라우저 검증/테스트. app/store/서버 정책은 수정하지 말고 A에 필요한 수정 내용을 전달한다.

fixture adapter를 A2의 실제 로컬 API에 연결해라. 화면 완료 표시를 실제 접수/해석/확인/검색 상태와 일치시켜라. 실제 API는 로컬 backend를 뜻하며 외부 OpenAI는 fake provider로 유지한다.

합성 데이터로 온보딩→자유 요청→이미지/부분·복수 선택+“A의 색에 B의 핏” 텍스트→필요한 확인→더 보기→최종 선택→장기 저장 거부/선택을 각각 완주해라. 상품 없이 종료, none/unsure/skipped, 미정 유지, 새 요청과 기존 요청 재개도 검증한다.

서버 재시작·페이지 새로고침 뒤 필요한 근거 상태를 복원하고 자동 장기 저장을 하지 않는다. 처리 중 입력 보존·중복 클릭·응답 순서 역전·stale·모델 오류·빈 검색 결과·이미지 로딩 실패를 사용자에게 구분해 보여줘라.

UI에 제품 사용자가 알 필요 없는 내부 DB/version/모델 prompt 정보를 노출하지 마라. 기본 흐름에서 모든 37개 사전 항목을 채우게 하거나 선택 이유를 매번 강요하지 않는다.

완료 조건: 실제 로컬 서버에서 브라우저 클릭 흐름, 화면과 DB 상태 대응, 키보드·부분 선택 좌표·좁은 화면·오류 후 재시도 검증. 스크린샷/DOM만 확인하고 저장·동의 정확성까지 검증했다고 보고하지 마라. 실제 외부 모델/상품 의미 품질은 미검증으로 남긴다.

=== TASK D4 / 세션 D / 오프라인 평가와 데이터 교체 리허설 ===

선행: A2 통합 검증 통과. E2와 병렬로 실행하되 E의 서버/DB를 공유하지 않는다.
담당: 합성 평가 fixture, 작은 오프라인 평가 스크립트와 평가용 테스트. 기존 제품/저장/모델/UI 코드를 동시에 수정하지 않는다. 발견한 결함은 A에 넘긴다.

master의 대표 시나리오를 기반으로 재현 가능한 오프라인 입력/기대 경계를 구성해라. 같은 입력으로 구조 검색·키워드 검색·fake semantic 연결의 동작을 비교하고, recall/오탐/근거 묶음 완전성/필수 조건 보존과 호출·지연을 따로 기록해라. fake의 수치를 실제 임베딩이나 모델 품질로 해석하지 않는다.

상품 측에서는 hard 위반률, unknown의 잘못된 충족, 후보 중복, 실제 존재하지 않는 비교 조합, 결과 없음의 처리를 검증해라. 사용자 기억 검색과 상품 검색의 지표를 섞지 마라. 실제 API 토큰·비용은 계측 경계만 준비하고 fake 수치를 실제 과금으로 표시하지 않는다.

기본 fixture와 다른 별도 합성 상품 파일을 새 외부 임시 경로에 넣고 가져오기→Map 생성→검색까지 실행해라. 코드 수정 없이 데이터 교체가 가능해야 한다. 잘못된 수집 자료에 무엇을 보완해야 하는지 위치와 이유를 반환하는지도 검증한다.

RQ·조건·설문·분석 계획을 바꾸거나 참가자 데이터 수집/실험 플랫폼을 추가하지 마라. 이번 평가는 개발 검증이다. 스크립트 사용법·입출력·관찰 한계를 A가 master에 반영할 수 있게 전달한다.

=== TASK A3 / 세션 A / 최종 통합과 연결 준비 완료 판정 ===

선행: 묶음 6 GATE 통과. 다른 세션은 편집을 멈춘 상태다.
담당: 최종 통합에 필요한 좁은 수정, docs/master.md 및 실행 자원. 새 기능/스택/크롤러/실제 API 호출은 추가하지 않는다.

전체 diff와 미추적 파일을 검토하고 담당 세션의 연결 누락/중복 정책/계약 불일치를 수정해라. 단위 통과만으로 전체 완료를 선언하지 말고 실제 로컬 fake 실행 경로와 브라우저 시나리오를 검증해라. 구조적 미완료가 남으면 해당 TASK의 좁은 보완 범위를 제시하고 미완료로 보고해라.

필수 검사:
PYTHONPATH=src python3 -m unittest discover -s tests -q
PYTHONPATH=src python3 -m stylemate_memory.cli demo --synthetic
PYTHONPATH=src python3 -m stylemate_memory.cli features
python3 scripts/check_repository.py
git diff --check
추가로 실제로 구현한 상품 가져오기/Map 생성 명령, 소비자 서버 실행, 별도 합성 카탈로그 교체, fake transport의 OpenAI wire 계약, 패키지에서 사전/화면 자원 로딩을 검증해라.

다음 완료 조건을 코드/실행 근거로 판정해라:
1. 자유 표현을 매핑 없이 보존하고 같은 요청 재개/새 요청 격리가 된다.
2. 확인·binding 확인·동의·최종 선택·종료가 분리되고 장기 원본/현재 예외가 유지된다.
3. 목표 Map의 직접 제약·미정·충돌·근거·최신성이 보존된다.
4. 공급 상품 자료에서 Map 생성/검색/실제 이미지 참조 표시/비교/선택+텍스트 재탐색이 연결된다.
5. stale·오류·없음·미확인 성능·삭제/만료/재색인·중복 batch가 안전하게 처리된다.
6. 코드 수정 없이 외부 상품 파일과 명시적 OpenAI API 설정을 연결할 수 있다. 실제 API 접근권한/의미 품질까지 검증했다는 뜻은 아니다.

master의 현재 구현/실행/다음 작업을 실제 상태로 갱신하고 아직 미구현인 실제 의미 검색·크롤러·실제 모델 평가·사용자 연구를 분리해라. 원본 사전의 runtime_implemented 같은 상태 표시는 실제 완성 범위를 확인한 뒤 필요한 메타데이터만 갱신하고 값·출처는 보존한다.

최종 전달은 다음을 간결하게 제시해라: 실행 명령, 나중에 공급할 상품 파일의 최소 형식과 이미지/라벨 조건, API 환경변수와 gpt-6-luna 설정 방법, 합성 검증 결과, 실제 연결 뒤 수행할 smoke test, 남은 제약. API 키 값은 요청하거나 출력하지 마라. 실제 API smoke test는 이 작업에서 실행하지 않는다.

=== GATE / 세션 A / 각 병렬 묶음 뒤 반복 ===

직전 병렬 묶음의 모든 담당 세션이 끝났다. 공통 규칙을 적용해 현재 변경을 통합 점검해라. 새 TASK를 자동으로 시작하지 마라.

담당별 완료 보고와 실제 코드·테스트를 대조하고 공통 함수/DTO·오류·version·소유 파일 충돌을 확인해라. 완료 보고가 전달되지 않았으면 파일 존재만으로 완료를 추정하지 말고 해당 작업의 완료 조건과 실행 근거를 직접 확인해라. 다른 세션이 아직 수정 중이면 전체 통합 검증을 시작하지 마라.

전체 unittest, 가상 demo, 사전 출력, 저장소 검사와 diff 검사를 실행한다. 아직 연결 전인 단계는 모듈 계약 테스트와 기존 진입점 호환을 구분해 확인한다. 후속 단계가 미구현인 사실을 숨기거나 모든 미래 기능을 당겨 구현하지 마라.

현재 묶음 때문에 발생한 작은 연결 결함은 수정하고 필요한 검사만 다시 수행해라. 큰 결함은 담당 세션에 붙여 넣을 구체적인 보완 프롬프트로 돌려주고 통과 전 다음 묶음을 열지 마라. 테스트를 삭제·완화해 통과시키지 않는다.

docs/master.md에는 실제 구현 변화·실행 방법·남은 연결만 갱신해라. 별도 계획/일지/세션 보고 MD를 만들지 마라. 결과는 “이번 묶음 통과/미통과, 검증 근거, 다음에 입력할 TASK ID”로 간결하게 알려줘라.
